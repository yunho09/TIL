로컬 작업 브랜치가 base 브랜치(예: `develop`)보다 수십~수백 커밋 뒤처져 있으면, 작업 트리·mock 코드만 보고 "이 기능/API가 아직 없다"고 단정하기 쉽다. 실제로는 이미 다른 PR로 merge돼 있는데, 그 변경이 로컬 브랜치엔 반영되지 않았을 뿐인 경우다.

## 문제

한 세션에서 "직원 목록 조회 API가 없다", "단체예약은 mock만 있고 API 연동이 안 됐다"고 여러 차례 단정했으나, 실은 두 가지 다 PR이 이미 `develop`에 merge된 상태였다. 원인은 작업 중이던 브랜치가 분기점(8/28) 이후 `develop`에 쌓인 108개 커밋을 한 번도 받지 않은 채였던 것 — `git log`나 코드 검색은 항상 로컬 작업 트리 기준으로만 동작하므로, 뒤처진 브랜치에서는 "없다"는 결론이 "아직 내 브랜치에 없다"일 뿐 "저장소 전체에 없다"가 아니다.

## 대응

기능이나 API의 부재를 근거로 진단·제안하기 전에, 특히 세션이 오래 지속됐거나 브랜치가 오래된 경우:

```bash
git fetch
git rev-list --count HEAD..origin/<base-브랜치>   # 뒤처진 커밋 수
git log HEAD..origin/<base-브랜치> --oneline       # 무엇이 있는지
```

뒤처진 커밋이 있다면, "없다"고 단정하기 전에 base 브랜치 쪽 코드도 확인한다. 특히 다음 단계가 "기존 구조 분석 후 계획 수립"이라면, 분석 시점 이전에 base를 merge/rebase해 최신 패턴을 기준으로 분석하는 게 낫다 — 안 그러면 이미 있는 유틸/훅/API 구조를 모르고 계획을 세웠다가 나중에 다시 써야 한다.
