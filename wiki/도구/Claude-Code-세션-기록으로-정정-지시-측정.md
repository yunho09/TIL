# Claude Code 세션 기록으로 정정 지시 측정

Claude Code 세션 기록(jsonl)에서 "AI를 바로잡은 사용자 메시지"를 세어 하네스·규칙 개선 전후를 비교하는 방법과 함정. 기본 보관 30일이라 개선 전 기준값을 쓰려면 보관 기간부터 늘려야 하고, 센 방식이 다르면 사람끼리 수치를 합칠 수 없다.

## 기록 위치와 한계
- Claude 세션은 `~/.claude/projects/<작업폴더 경로를 -로 바꾼 이름>/*.jsonl`에 남는다(예: `-data-project-ToyVillage-Admin-FE`). Codex 기록은 별도이고 동료 기록은 그 사람 컴퓨터에만 있어 직접 못 본다.
- **`gitBranch` 필드는 대부분 `HEAD`로만 남아** 브랜치 추적에 못 쓴다 → tool_use 입력의 `git checkout`/`switch`/`gh pr create` 명령으로 추적. 작업 폴더 경로로 줄 수를 세면 worktree가 섞여 크게 부풀려진다(61,038줄 사례).
- **기본 보관 30일**. `~/.claude/settings.json`에 `"cleanupPeriodDays": 365`를 추가해 늘렸다(전역 설정이라 사용자 승인 후 변경, JSON 재검증). 측정 원본(분류 결과·스크립트)은 임시 폴더에 두면 날아가므로 노션 등 안 지워지는 곳에 남긴다. 팀 저장소에 커밋하지 않기로 했다(외주 저장소, 그리고 프롬프트 원문에 JWT가 섞여 있었음 — **프롬프트 원문은 저장소에 두지 않는다**).

## 측정 방법과 함정
- **키워드 선필터("아니", "다시", "규칙")는 누락이 크다.** 같은 세션을 키워드로 거르면 26건/917개였는데 프롬프트 980개를 전부 읽고 분류하니 하네스 원인 65건. 정정 표현 없이 지시한 경우가 빠지기 때문 → 전수 읽기로 재집계.
- **세는 기준을 먼저 고정한다**: 정정 지시 = 직전 AI 결과·행동을 바로잡는 메시지(새 요청 제외) / 하네스가 막았어야 할 것 = 규칙·검사·기준 파일이 하네스에 있었다면 안 생겼을 정정 / 원인별 분류 / 게이트 절차 프롬프트. 한 사람은 "하네스가 원인인 것만", 다른 사람은 "모든 정정 후 막을 수 있던 것"을 세서 100개당 2.8건 vs 13.7건처럼 5배가 났다 — 합치거나 비교하려면 같은 기준·스크립트로 다시 세야 한다.
- 메시지 수 기준이라 같은 일을 여러 번 말한 경우가 포함된다. 분류를 AI가 했는지 본인이 했는지도 비율 차이의 원인이 된다. 개인 환경 문제(포트·작업 폴더)·기능 버그·범위 논의는 하네스 대상에서 제외.
- **정정 지시 합산 사례 (2026-10-08)**: 팀 규칙 정정은 윤호 34건(전수 읽기, 8개 규칙 합계 7+6+5+5+4+4+2+1)과 지환 15건(프롬프트 기준)/20건(규칙 기준)이 **판정 방식이 달랐다** — 지환은 롤백·"더"·"다시"·"~하지마"가 붙은 것을 정정으로 보고 최초 지시는 제외(포함하면 37건), 연속 재전송은 1건. 한 프롬프트에 규칙이 3개 들어간 경우가 있어 프롬프트 기준/규칙 기준을 따로 적어야 한다. 합계 49건은 프롬프트 기준으로 맞춘 값. 4주 뒤 재측정은 같은 판정 조건·같은 스크립트로.
- **테스트 실행 횟수 판정 기준**: `playwright test`·`verify:e2e`·`run-scenarios`·`verify:api` 등이 포함된 호출과 결과를 짝지음 / 백그라운드 실행 제외 / 출력에 `N failed`·`N passed`·`Running N test`·`✘` 흔적이 있는 것만 집계(안 거르면 설정 파일·git diff 출력이 100건 섞임) / 실패 = `N failed` 또는 `✘`(출력이 잘려 요약줄이 없는 경우 포함). 같은 (failed, passed, duration)은 중복 실행으로 보고 한 번만 센다. 결과: 윤호 457회 중 196회(43%, 9/7~10/6), 지환 526회 중 214회(41%, 7/27~9/29). 세션이 30일 지나 지워져 9/7 이전은 없다. 유형 분석은 [[Playwright-e2e-실패-유형-분류와-취약-선택자-패턴]].
- **after 재측정 (윤호 몫, 2026-11-13)**: 기간은 하네스 개선 끝난 다음 날(10/21)부터 퍼블리싱 하네스를 또 바꾼 11/10 전까지(약 3주)로 잘라 이후 변경이 섞이지 않게 했다. 기준 문서(rubric) 하나를 정해 두고 프롬프트를 묶음으로 나눠 서브에이전트 4~5개가 **같은 기준으로 동시에 전수 분류**, 정정이 유독 적은 묶음(68개)은 앞 결과를 안 보여 주고 다시 분류해 "막을 수 있던 것" 판정이 전부 같음을 확인. 결과(before 8/11~9/29 980개 → after 233개): 막을 수 있던 정정 65건(100개당 6.6) → **4건(1.7)**, 팀 규칙 원인 34→0, 입력 기준(옛 Figma·명세) 11→0, 화면 불일치 16→4(스크린샷 비교 게이트는 미구축이라 예상대로), 게이트 절차 프롬프트 5.2%→6.4%(재승인 때 변경분 확인 단계 증가 추정).
- **비율보다 "100개당 건수"**: after에는 글쓰기 세션이 절반 넘게 섞여 "정정 중 비율"이 36%→11%로 나오지만, 코드 고친 세션만 보면 12건 중 4건(33%)이라 before와 같다 — 정정 전체가 같이 줄면 비율은 안 움직인다. 12건 표본이라 1~2건에도 출렁이므로 분모를 프롬프트 수로 둔다. 한계: 윤호 몫만·기간이 before(7주)보다 짧음·before 분류 원본이 없어 같은 정의로 새로 분류·Codex 작업 제외. 팀 합산은 다른 팀원이 같은 방법으로 세어 오기를 기다리는 중(메모리에 결정 기록): 스크립트·분류 기준을 한 프롬프트로 만들어 그 사람 Claude Code에 붙여 넣게 하고, 원문 대신 숫자 블록만 받으며, 이쪽 숫자는 넣지 않아 분류가 끌려가지 않게 한다(디스코드 한 칸 2,000자 제한 때문에 약 9,300자 프롬프트는 파일로 전달).
- 측정 결과와 적용: [[하네스-점검-결과와-개선-방향]]. 평균·중앙값 함정은 [[ToyVillage-Admin-FE/프로젝트-현황]]의 PR 지연 재계산 절 참고.
