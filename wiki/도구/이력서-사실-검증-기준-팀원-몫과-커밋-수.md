# 이력서 사실 검증 기준 — 팀원 몫과 커밋 수

노션 정리·AI 분석 페이지를 그대로 이력서에 옮기면 **팀원 몫이 섞이거나 수치가 부풀려진다**. 토빌·Commonly·JOBIS 이력서 초안을 PR·커밋과 문장별로 대조하며 얻은 검증 기준. (Claude 세션 관찰)

## 커밋 수 세는 법
- `origin/develop`에서 `git rev-list --count --no-merges`, **이메일로 작성자 묶기**(이름 필드는 yunho09/yunho/JANG YUN HO로 갈려 숫자가 달라짐).
- `--all`(안 머지된 브랜치 포함)은 부풀려진다. 예: Commonly `--all` 268 vs develop 259, 이력서에는 develop 기준(196개 중 140개). JOBIS는 2월 이후 develop 기준 377개 중 202개.
- 레포 전체 대비 커밋 수를 "학생 앱" 같은 특정 영역 줄에 붙이면 그 영역 커밋처럼 읽힌다 → 헤더/역할 줄에 둔다.

## 내 몫 판별
- 최초 연동·최초 작성자를 PR 작성자와 `git log --follow`로 확인. 후속 수정만 했다면 "구현"이 아니라 **"결함 수정과 확장"**으로 쓴다.
- 예: 공지 목록·모집의뢰서 목록은 팀원이 만들고 본인은 상세·등록·수정, 필터 연동 오류 수정만 했다 → 문구를 본인 몫만 남겨 수정.
- `createDomainApi`처럼 노션엔 성과로 적혀 있어도 git상 최초 도입자가 다른 경우가 있다 → 면접에서 위험하므로 본인 설계로 쓰지 않는다.
- 노션에 적힌 "e2e로 찾은 버그"는 수정 커밋이 e2e 추가 커밋보다 앞서면 e2e 성과가 아니다 → 기록으로 확인되는 것만.
- 백엔드 이슈 작성자가 다른 사람이면 "고아 데이터 발견" 같은 성과를 본인 것으로 쓰지 않는다(본인이 먼저 찾아 전달했다는 확인이 있으면 가능).

## 표현 수위
- PR 본문의 검증이 "빌드·단위 테스트"뿐이고 배포 후 확인 기록이 없으면 "정상 저장"이 아니라 **"요청 형식을 백엔드 계약에 맞춰 수정"**으로 낮춘다.
- 테스트 통과 수는 최신 PR 본문 기준으로 갱신(331 → 342).
- 실사용자 기록이 없으면 "실서비스"라고 쓰지 않는다.
- 측정하지 않은 "측정 예정" 항목은 결과로 적지 않는다 → 삭제.
- 회고 문장을 AI가 새로 쓴 경우 본인 기록에 없는 말이므로 사용자가 직접 검토해 정하게 한다.
- 노션 프로필 한 곳에만 있는 항목(수상, 인턴 멘토링 등)은 사용자에게 사실 여부를 확인하고, 사용자가 확인하면 유지.

## 사용자 확인 결과 (2026-11-04)
- Commonly **민원인 본인 발급**: PR상 백엔드 설정(`CERTIFICATE_SELF_ISSUE_ENABLED` 기본 false)으로 닫혀 있어 낮춰 썼으나, 사용자가 "원래 다 됐음"이라 확인 → 배경 문구를 원래대로("본인 경력증명서를 직접 발급받는") 되돌림. 서브에이전트의 '근거 없음' 판정은 기록 부재일 뿐 거짓 판정이 아니므로 **사용자 확인이 최종**.
- **5기 인턴 2명 멘토**: 레포엔 기록이 없고 노션 프로필에만 있었으나 본인이 아는 사실이라 유지. 본인 활동처럼 레포로 증명할 수 없는 항목은 한 번 확인하되, 사용자가 이유를 되물으면 근거가 노션 한 곳뿐이라서라고 답하고 그대로 둔다.
- 회고 줄(Claude가 새로 쓴 문장)은 사용자가 직접 보고 정하게 남기고, 사용자가 "결과·회고가 없다"고 하면 자리를 만들어 채우되 "합의"처럼 **실제로 확인된 단계까지만** 쓴다(예: 유저별 면접 조회 API는 9/16 기준 없어서 "만들기로 합의"까지만).
