# Chrome MCP 네트워크 관측 함정과 멀티에이전트 감사 운영

Claude-in-Chrome 계열 도구로 라이브 사이트를 감사할 때 겪은 측정 오탐과, 에이전트 3개를 병렬로 돌릴 때의 운영 요령. 핵심은 **도구 출력만 믿고 "조용한 데이터 유실" 같은 중대 결론을 내리지 않는 것**이다.

## 도구 함정
- `read_network_requests`가 **같은 URL의 OPTIONS(preflight)와 본요청을 1건으로 합치면서 상태코드를 잘못 붙인다**. `PUT /api/human/5`가 503으로 찍혔지만 실제로는 204로 성공(이름 변경이 재조회에서 반영됨)이었고, "실패해도 완료 표시" 보고는 철회됐다. 세션 내내 "Found 1 network request"만 나온 것도 같은 현상.
  - 대응: 실패는 **화면 문구 / 페이지 내 fetch 래퍼가 잡은 예외 / 직접 fetch 결과** 중 독립 신호 2개 이상으로 교차 확인. 성공 화면도 믿지 말고 API로 재조회해 저장 여부 확인(실제로 등록·수정 모두 이렇게 검증).
  - 반대 사례: 업로드 503은 화면 에러 + fetch 예외(`Failed to fetch`) + 도구 로그 3신호가 일치해 확정. 같은 입력 조건에서 파일만 바꾸는 A/B(깨진 zip → 읽히는 500, 정상 워크북 → CORS 없는 503)로 실패 단계를 좁혔다([[에러-응답-CORS-헤더-누락-상태코드-차단]]).
- 브라우저 확장은 `localStorage`의 토큰 값 읽기를 `[BLOCKED: Sensitive key]`로 차단한다. 토큰을 꺼내지 않고 **페이지 컨텍스트 안에서 그대로 쓰는 호출**로 우회해야 한다. 비밀번호는 에이전트가 입력하지 않고 사용자가 직접 로그인한다.
- 폼 컨트롤(라디오 등)이 접근성 트리에서 안 잡히면 JS 클릭이 안정적이었다(단, 스크롤 위치가 안 바뀌어 위치 측정이 왜곡됨 — [[API-에러-메시지-우선순위와-화면-밖-렌더링]]).
- 로그인 토큰이 1시간 만료이고 갱신 엔드포인트가 없어, 긴 감사 중 세 탭이 모두 로그아웃됐다 → 세션 길이를 감안해 라이브 단계를 몰아서 진행.

## 멀티에이전트 감사 운영
- 에이전트별로 **전용 탭 하나**, 탭 침범·로그아웃·삭제 실행 금지, 테스트 데이터는 이름 충돌 없게(`테스트대상자`, `…2`) 못박는다. 이미 확인한 사실은 브리핑에 넘겨 중복 조사를 막는다.
- 사용자가 "에이전트 3개로 한 방에" 지시했는데 메인이 직접 클릭하고 있으면 어긋난다 — 소스 감사 후 **같은 에이전트에게 라이브 검증까지 이어서** 시킨다(SendMessage).
- 보고가 길면 **중간에 잘린다**. 파일로 쓰게 하되(scratchpad), 서브에이전트는 하네스가 파일 쓰기를 막을 수 있어 그땐 1/3, 2/3, 3/3으로 **나눠 메시지로** 받는다.
- 에이전트끼리 결론이 충돌하면(403 vs 401, 503 + "완료" 표시) 각자 근거를 교차 대조시켜 매듭짓고, 틀린 쪽이 스스로 철회하게 한다. 사용자에게 이미 전달한 오보는 명시적으로 정정한다.
- 결과를 "소스·번들로만 확정"과 "실제 클릭으로 확인"으로 **구분 표기**한다(상류가 막혀 도달 불가한 항목이 많았음).
- 비용 관점은 [[Claude-Code-서브에이전트-fan-out-토큰-과다소모]] — 이번엔 독립적이고 덩어리가 큰 3앱 감사라 fan-out이 타당했다.
