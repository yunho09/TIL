# GA4 — 내부 직원용 어드민 SPA에 붙일 때 체크리스트

일반 소비자 서비스용 GA4 가이드를 그대로 내부 관리자(어드민) 도구에 적용하면 놓치는 지점들. 아직 실제로 도입하지는 않았고, 도입 제안서를 검토하며 정리한 내용이다(Claude 보충 다수 포함).

## Sentry와의 역할 차이
- **Sentry** = 뭐가 깨졌는지 (에러·성능)
- **GA4** = 뭘 쓰는지 (페이지·기능 사용량·이동 흐름)
- 내부 직원용 도구는 유입·전환 분석이 의미 없으므로 GA4는 **기능 사용 분석**(어떤 메뉴를 쓰는지/안 쓰는지, 어떤 단계에서 이탈하는지)으로 용도를 한정해야 한다.

## SPA 페이지뷰
- GA4의 자동 "history 변경" 수집을 끄고, 라우트가 바뀔 때 직접 페이지뷰를 전송해야 중복 집계를 피한다.
- 라우트는 실제 값이 아니라 패턴(`/species/:speciesId`)으로 보내야 ID별로 잘게 쪼개지지 않는다.

## 놓치기 쉬운 개인정보 노출 지점
- 라우트를 패턴으로 바꿔도 `page_location`에는 **전체 URL**(쿼리스트링 포함)이 그대로 들어간다. 목록 화면의 검색어·필터 값이 이름 등 개인정보를 담고 있을 수 있으므로 **쿼리스트링을 뗀 주소**를 보내야 한다.
- `page_title`도 문서 제목을 그대로 쓰면 위와 같은 문제가 생길 수 있어 고정값을 쓰는 게 안전하다.
- `user_id`는 굳이 해시하지 않아도 된다 — 숫자 ID 해시는 쉽게 역산돼 보호 효과가 없고, 내부 시스템 ID 자체는 개인정보가 아니다. 오히려 "누가"보다 **역할별 사용량**(`role` 같은 user property)이 분석에 더 쓸모 있다.

## 이탈 지점을 보려면 이벤트 설계가 먼저
- 기능 하나당 이벤트 하나(`account_create`)로는 어디서 그만두는지 안 보인다. `account_create_start` → `..._submit` → `..._success`처럼 단계별 이벤트가 있어야 GA4 퍼널(탐색 보고서)로 이탈 지점을 볼 수 있다.
- 실제 작업량의 대부분이 여기(추적할 기능 3~5개를 고르고 이벤트 목록에 합의하는 것)에 있다.

## GA4 기본 설정 중 반드시 바꿔야 하는 것
- **데이터 보관 기간**: 기본 2개월. 퍼널 탐색은 이 기간을 넘는 과거 데이터를 못 보므로 14개월로 늘려야 한다.
- **Google Signals**: 사용자 수가 적으면(직원 수 규모) 임계값 처리로 데이터가 자꾸 가려진다. 꺼 두는 게 낫다.
- 개발자/테스트 트래픽은 내부 트래픽 필터로 제외한다.

## 한계로 남는 것
- 사용자 수가 수십 명 수준이면 수치가 소수 인원의 습관에 크게 흔들린다 — "개선 우선순위의 근거"가 아니라 "참고 지표" 정도로 기대치를 관리해야 한다.
- 광고 차단기(uBlock 등)가 `gtag.js`를 막으므로, 실제 사용량보다 낮게 집계된다.
- 직원의 화면 사용 행태를 수집하는 것이라 회사 차원의 고지·동의가 필요한지는 별도로 확인이 필요하다(법적 판단 아님).
