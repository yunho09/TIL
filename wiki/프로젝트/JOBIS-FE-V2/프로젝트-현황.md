# JOBIS-FE-V2 프로젝트 현황

취업 지원 플랫폼 JOBIS의 프론트엔드 모노레포(`apps/student`, `apps/admin`, `apps/company` + `packages/api`, `packages/design-system`, `packages/sentry`). 화면 퍼블리싱은 항상 `@jobis/design-system` 컴포넌트를 가져다 쓰는 게 원칙이고, 커밋 메시지 형식·스코프를 git 훅이 강제한다.

## 퍼블리싱 컨벤션

- **페이지 구조** — `apps/<app>/src/pages/<page-name>/`에 `page.tsx`, `index.ts`, (데이터 필요 시) `loader.ts`. 이후 해당 앱의 `router.tsx`에 라우트 등록.
- **컴포넌트** — 새로 만들지 않고 `@jobis/design-system`에서 가져다 쓴다. 디자인과 안 맞는 부분이 있어도 기존 컴포넌트를 우선 사용하고, 정말 없는 경우에만 사용자 허락을 받은 뒤 **optional prop 추가**(기존 사용처에 영향 없게) 방식으로 확장한다. 정말 재사용 가능한 새 UI 패턴(예: 페이지 로컬 인라인 버튼을 여러 화면에서 반복해서 만들게 되는 경우)이면 컴포넌트 자체를 승격하는 것도 옵션 — `FileDownload`의 대칭으로 `FileUpload`(텍스트 좌·아이콘 우·전체폭 버튼) compound 컴포넌트를 이렇게 추가한 사례 있음(타입·스토리·테스트 세트 포함, `compound/index.ts`에서 export).
- **스타일 규칙** — 색상 하드코딩 금지, `const { currentTheme: theme } = useTheme()` → `theme.color.grayScale[90]` 형태로만 사용. 레이아웃 수치(`$maxWidth`, `$gap` 등)는 상수로 빼지 않고 JSX에 인라인으로 쓰는 게 이 레포 컨벤션 — 상수화는 `RECRUITMENT_STATUSES`류의 **옵션 데이터 배열**에만 쓴다.
- **로더 패턴** — id 파라미터 검증 → 잘못되면 목록 페이지로 redirect → 관련 데이터 `prefetch`. 로딩 중엔 `Skeleton` 컴포넌트.
- 관련: [[CSS-Container-shrink-to-fit]] (`main` 레이아웃 때문에 `Container $maxWidth`가 폭을 못 잡는 문제), [[S3-Presigned-URL-업로드]] (파일 첨부 업로드 구현 시), [[Figma-Dev-Mode-MCP]] (디자인 스펙 확인 시)

## 커밋 컨벤션 (`scripts/shared.ts`)

- 형식: `<이모지> (스코프) :: <설명>` (설명 30자 이내, 한 줄만 — `commit-msg` 훅이 메시지 **전체**를 정규식(멀티라인 미지원 플래그)으로 검사해서 여러 줄 트레일러(`Co-Authored-By:` 등)를 못 붙인다).
- 스코프는 스테이징된 파일 경로로 `detectScopesFromFiles`가 자동 판정:

  | 코드 | 의미 | 경로 |
  |---|---|---|
  | `AD` | Admin | `apps/admin/` |
  | `CO` | Company | `apps/company/` |
  | `ST` | Student | `apps/student/` |
  | `AP` | API | `packages/api/` |
  | `DS` | Design System | `packages/design-system/` |
  | `SY` | Sentry | `packages/sentry/` |
  | `RT` | Root | 위 어디에도 안 걸리는 나머지(예: 루트 `.gitignore`) |

- **커밋 하나에 스코프가 2개 이상 섞이면 `detectScopesFromFiles`가 에러를 낸다** — 여러 영역을 동시에 고쳤으면 스코프별로 커밋을 쪼개야 함.
- `pre-commit` 훅이 `yarn lint`(eslint, `--cache`)와 `yarn type-check:all`을 돌린다. `--cache` 때문에 로컬에 캐시가 남아있으면 이미 깨진 파일이 재검사 없이 통과할 수 있어, 다른 사람 환경에서만 실패하는 lint 에러가 생길 수 있다(예: 파일 끝 개행 누락이 `develop`에 이미 병합돼 있었던 사례).
- **작업 관리 기본값: 이슈 1개 = 브랜치 1개 = PR 1개.** 여러 화면을 한 번에 맡길 때도(예: "9개 화면씩 담당자 나눠서") 명시적으로 "이슈/브랜치/PR 각각 쪼개라"는 지시가 없으면 담당자·화면이 여러 개라도 하나로 묶는 게 이 프로젝트의 기본 기대치다(2026-09-07, 9이슈/8PR로 쪼갰다가 "이슈 하나로 브랜치 하나로 pr도 하나로 해"라는 정정을 받고 전부 통합·재정리한 사례 있음).

## 알려진 인프라 이슈

- **staging 도메인 DNS 오지정** (2026-09-06 기준) — `stag.jobis-dsm.kr`의 TLS 인증서 CN이 `ap-south-1.prod.p1.s1.systbl-mock.s3tables.aws.dev`로, JOBIS와 무관한 AWS S3 Tables mock 엔드포인트를 가리키고 있었다. 인증서 도메인 불일치로 브라우저가 연결을 차단(`ERR_CERT_COMMON_NAME_INVALID`)하고, 루트로 들어가면 `<UnknownOperationException/>`을 반환하며 모든 API 경로가 404. DNS(A/CNAME) 레코드 확인 필요 — 이게 안 풀리면 실서버 기준 검증 자체가 불가능하다.
- **`packages/design-system`의 vitest 테스트는 로컬에서 못 돌린다** — 브라우저 러너를 쓰는데 Playwright chromium(`ms-playwright/chromium_headless_shell-*`)이 설치돼 있지 않다. 이 레포에 새로 생긴 문제가 아니라 기존 환경 결함(변경 전 stash 상태에서도 재현됨)이라, DS 컴포넌트를 추가·수정한 PR은 로컬 검증 없이 "CI에서 확인 필요"로 명시하고 올리는 게 맞다.

## 알려진 공용 코드 결함 (`packages/api`)

- **`usePresignLogoFile`** — raw `axios`를 써서 `Authorization` 헤더가 안 붙는다(presign 명세상 인증 필수라 401 가능성). `new Promise(resolve => ...)`로 감싸놓고 **reject를 안 해서** S3 PUT 실패 시 영원히 pending 상태로 멈춘다. `data.urls[0]`만 처리해서 다중 파일 업로드도 안 된다.
- **`create-hook.ts`의 더블 슬래시 — 수정 완료 (2026-09-07, 커밋 `c6cc426`).** `createIdMutationHook`이 `path: "/"`일 때 `` `${domain}${path}/${id}` `` 조합으로 `/notices//1`처럼 슬래시가 겹치던 문제를, `path === "/" ? "" : path`로 비워서 고쳤다. 훅 하나만 고치면 이 패턴을 쓰는 `useUpdateNotice`·`useDeleteNotice`·`useUpdateCompany`·`useDeleteReview` 전부에 자동 반영된다(`createQueryHook`의 `resolvePath`는 애초에 같은 방식으로 처리하고 있었음). 백엔드 확인 결과 `//`로도 지금까지는 정상 동작하고 있었다고 함. **단, 아래 "상충하는 정보" 참고 — 이 전역 수정이 모든 브랜치에 들어가 있다고 가정하지 말 것.**
- **`useCreateApplication`에 캐시 무효화 누락 — 수정 완료 (2026-09-09, 커밋 `32658a5`).** 같은 파일의 `useDeleteApplication`은 성공 시 `applicationsKeys.studentApplications()`를 invalidate하는데, `createIdMutationHook` 제네릭으로 만든 `useCreateApplication`엔 그게 빠져 있어서 지원해도 마이페이지 지원 목록이 갱신되지 않았다. `useDeleteApplication`과 같은 형태로 다시 작성해 고쳤다. **`createIdMutationHook`으로 새 mutation 훅을 만들 때는 같은 도메인의 다른 훅(특히 delete류)에 캐시 무효화가 있는지부터 대조할 것** — 제네릭 팩토리가 자동으로 챙겨주지 않는다.
- **401/403 이중 의미 문제** — 공용 인터셉터(`instance.ts`)가 모든 401/403을 "토큰 만료"로 간주해 재발급을 시도하고, 실패하면 `main.tsx`의 `onTokenExpired`가 `/login`으로 강제 이동시킨다. 그런데 학생 지원 API처럼 401이 "권한 없음"(예: 3학년이 아님)을 의미하는 엔드포인트도 있어서, 정상 로그인한 사용자가 특정 액션을 시도했을 뿐인데 안내 없이 로그아웃당하는 문제가 생긴다. 근본 해결은 응답 body의 에러 코드로 "토큰 문제"와 "권한 문제"를 구분해야 하며, 여러 앱에 영향이 가는 변경이라 신중히 접근해야 한다. (2026-09-09 기준 여전히 미해결 — 학생 지원 페이지의 401/403 문구는 이 인터셉터 때문에 실행되지 않는 죽은 코드로 남아있음)
- `instance.ts`는 HTTP 에러를 **status code 숫자로 throw**한다. 400/401/403/404/409별로 각각 다른 안내 문구(토스트 등)를 붙이고 싶으면 `catch`에서 숫자로 분기하면 된다 — 학생 지원 페이지에서 이 방식으로 4xx별 토스트를 구현·검증함.

## 설계상 한계 — 첨부파일 종류를 서버가 구분 못 함

지원 API의 `attachments`는 `{ url, type }`(`type: "FILE" | "URL"`)만 받는다. 학생 지원 화면은 포트폴리오/자소서/첨부파일처럼 항목이 나뉘어 있어도, 제출 시엔 전부 `type: "FILE"`로 뭉개져서 **서버가 어떤 파일이 포트폴리오였는지 구분할 방법이 없다.** `RecruitmentDetailResponse.submit_document`도 자유 텍스트 하나뿐이라 "이 모집의뢰서가 어떤 서류를 요구하는가"를 구조화해서 받아올 수도 없다 — 그래서 화면의 3개 필드명(포트폴리오/자소서/첨부파일)은 프론트 하드코딩 상태다. `attachments[]`에 `name`/`document_type` 같은 구분 필드가 추가되고, 모집의뢰서 쪽에도 요구 서류 목록이 구조화돼야 근본 해결된다(2026-09-09 백엔드에 전달, 미해결).

## 파일 업로드 API 스펙 두 벌 (미해결)

같은 파일 업로드 기능에 대해 서로 다른 두 스펙이 순차로 전달된 적이 있다:
1. 경로 미기재 `multipart/form-data` + 쿼리스트링 `type`, 응답 `urls: string[]`
2. `/files/pre-signed`(기존 코드에 남아있어 경로가 확인됨) + presigned URL 2단계 흐름, 응답 `urls: [{file_path, pre_signed_url}]`

①을 먼저 구현했다가, 나중에 도착한 공식 Notion 스펙 문서가 ②였음이 확인돼 [[S3-Presigned-URL-업로드]] 방식으로 전면 재작성했다. ①이 폐기된 API인지 별도로 살아있는 API인지는 2026-09-09 기준 미확인. **같은 기능의 스펙을 여러 출처(과거 대화, Notion 링크 등)에서 받으면, 구현 전에 어느 쪽이 최신/공식 버전인지부터 확인할 것** — 업로드 방식(multipart vs presign)처럼 근본적으로 다른 구현이면 재작업 비용이 크다.

## 알려진 공용 코드 결함 (`apps/*` 공통 패턴)

- **`updateParams`/`getParam` 키 표기 불일치로 필터가 조용히 죽는 버그 클래스** — `apps/student/src/utils/hooks.ts`의 `updateParams`는 카멜케이스 키를 케밥케이스로 자동 변환(`key.replace(/([a-z0-9])([A-Z])/g,"$1-$2").toLowerCase()`)해서 querystring에 쓰는데, `getParam`과 각 페이지의 `loader.ts`는 원래 키(카멜케이스)로 그대로 읽는다. 그 결과 `updateParams({ state })`로 썼는데 `getParam("status")`로 읽거나(모집의뢰서 상태 필터), `techStack`으로 썼는데 `tech-stack`으로 읽어야 하는(기술스택 필터) 식으로 **한 querystring hook 안에서 두 번 같은 원인으로 필터가 무효화된 사례**가 있었다. 이런 훅을 쓰는 다른 목록 페이지를 만들 때도 write 쪽 키와 read 쪽 키의 표기(camelCase vs kebab-case)를 반드시 맞춰서 대조해야 한다.

## API 명세 작성 시 흔한 함정 (이 레포 경험 기준)

- 필드 설명 목록과 실제 예시(body example)가 다를 수 있다 — 예: 필드 설명엔 `url`/`type`만 나열됐는데 예시는 `{ "attachments": [...] }`로 한 단계 감싸져 있었음. **필드 설명만 보고 구현하면 실제 요청 형태를 놓친다**, 예시 JSON을 반드시 대조할 것.
- presign류 업로드 API처럼 **엔드포인트 경로가 명세에서 아예 누락**되는 경우가 있다. 이때는 같은 도메인의 기존 코드(레거시 훅 등)에 남아있는 실제 호출 경로를 근거로 삼는 게 그나마 신뢰도 높은 추정이다.
- Notion 명세가 옛날 버전으로 방치돼 실제 응답과 어긋나는 경우가 있다 — 예: 배너 명세는 `banner_url` 기준으로 남아있지만 실제로는 텍스트 기반 배너로 바뀌어 필드 자체가 사라졌고, 공지 상세 명세엔 디자인에 있는 조회수 필드가 아예 없다. **명세만 믿지 말고 막히면 바로 백엔드에 최신 응답 예시를 요청**하는 게 빠르다.
- 명세 문서 자체에 오타·배치 오류가 섞여 있을 수 있다 — 예: `POST /acceptances/employment`의 Body Example에 `applicatoin_ids`(실제 프론트 필드명은 `application_ids`), `DELETE /acceptances`의 `application_ids`가 Body가 아니라 Header 섹션 아래 잘못 배치. 프론트 기존 요청 타입과 다르면 오타를 의심하고 백엔드에 필드명 확인부터 요청할 것.

## 백엔드 확인 완료 사항 (2026-09-07, PR #147 관련 문답)

- **모집의뢰서 `status` enum** — `READY`는 실제로 안 쓰는 값. "모집전" 상태는 `REQUESTED`를 써야 한다.
- **`acceptances` 삭제 API는 실제로는 취소** — `DELETE /acceptances`는 레코드를 지우는 게 아니라 "현장실습→취업 취소" 의미다. 훅 이름도 `useDeleteAcceptance` → `useCancelAcceptance`로 정정(커밋 `233d567`). 이름만 보고 destructive 동작을 가정하지 말 것.
- **상태변경 메뉴의 "근로계약 변경"** — `POST /acceptances/employment`(현장실습→근로계약 전환)가 맞다. `code_keywords`를 받는 시그니처가 의미상 안 맞아 보였지만 그대로 쓰면 된다고 확인됨.
- **공지 조회수** — 기능 자체는 이미 구현돼 있고, 프론트가 별도로 `POST /views`를 호출해야 반영된다(정확한 경로·request/response 스펙, 응답에서 조회수를 읽는 필드명은 세션 종료 시점까지 미확정 — 추가 확인 필요).
- **공지 수정 API의 첨부파일 미지원**은 의도한 게 아니며, 필요하면 열어주겠다고 확인됨(`PATCH /notices/{id}`에 `attachments` 추가 요청은 아직 대기 중).
- **취업관리(acceptances) 전체 학생 조회 API는 아직 없음** — 새로 추가해야 한다고 확인됨. 그전까지는 "기업 선택 → 해당 기업 학생 조회" 흐름으로 우회. **2026-09-09 Notion 명세서(`JOBIS API (1)`)로 재확인**: `/acceptances` 도메인 5개 엔드포인트 중 조회는 `GET /acceptances/{company-id}` 하나뿐이고 `company-id`가 Path Variable(필수)로 박혀 있어 Query Parameter 자체가 없다 — 프론트 미연동이 아니라 서버에 애초에 없는 게 확정. `GET /acceptances/field-train`, `GET /acceptances/contract`(각각 `page`/`student_name`/`company_name`/`year` 쿼리 + `/count`, 응답에 `application_id`/`acceptance_id` 포함) 스펙으로 백엔드에 추가 요청 전달함(응답 대기).
- **배너 `banner_url`는 폐기, 텍스트 기반 배너로 전환됨.** 다만 이 프로젝트에서 스튜던트 홈 배너는 애초에 "회색 배너 하드코딩, 내용은 나중에(디자인 협의 필요)"로 합의돼 있었어서, `useBannerList` API 연동을 한 번 붙였다가 사용자 정정으로 되돌렸다(커밋 `6124ee8`). 배너 API 연동은 디자인·백엔드 협의가 끝나기 전까지 다시 손대지 말 것.
- **`banner_type`별 `detail_id`** — 모집의뢰서 id로 보는 게 맞다고 확인됐지만, 백엔드 연결이 아직 제대로 안 돼 있어 프론트에서 임의로 규약(어떤 타입이든 `detail_id`를 모집의뢰서 id로 취급)을 맞춰줘야 하는 상태.
- **학생 검색 응답의 학년반번호 필드**는 `school_number`도 `school_gcn`도 아니고 `student_gcn`이 맞다(프론트는 이미 이걸 쓰고 있어서 변경 불필요였음).

## 어드민 취업관리(`/student`) 화면 구조

어드민 헤더의 "학생" 메뉴(`packages/design-system/.../Header.tsx:58`), 라우트 `/student`(`apps/admin/src/router.tsx:69`), 파일 `apps/admin/src/pages/student/page.tsx`. 실제 화면명은 커밋 로그(`✨ (AD) :: 학생 취업관리 페이지 퍼블리싱`) 기준 **"취업관리"가 맞다.**

탭 3개, 기본 탭은 `company`(`loader.ts:31`):

| 탭 | `?tab=` | 쓰는 API | 내용 |
|---|---|---|---|
| 기업 | `company` | `GET /companies/employment`(+`/count`) | 전 기업 + `field_trainee_count`/`contract_count` |
| 현장실습 | `field-train` | `GET /acceptances/{companyId}` → `field_trainees_response` | **그 기업 소속** 현장실습생만 |
| 근로계약 | `contract` | `GET /acceptances/{companyId}` → `acceptances_response` | **그 기업 소속** 근로계약생만 |

현장실습/근로계약 탭은 기업 탭에서 기업을 클릭해 `company-id` 쿼리파라미터가 붙어야 조회가 나간다(`enabled: hasSelectedCompany`). Figma 시안(`JOBIS-Web` 파일, `5139:9313`/`5139:8869`/`1419:1933`)은 목업이 전부 "코드잇" 한 기업이라 "기업별 조회"와 "전 기업 통합 목록" 어느 쪽으로도 읽혀서 판단 근거가 못 됐고, 최종적으로는 사용자가 백엔드에 명세 확인 요청을 보내 위의 "전체 조회 API 없음"으로 결론남.

**PR #147 최종 상태 — API 연동 전부 제외, 순수 퍼블리싱만 유지 (2026-09-09).** 이 화면(라우트·탭·필터·검색·페이지네이션·테이블 골격)은 이번 브랜치의 다른 작업(버그 제보, 홈 배너)과 무관한 별도 화면이라, 사용자가 "학생 관련 페이지는 이번 브랜치에서 제외하자"고 결정해 아래를 전부 되돌렸다:
- **기본 기업 자동 선택** (탭 직접 클릭 시 `company-id` 없어 빈 화면이던 것을 첫 기업으로 자동 채우던 기능, 커밋 `125785c`) — `git revert`(`5ccacef`)로 되돌림.
- **행 체크박스 + 삭제 연동** (`useCancelAcceptance` 실제 동작, 커밋 `79fb966`) — 아직 푸시 전이라 그냥 제거하고, 잃어버리지 않게 로컬 브랜치 `backup/admin-student-checkbox`에 보관(`git cherry-pick 79fb966`로 복구 가능).
- **API 연동 전체**(`useEmploymentCompanyList`/`useAcceptanceDetail` 등, `loader.ts` 프리페치 포함) — 별도 커밋(`1175e07`)으로 제거, 데이터는 빈 배열. `git diff <퍼블리싱 커밋> HEAD -- apps/admin/src/pages/student/`가 비어 있어 최초 퍼블리싱 상태와 바이트 단위로 동일함을 확인.

그런데 사용자가 곧바로 "체크박스는 그대로 놔 figma 그대로"라고 정정 — **체크박스 UI 껍데기만 시안 그대로 다시 붙였다**(커밋 `2f0d03e`). 세 탭 전부 행 체크박스(전체선택 헤더 포함) + 우측 `상태변경 ▾` 드롭다운을 렌더하지만, **API 호출은 하나도 없다** — 선택해도 아무 요청이 안 나간다. 드롭다운 옵션은 시안에 옵션이 그려진 현장실습 탭만 `삭제 / 근로계약 변경`을 채웠고, 기업·근로계약 탭은 시안에 옵션이 안 그려져 있어 빈 채로 둠. 실제 삭제 동작(`useCancelAcceptance` 연결)은 위 `backup/admin-student-checkbox` 브랜치에만 살아있다.

**다음 브랜치에서 복구할 작업 3가지**: API 연동(`git revert 1175e07`), 기본 기업 자동 선택(`git revert 5ccacef`), 체크박스 삭제 동작(`git cherry-pick 79fb966`).

## 로컬 dev 환경 — 학생 앱 크래시 2건

`apps/student`를 로그인 없이 로컬 dev로 열면 화면이 아예 안 뜬다.

1. **홈이 흰 화면 (미해결)** — `homeLoader`가 prefetch 4개를 `await`하는데, 비로그인 상태라 API가 403을 던져도 catch가 없어 그대로 매달린다. 에러 화면도, 로그인 리다이렉트도 안 뜬다.
2. **`Footer.tsx:27` 크래시(`theme.color`가 `undefined`) — 프로젝트 버그 아님, 정정됨(2026-09-09).** 처음엔 dev 모드에서 `tsconfig.app.json`의 paths alias가 `packages/design-system`을 소스로(`@fs/.../design-system/src/...`) 직접 불러오면서 emotion 인스턴스가 두 개가 되는 구조적 문제로 보고, `vite.config.common.ts`에 emotion `dedupe`+`optimizeDeps.include`를 임시로 넣어 재현·완화까지 확인했었다. **그런데 같은 세션 안에서 이미 5173 포트에 떠 있던 정상 dev 서버(다른 방식으로 기동된 것)로 다시 테스트하니 이 크래시가 재현되지 않았다** — 원인은 프로젝트 코드가 아니라, 크래시를 처음 겪을 때 `yarn workspace @jobis/student dev`를 `--force`로 캐시를 지우고 새로 띄운 **그 실행 방식 자체**였던 것으로 결론남. 평소처럼 띄운 dev 서버(5173)와 프로덕션 빌드 둘 다 테마가 정상 적용된다. **팀 공유 대상에서 제외** — dedupe 설정도 넣지 않았다(넣어봤다가 되돌림, 워킹 트리에 남은 변경 없음). 이후 dev에서 같은 증상을 다시 보면 먼저 `--force` 없이 재시작해서 재현되는지부터 확인할 것.

## 버그 제보 페이지 — Figma 정합화로 디자인시스템 확장 (2026-09-09)

`apps/student/src/pages/mypage/bug-report`를 시안과 픽셀 대조해 4가지 차이를 고쳤다. 그중 2개는 **공용 `@jobis/design-system` 컴포넌트를 확장**하는 방식으로 처리해서 다른 화면에도 영향이 간다:

- **`Input`/`TextArea`에 `$variant="underline"` 추가** — 기존엔 `grayScale[20]` 채움 박스(`filled`) 고정이었는데, 시안이 밑줄 입력이라 새 variant를 추가했다. **기본값은 그대로 `filled`라 기존 화면은 영향 없음.**
- **`FileUpload` 스펙 변경(패딩 9/23, 텍스트 body3, 아이콘 16, 기본 아이콘 `Plus`→시안엔 `Upload`)** — 이 컴포넌트는 **어드민 공지 등록 화면에서도 재사용 중**이라, 버그 제보 페이지 시안에 맞춰 크기를 줄이면 공지 등록 쪽 버튼도 같이 작아진다. "같은 컴포넌트니 시안이 하나일 것"이라는 가정으로 그대로 반영했는데, **공지 등록 시안이 다르면 별도 확인 필요** — 미확인 상태로 남음.

공용 디자인시스템 컴포넌트를 프로젝트 컨벤션대로(신규 컴포넌트 대신 optional prop 확장) 고칠 때는, 그 컴포넌트를 쓰는 다른 화면이 있는지부터 확인하고 영향 범위를 사용자에게 알려야 한다는 사례.

**학생 앱 레이아웃 버그도 같이 발견해 고침** — `apps/student/src/router.tsx:36`의 `<main style={{flex:1}}>`이 세로 flex 컨테이너 안에서 `width` 없이 내용물 너비로 줄어들고 있었다(헤더·푸터는 1295px인데 main만 780px). 페이지 배경을 깔아도 카드 폭만큼만 칠해지는 원인이 이것이었다. `width: "100%"` 한 줄 추가로 **학생 앱 전체**에 적용되는 라우터 레벨 수정. [[CSS-Container-shrink-to-fit]]에서 다루는 것과 같은 shrink-to-fit 패턴의 재발 사례 — 이번엔 페이지별 우회가 아니라 공용 `router.tsx`에서 근본 수정함.

## 잡다한 팁

- **같은 파일을 `<input type="file">`로 연속 선택**하면 두 번째부터 `change` 이벤트가 안 터진다(브라우저가 값이 안 바뀌었다고 판단). 선택 처리 후 `event.target.value = ""`로 초기화해야 재선택이 인식된다.
- 화면 스펙을 픽셀 계측으로 역산할 때, **폰트 크기는 감으로 추정하지 말고** 후보 크기별로 실제 폰트를 캔버스에 렌더해서 잉크 바운딩박스 크기를 비교하면 정확히 맞출 수 있다.
- **백엔드(staging)가 죽어 있어도 화면을 임시로 확인**하고 싶으면, 목 API 서버를 로컬에 띄우고 레포 루트에 `.env.development.local`을 만들어 `BASE_URL`/`FILE_URL`만 덮어쓰면 된다. Vite는 `.env`보다 `.env.development.local`을 우선 적용하고, `.gitignore`의 `.env.*` 규칙에 걸려 **커밋에 안 잡힌다**. 확인이 끝나면 그 파일만 지우면 원상복구(원래 `.env`의 staging 주소로 자동 복귀). 기존 dev 서버(포트 고정)를 건드리지 않으려면 별도 포트로 새 dev 서버를 하나 더 띄우면 된다.
