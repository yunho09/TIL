# 냉장고 공유 API 설계와 리뷰 반영 (bium-be #24·#25)

Sprint 2에서 FE가 공유 화면을 목데이터로 퍼블리싱하는 동안, BE는 **요청·응답 명세를 먼저 확정해 FE에 넘기고** 초대·참여·멤버 API(#24, PR #26 병합)와 활동 기록(#25, PR #30 리뷰 대기)을 만들었다. 결정 사항과 리뷰에서 나온 정책 문제를 남긴다. 락 관련 기술 내용은 [[MySQL-잠금-읽기와-H2-테스트-사각지대]].

## 확정한 결정
- **권한**: 초대 코드 만들기·조회·멤버 내보내기는 OWNER만, 재료 수정·삭제는 멤버 모두. 멤버가 아니면 `FRIDGE_NOT_FOUND`(404, 남의 냉장고 존재를 숨김), OWNER 전용을 MEMBER가 하면 `FRIDGE_OWNER_ONLY`(403).
- **초대 코드**: 8자 영문 대문자+숫자(헷갈리는 0·O·1·I 제외 → 32종), `SecureRandom`, 24시간 유효, 새로 만들면 기존 코드 즉시 무효. 입력은 공백 제거·대문자화 후 조회, 충돌 시 재시도.
- **API 6개(+활동 기록 1개)**: `POST /api/fridges/{id}/invites`, `GET .../invites/active`, `POST /api/fridges/join {code}`, `GET .../members`, `DELETE .../members/{userId}`(204), `DELETE .../members/me`(204), `GET .../activities`(최근 50개). `/members/me`는 리터럴 경로가 `{userId}`보다 우선해 타입 불일치 400이 나지 않음을 테스트로 확인.
- **오류 코드**: `INVITE_NOT_FOUND`(404), `INVITE_EXPIRED`(410), `ALREADY_FRIDGE_MEMBER`(409), 명세에 없다가 추가된 `OWNER_CANNOT_LEAVE`(409)·`FRIDGE_MEMBER_NOT_FOUND`(404). FE가 `error.message`를 그대로 화면에 보여 주므로 메시지는 사용자용 문장으로 작성.
- **FE 요청 반영**: 멤버 응답에 `isMe: boolean` 추가 — FE는 로그인 응답으로 토큰만 받아 자기 userId를 모르기 때문. 내 역할은 `GET /api/fridges`의 role로 판단하고 MEMBER는 `invites/active`를 호출하지 않음. (Jackson이 `isMe`를 `"isMe"` 이름 그대로 내는지 테스트로 확인 — boolean `is` 접두어 이름 변환 함정)
- **정책 구멍 (리뷰 발견)**: 내보낸 멤버가 아직 유효한 같은 코드로 바로 재참여 가능 → 내보낼 때 그 냉장고의 활성 코드도 함께 무효화. 스펙에 없던 제품 결정이라 PR에서 팀에 공유.
- **활동 기록 범위**: 재료 추가·수정·삭제와 참여·나가기(내보내기는 "내보내진 사람의 LEAVE")만 기록. 기록은 동작과 같은 트랜잭션이라 실패하면 같이 롤백. 이동·차감·되돌리기(MOVE·DEDUCT·RESTORE)는 최선재 담당(#27)이라 제외 — 차감을 재료마다 기록할지 요리 한 번에 하나로 기록할지는 그와 합의 필요. 이슈 #25에 없던 재료 추가(`create`)의 ADD 기록은 이강희 코드를 한 줄 고친 것이라 PR에서 확인 요청.
- 미해결/보류: 참여 API 호출 제한, 활동 기록 `createdAt`이 서버 시간대(`@CreationTimestamp`)라 UTC 서버면 9시간 차이(기존 코드 전반의 관례), 응답에 `userId` 없음(같은 닉네임 구분·"나" 표시 불가, FE가 아직 안 씀), 내보낸 주체를 `detail` JSON에 남기기.

## 작업 방식에서 얻은 것
- FE 세션과 명세를 먼저 맞춘 뒤 목데이터 타입을 그 모양으로 만들게 하면 연동 때 안 꼬인다 — 앞서 FE가 배열로 가정한 재료 목록과 BE의 구역별 객체가 어긋나 레시피 화면이 깨졌던 일([[Bium/프로젝트-현황]]의 협업 교훈)의 재발 방지.
- 커밋 직전에 별도 에이전트에게 리뷰를 맡기고, 리뷰어가 **실제 트랜잭션 테스트를 따로 돌려** 걱정 항목(권한, 지연 로딩, 참여 더블클릭)을 확인하게 했다. 그래도 MySQL 전용 문제는 CodeRabbit이 PR 단계에서 추가로 잡았다.
- PR 설명을 통째로 갱신하면 하단의 CodeRabbit 자동 요약이 지워질 수 있어 본문을 먼저 확인하고 고친다. 이슈는 삭제하지 않고 완료로 닫고(`Related to #N`이면 병합해도 자동으로 안 닫힘), 병합 뒤 develop 전체 테스트(108→115개)를 다시 돌려 다른 팀원 PR과의 합침을 확인.
