# Bium(비움) 2학기 백엔드 확장 — 제안서 결정 사항

1학기에 혼자 만든 프론트엔드 단독 냉장고 관리 웹 **Bium**(React·Vite·Zustand·dnd-kit·Emotion, localStorage 저장, Gemini 레시피)에 백엔드를 붙여 3인 팀 프로젝트로 확장하는 2학기 "백엔드 연동 제안서"의 확정 내용과 근거. 제출은 완료됐고, 이 페이지는 이후 개발·발표에서 다시 참조할 결정 목록이다.

## 확정된 결정
- **팀**: 장윤호(프론트엔드 전체 + API 연동 + 이미지 업로드), 이강희(백엔드: 서버·로그인 JWT·냉장고/식재료 CRUD API·영수증 등록·공유·이메일 알림), 최선재(백엔드: 자동 차감·부족 재료 추천·장보는 날·영양 정보·피드). 팀장 표기는 쓰지 않기로 함. 역할 분담은 초안을 사용자가 "괜찮은 듯"으로 승인.
- **스택**: Java + Spring Boot(Spring Security+JWT, JPA, `@Scheduled`), MySQL, Gemini 무료 API, 식약처 식품영양성분 DB API, 이메일(JavaMailSender), 배포는 **ngrok** — 상세는 [[Bium-백엔드-연동-기술-메모]].
- **알림은 카카오톡 대신 이메일**: 카카오 "나에게 보내기"는 카카오 로그인 연동이 필요해 범위가 커짐. 이메일은 유통기한 D-3·D-Day만 보내고, 장보는 날은 앱 달력에만 표시(두 범위를 섞어 쓰면 문서 안 모순이 됨 — 검토에서 실제로 지적됨).
- **피버타임**: 재료별 **구매 주기**(예: 우유 7일, 계란 14일)로 다시 살 날을 달력에 추천하고, 같은 날 산 재료들의 주기가 다시 겹치는 날(최소공배수, 7일·14일이면 14일째)을 "피버타임"으로 표시. 기준일이 없으면 뜻이 모호해져 "같은 날 산 재료들" 조건을 명시. 달력이 월 단위라 한 달 밖(70일 등)의 겹침은 표시되지 않음.
- **보관 구역은 냉장실·냉동실·실온 3구역**: 문칸·중앙 칸은 각 구역 **안의 위치**이지 별도 구역이 아님(1학기 보고서 구조). "신선실"은 포스트잇 원안에 있던 표현이었으나 "실온"으로 정정.
- **이미지(식재료 아이콘)**: 사진 업로드만, 저장은 브라우저 로컬. 그리기 기능은 뺌. 한계: 공유 냉장고의 다른 멤버·다른 기기에선 기본 아이콘이 보임(발표 질문 대비 포인트).
- **1학기 localStorage 데이터 이전은 하지 않기로** 함(일부 문장만 지우면 2-다·3-나에 남아 모순 → 세 곳을 함께 지워야 했음).
- **장보기 목록**(앞으로 살 재료)과 1학기의 **장본 음식 목록**(이미 산 재료)은 별개로 정의. 부족 재료 추천이 담기는 쪽은 장보기 목록.
- **방법론**: 1주 스프린트 스크럼, 노션 "기능 후보 목록"을 백로그로 사용, API 명세 먼저 → FE·BE 동시 개발, PR 리뷰 후 main 병합, 주간 리뷰·회고.
- **기존 학교 프로젝트 비교(2-나)**: PiCK(백엔드 1명이 전부 맡음·교내 학생 전용 → 이번엔 FE1·BE2 협업, 대상은 "냉장고 관리가 필요한 사람"), 파블로(애자일 없이 진행해 일정이 계속 밀림 → 1주 스프린트), 토이빌리지(요구사항을 주는 사람이 따로 있어 요구사항 문제 없었음 → 이번엔 팀이 직접 정의).

## 노션 기능 후보 목록
- 포스트잇 회의로 17개 후보 → 구현 예정 11개(제안서 기능 ①~⑩, 일러스트/애니메이션 개선이 ⑩ 하나로 묶임) / 제외 6개(사유 칸은 사용자가 직접 기입). 우선순위 숫자가 클수록 중요(보드의 중요도 화살표 방향 기준).
- 노션은 제안서의 최신 결정(이메일·실온·피버타임)으로 맞춰 수정함. 제안서와 노션이 갈라지기 쉬우니 결정이 바뀌면 둘을 같이 고친다.

## 채점 기준과 제안서 설계에서 얻은 교훈
- 채점 문구: 제안서(5점) = 주제 적합 / "객체 지향을 활용해 백엔드 연동 후 구현할 기능" 2쪽 이상 / "기존 프로젝트와의 차별점" 2쪽 이상, 발표(5점) = 자료 제출 / 질문에 정확히 2회 이상 답변 / 시간 엄수.
- 양식(HWP)의 쪽수 기준은 섹션별(1-가~다 1쪽 초과, 1-라 2쪽 초과, 2장 2쪽 초과, 3장 1쪽 이상)이라 **분량은 섹션 단위로 재야** 한다. 2장 전체는 3.9쪽이지만 2-나(학교 프로젝트 비교)만 보면 약 1.35쪽 — 채점 문구를 엄격히 읽으면 부족할 수 있어 발표에서 말로 보완하는 쪽으로 정리.
- "객체 지향" 설명이 Java·Spring Boot라는 이름으로만 드러나 약했음. 보완 문구: Controller–Service–Repository 계층 분리, 회원·냉장고·식재료 엔티티 클래스, D-Day 계산을 식재료 클래스의 메서드로 두어 화면 색과 이메일 알림이 같은 규칙을 쓰게 함. 알림 발송 인터페이스(예: `NotificationSender`)로 나중에 채널을 늘릴 수 있다는 설명은 (Claude 보충, 팀 합의 전).
- 검토 에이전트가 반복해서 잡아낸 유형: 섹션 간 모순(역할·일정표·수행 방법의 담당자 불일치), 근거 없는 경쟁 서비스 단정("대부분의 앱은…", 실명 서비스에 대한 단정), 담당·일정 없는 기능 언급, 용어 혼용(Bar/막대, 장보기/장 보기). 제안서는 "많은", "~하지는 않는다" 정도로 한정해 쓰는 편이 안전.
- 발표 대비 질문 후보(제안서에 이유가 없어 팀이 답을 맞춰야 하는 것): 왜 카카오톡이 아니라 이메일인가, 왜 클라우드가 아니라 ngrok인가, JWT 만료 시간·저장 위치, 영수증 개인정보(이미지 서버 미저장 여부), 단위가 다른 재료의 자동 차감, 구매 주기를 누가 정하는가.

## 미확정
- 제출한 제안서에 남은 어색한 표현(1-나의 "기존 백엔드와 프런트엔드가 사용해 익숙한 기술스택", "다를 수 있다" 등)은 사용자가 고치지 않기로 하고 제출함. PPT 3장의 "냉장실·냉동실실온·문칸" 4구역 표기도 최종 제출 전 수정 여부 미확인.
- 식약처 API의 "계란/달걀" 같은 이름 매칭, Gemini 무료 한도 실측은 개발 단계에서 확인할 일.
