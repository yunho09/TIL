# 영양 정보 — 식약처 API 연동 설계와 실측 (3차 스프린트)

Bium 3차 스프린트에서 재료 영양 정보(탄단지)를 **식약처 식품영양성분DB API → DB 저장 → 화면 도넛 그래프**로 보여 준 설계와, 실제 키로 붙여 보고서야 드러난 문제(느린 응답·이름 불일치)의 기록이다. 가짜 서버로만 확인한 FE는 문제를 못 잡았다는 교훈이 핵심이다. 사전 조사는 [[Bium-백엔드-연동-기술-메모]]의 영양 정보 절 참고.

## 전체 흐름 (BE develop 기준)
- 재료 이름 → 검색어 만들기 → `food_nutrition`에 저장된 값이 있으면 **바로 응답**, 없을 때만 식약처 호출 → 맞는 식품 고르기 → 저장 → 응답.
- 식약처를 실제로 부르는 곳은 BE 한 군데(`FoodNutritionClient.searchByName`). 경로는 둘: 화면이 기다리는 **직접 조회**(재료 모달), 기다리지 않는 **백그라운드 미리 찾기**(`NutritionPrefetcher`, 스레드 2개).
- API: 공공데이터포털 "식품의약품안전처_식품영양성분DB정보"(`FoodNtrCpntDbInfo03/getFoodNtrCpntDbInq03`), 활용신청은 **자동 승인**(2년, 2026-11-11~2028-11-11). 키는 서버 환경변수 `NUTRITION_API_KEY`(**일반 인증키 Decoding 값**, Encoding 아님)로만 받고 프론트엔 없다. 조건은 `FOOD_NM_KR`+`DB_CLASS_NM=품목대표`, 값은 응답 `AMT_NUM`에서 읽는다.
- 저장 규칙: 찾음/못 찾음(null)은 저장(못 찾음은 30일 뒤 재조회), **식약처 실패(시간 초과·한도)는 저장하지 않고 502** → 다음 요청 때 재시도. 30일 지난 못 찾음을 재조회하다 실패하면 502 대신 저장된 null.
- 냉장고 재료 자체(이름·아이콘·유통기한)는 도감/장본 음식/영수증 값 그대로고, 식약처에서 가져오는 건 **영양 정보뿐**이다.

## 가짜 서버가 못 잡은 문제 (실측)
- **느린 응답:** 식약처는 결과가 한 페이지를 못 채우면(결과 없음·적음·마지막 페이지) **4~6초**가 걸린다. 처음 BE는 3초만 기다려 키를 넣자 모든 재료가 502였다. FE 가짜 서버는 0.4~0.8초로 응답해 전혀 몰랐다.
  - 진단: 같은 키로 직접 호출하면 1.2초(결과 많음)였으나 BE 경유는 3초 초과 → 직접 시간 측정으로 "결과 없는 검색이 느림"을 특정. FE가 의심한 "한글 인코딩 차이"는 BE가 보내는 URL을 키만 가려 찍어 비교하니 **아니었음**.
  - 해결: 한 번에 500개씩(흔한 재료도 300개 미만이라 대부분 1회) 최대 2페이지, 대기 3초→10초(첫 페이지가 5초 넘으면 다음 페이지 생략, 단건 대기 최대 약 17초). 재료 모달은 처음 찾을 때 그만큼 로딩을 보여 줘야 한다.
- **이름 규칙이 예상과 다름:** 원재료는 `"양파, 생것"`, `"파, 대파, 생것"`처럼 쉼표로 이어 쓰고, 계란은 "달걀". "두부"로 찾으면 "두부조림"도 온다.
- **교훈:** 외부 API 기능은 가짜 서버로만 확인하지 말고 **처음부터 실제 키로 붙여** 응답 시간·데이터 모양을 확인한다.

## 이름 맞추기 3단계
1. **검색어 다듬기:** 띄어쓰기 제거("방울 토마토"→"방울토마토"), 별칭(`SEARCH_ALIASES`, "계란"→"달걀"). 도감 재료는 도감 이름, 아니면 재료 이름.
2. **결과 고르기(`FoodMatcher`):** 이름 동일 → 뒤에 세부 이름만 붙은 식품("양파, 생것", "두부_부침용") → 쉼표 뒤 세부 이름이 재료 이름인 식품(대파→"파, 대파, 생것"). 같은 순위면 네 값이 다 있는 것→원재료→"생것"→이름 짧은 것. 규칙에 안 맞으면 **엉뚱한 음식을 보여 주지 않으려고 null**.
3. **자주 쓰는 재료 76개는 직접 골라 미리 넣기(BE #54):** 규칙대로 하면 13개가 문제(새송이버섯 못 찾음→"큰느타리버섯(새송이버섯), 생것", 닭가슴살→"조미훈제"가 골라짐→"닭고기, 가슴, 생것", 삼겹살·깻잎·숙주·쌀 못 찾음 등). 값을 레포 `basic-foods.tsv`에 두고 **서버 시작 시 `food_nutrition`에 없는 것만 삽입**(식약처 미호출이라 키 없이도 동작, 실패해도 서버 기동, 테스트에선 `seed-basic-foods: false`). 저장된 값이 있으면 규칙을 거치지 않으므로 항상 직접 고른 식품이 나온다.
- 한계: 76개 밖 재료는 규칙에만 의존("냉동 만두"는 못 찾음, "김치"는 "김치, 갓김치"로 골라짐). 앞말 빼고 재검색은 안 하기로 결정.
- 캐시는 **DB마다 따로**라 팀원은 `.env`에 키가 없으면 76개 외 재료가 502. 키는 레포·노션에 올리지 않고 각자 신청(자동 승인)하거나 개인 전달.

## 미리 찾아 두기와 동시 조회
- 재료를 넣을 때(하나씩 추가·영수증 일괄·장본 음식 옮기기) **커밋된 뒤에만** 백그라운드로 영양 정보를 찾는다(응답은 안 기다림, 롤백되면 안 찾음).
- 처음엔 요약 한 번이 못 찾은 이름들을 작업 하나로 묶어 스레드 하나가 차례로 처리했고, 다음 요청은 "찾는 중" 이름을 걸러 두 번째 스레드는 놀았다 → **이름마다 작업 1개**로 바꿔 2개 동시, 대기·진행 중 이름은 재등록 안 함, 한 이름이 실패해도 나머지 계속(실패 이름은 다음 요약 때 재등록), 큐 200. 키가 없으면 서버 시작 때 ERROR 한 번만 남기고 요약의 백그라운드 조회는 넣지 않는다(로그 폭주 방지).

## FE 영양 UI 설계
- **레시피 상세 도넛:** 탄·단·지 **열량 비율**(탄·단 4kcal/g, 지방 9kcal/g). %는 최대 잔여법으로 합이 항상 100. 가운데에 kcal(없으면 g 합산 앞에 "약"). 일부 null이면 차트 없이 범례+안내, 전부 null/0도 별도 문구. 레시피 영양은 식약처가 아니라 Gemini가 레시피 생성 때 준 1인분 값이며 컴포넌트만 공유(`Common/NutritionChart`).
- **재료 수정 모달:** `GET /api/fridge-items/{id}/nutrition`(100g당). 영양은 **따로 불러와** 로딩·실패여도 이름·유통기한 수정/삭제는 가능. 이름이 다르게 매칭되면 "'배추김치' 기준" 표시, 404엔 다시 시도 버튼 숨김.
- **냉장고 "영양 균형" 모달:** `GET /api/fridges/{id}/nutrition-summary?storage=FRIDGE|FREEZER|ROOM`(storage 생략=전체, 대문자만, 틀리면 400 INVALID_INPUT). 재료마다 **100g씩 있다고 보고** 합친 비율이고 값이 일부 없는 재료는 합계에서 빠진다. 구역별 응답을 따로 주면 같은 재료가 두 번 실려 커지므로 **구역 필터 한 API**로 정했고, 요약은 DB만 읽어 빨라 탭마다 재요청해도 된다. 요약 API는 식약처를 안 기다리고 `pendingCount`만 준다.
- **폴링:** `pendingCount>0`이면 재요청 — 처음 2초×3회였다가 실측(재료당 4~6초, 스레드 2개) 때문에 **3초×최대 6회(약 18초)**로 변경. 탭을 바꾸면 이전 탭 타이머를 멈추고 새 탭 기준으로 처음부터. 이 때문에 모달 세션 키는 열기/재시도/탭 전환마다 오르는 카운터 하나로 두고(그냥 `fridge-scope`를 키로 쓰면 이전 탭으로 돌아올 때 횟수가 이어짐), 결과에 "몇 번째 요청의 응답인지"를 같이 저장해 `isPolling`을 계산한다(안 그러면 마지막 응답 전에 "확인하지 못했어요"가 먼저 뜸).
- 리뷰·QA에서 나온 UI 함정: 서버 소수 2자리 값이 도넛 가운데를 넘침(g 소수 1자리·kcal 정수로 반올림), 탭마다 내용 높이가 달라 모달이 움직임(위쪽 정렬 옵션), 영양 블록 로딩→차트 전환 때 저장 버튼이 밀림(placeholder `min-height`), `aria-label`은 role 없는 div에서 안 읽힘(`role="group"`), "탄/단/지" 약어는 낭독 시 모호. CodeRabbit의 "함수마다 docstring" 요구는 레포 규칙(필요할 때만 주석)과 달라 반영하지 않고 이유를 PR에 남김.

## 도감 기본 재료 76개 (BE #55·FE #59)
- 영양 미리 넣기(`food_nutrition`)와 **다른 표**(`ingredient_catalog`)다. 도감은 `owner_id`가 NULL이면 공용 재료인데, 기존 목록 API는 내 재료만 반환했고 냉장고 넣기·장본 음식·즐겨찾기도 `findByIdAndOwnerId`(3곳)라 공용 재료를 못 받았다 → 목록에 공용+내 재료를 함께 주고(응답에 `basic` 추가) 세 API가 공용 id를 받게 고침. 서버 시작 시 없는 것만 삽입(재시작해도 안 늘고, 배포 DB 불필요), 기본 재료는 삭제 불가("기본" 표시), 같은 이름으로 새로 추가하면 409, 예전에 같은 이름을 직접 추가한 사용자에겐 기본 재료를 숨김.
- 식약처에서 도감 값 중 채울 수 있는 건 이름·(아마)분류뿐이고, 아이콘·기본 보관 위치·유통기한·구매 주기·단위는 직접 정해야 한다(일반 권장값, 팀 확인 필요). 도감 응답에 보관 위치가 없어 "냉장고에 넣기" 모달이 기본 재료도 냉장실로 열리는 한계가 남음. 도감은 다른 팀원 담당이라 PR에 확인 요청을 남김.

## 협업·운영 메모
- FE·BE 세션이 따로일 때: **명세를 먼저 확정**(필드·null·오류 코드)한 뒤 FE는 가짜 서버로 퍼블리싱, BE PR이 올라오면 **임시 worktree+끄면 사라지는 임시 MySQL**로 실서버 연동을 확인(BE 작업 폴더·실 DB 안 건드림). 머지 순서는 BE→FE, 스택 PR(#47이 #46 위)은 하위가 머지되면 대상을 develop으로 바꿔야 CodeRabbit 자동 리뷰가 돈다. 무료 리뷰 한도에 걸리면 재요청을 기다림.
- 테스트 데이터를 mysql 클라이언트로 넣을 때 `--default-character-set=utf8mb4`가 없으면 한글이 깨져 전부 "못 찾음"처럼 보인다.
- `.env`에서 `KEY= 값`처럼 `=` 뒤에 공백이 있으면 셸이 값을 명령으로 실행하려다 오류 메시지에 값을 그대로 찍는다(비밀값 노출 + 다른 도구가 빈 값으로 읽을 수 있음). `.env`는 셸로 source하지 말고 필요한 값만 꺼내 쓴다. Spring은 `spring.config.import: optional:file:.env`로 읽는다.
- zsh에서 모니터링 스크립트의 변수가 단어 분리되지 않아 URL이 깨짐 → bash로 실행.
