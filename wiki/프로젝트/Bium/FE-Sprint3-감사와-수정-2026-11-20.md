# Bium FE — Sprint 3 감사와 수정 (2026-11-20)

Sprint 1~3 기능을 FE 코드·BE develop 컨트롤러·실서버 스모크 테스트로 대조 감사한 뒤, FE만 고치면 되는 결함을 이슈 #63~#67, #74, #78로 나눠 PR(#68~#73, #75, #79)로 머지했다. 계약 불일치는 없었고 대부분 "상태 캐시가 낡았을 때 복구되지 않는" 유형이었다. 감사·구현·검증을 일꾼 에이전트로 나눠 돌렸다.

## 감사 결과 요약
- **계약**: BE develop 엔드포인트 47개를 FE `src/api`가 모두 부름. 스모크 37개 호출 전부 FE 타입과 일치. 빠진 것은 응답 필드 `marketPrice` 하나.
- **BE 응답 특성(FE 책임 아님)**: 형식이 틀린 본문의 `BAD_REQUEST`/영어 "Bad Request"(→ BE PR #61에서 `INVALID_INPUT`+한국어로 해결), 내용 없는 이미지에도 Gemini가 목록을 지어냄(→ 스캔 결과를 사용자가 확인·수정하는 단계가 필수인 근거), 영수증 이미지 검사는 선언된 Content-Type만 봄.
- **요리 되돌리기 구멍**: 요리 완료 응답에 되돌리기용 `id`가 오는데 FE(`CookingModal`)가 버리고, 되돌리기 버튼은 활동 기록에만 있었음. BE 활동 기록은 최근 50개만 주므로 영수증으로 재료 50개를 넣으면 되돌릴 방법이 사라짐 → 요리 완료 안내 옆에 그 `id`로 버튼을 두는 방향(BE 변경 없음, 팀원 #77에서 처리).
- **"다시 불러왔어요" 거짓 안내**: `refreshContents`가 실패해 null을 돌려줘도 성공 문구를 띄우던 패턴(옮기기·장본 음식 넣기·만료 일괄 삭제). 옮기기는 화면에 낙관적으로 옮긴 재료가 원래 자리로 안 돌아옴.
- **정의 없는 항목**: "유통기한 Bar·장보는 날·피버타임"은 감사 시점에 FE·BE·v1 어디에도 없었음(이후 #76으로 팀원이 머지). 즐겨찾기 "전체 탭 맨 위 고정"은 카테고리 묶음마다 맨 앞이라 의도 확인이 필요했음(#77에서 처리).

## 고친 결함과 설계 결정
- **시세 표시(#68)**: BE `marketPrice`는 쇼핑몰 최저가가 아니라 **KAMIS 소매가**라 문구를 "최저가"가 아닌 "시세"로. 값은 KAMIS 키가 있고 매일 18:00 수집이 한 번 돈 뒤에야 채워짐(그 전엔 전부 `null`). 안내 문구는 두 묶음 아래 한 번만(#75).
- **로그아웃(#69/#73)**: BE가 세션 없이 JWT(1시간)만 쓰므로 FE가 토큰·선택 냉장고·`bium-recipes`를 지우고 `/login`으로 보내면 끝. 로그인 상태에서 `/`·`/login`은 `/fridge`로. 로그인 화면 가드의 판정은 `RequireAuth`와 같아야 한다는 CodeRabbit 지적을 #73에서 반영.
- **없는 주소(#70)**: react-router는 맞는 주소가 없으면 `path === "/"` 라우트에 404를 붙이는데 그 라우트가 `<Navigate>`라 헤더 없는 기본 영문 오류 화면이 뜸 → `*` 라우트 + `NotFound` 추가.
- **'다시 시도'가 복구 안 됨(#72)**: 헤더 냉장고 목록을 한 번 받아 캐시하고 모든 화면이 그 목록에서 고르므로, 내보내진 냉장고 X는 캐시에 남아 404가 반복되고, 첫 목록 요청이 실패하면 헤더 버튼도 새로고침 전까지 없어짐.
  - 채택: `client.ts`가 `FRIDGE_NOT_FOUND`를 받으면 `markFridgeListStale()`로 낡음 표시 → 다음 `getFridges()`가 목록을 새로 받음(401 때 `clearAuth()` 부르는 기존 방식과 같은 모양). `getMyFridge()`는 스토어의 `getFridges()`를 거치고, 진행 중인 목록 요청(`pendingList`)은 같이 기다려 동시 요청을 1번으로 합침. 새 목록에 고른 냉장고가 없으면 `selectedFridgeId`를 null로.
  - 버린 대안: 404 즉시 목록 재요청(공유 화면의 "내보냈을 수 있어요" 안내가 사라지고 남의 피드 404에도 요청이 나감), 매번 목록 받기(왕복 추가), 화면마다 `await loadFridges()`(남의 화면 수정).
  - 부작용: `client.ts → fridgeStore → api/fridge → client.ts` 순환 import. 모듈 최상단에서 서로 안 쓰면 무해하고 build 경고도 없으며 프로덕션 번들에서도 오류 없음을 확인.
  - CodeRabbit 지적: 초대 코드 참여 **전에** 보낸 목록 요청이 늦게 오면 방금 참여한 냉장고가 지워질 수 있음(요청 번호로 낡은 응답 무시).
- **냉장고 전환 잔상(#71)**: `AppLayout`의 `<Outlet key={selectedFridgeId}>`는 화면만 다시 그리고 `/recipes/:id` 주소는 그대로라, 다른 냉장고 레시피에서 '요리 완료'가 이전 냉장고 재료를 뺌(BE 레시피 응답에 `fridgeId`가 없어 FE가 구분 못 함).
  - `FridgeSwitcher.handleSelect`에서 상세 화면이고 고른 냉장고가 현재와 다를 때 `navigate("/recipes", { replace: true })` 후 선택. `replace`는 뒤로 가기로 이전 상세로 안 돌아오게 하려는 것.
  - 버린 대안: 스토어 구독으로 `selectedFridgeId` 변화 감지 — 첫 로딩(null→값)·로그인 전환·나가기(값→null)도 "변경"으로 잡혀 새로고침 때 상세가 튕김. `useRef`는 Outlet key 때문에 재마운트돼 불가.
  - '만들고 싶은 음식'의 `TargetState` 로딩·오류에도 요청한 `fridgeId`를 넣어 요청한 냉장고에서만 보여 줌(AI 추천 `RecommendState`에 #53에서 한 것과 같은 방식). 입력칸은 `typed` 상태로 고정해 요청이 끝나도 안 비게.
- **헤더 폭(#69→#75)**: 로그아웃 버튼 36px+간격이 냉장고 이름 칸을 줄여 이름이 잘림. grid 오른쪽 칸을 `clamp(...)`로 넓히고 구간별로 padding·간격을 줄여 1001px 이상에서 이름(94px)이 다 보이게 함. 1001~1079px에서는 메뉴가 가운데보다 왼쪽으로 최대 ~59px 치우치는 대가를 감수(이름 94 + 브랜드 86 + 메뉴 671px 이상의 합이 안 들어감). 시연은 1280px 이상 권장.
- **피드 내 냉장고 카드(#75)**: 나간 냉장고가 비공개면 미리보기 '다시 시도'가 같은 X를 또 부름 → `FRIDGE_NOT_FOUND`일 때만 `loadFridges()`를 먼저 await. X가 공개면 서버가 누구에게나 보여 주는 정상 동작이라 오류 없이 보임.

## 멤버 내보내기 활동 기록 (FE #79 ↔ BE #65)
- 협의로 확정한 명세: `GET /api/fridges/{id}/activities`에 action `REMOVE` 추가(전체: ADD, UPDATE, MOVE, DELETE, DEDUCT, RESTORE, JOIN, LEAVE, REMOVE), 모든 기록에 `targetNickname: string | null`(REMOVE만 값). REMOVE에서 `nickname`=내보낸 주인, `targetNickname`=내보내진 멤버. 이전 내보내기는 "내보내진 사람의 LEAVE"로 남아 있고 옮기지 않음.
- **배포 순서**: FE를 먼저. #79 이전 FE는 `actionMeta[row.action]`이 undefined라 `Cannot destructure property 'icon'`으로 공유 화면 전체가 오류가 됐음(실제 재현). 그래서 #79는 모르는 action을 건너뛰고, 보여 줄 줄이 없으면 빈 목록 안내를 띄움. **모르는 enum 값이 와도 전체가 죽지 않게 하는 방어**가 핵심.
- 실서버 확인된 내보내기 동작: 멤버가 남을 내보내면 403 `FRIDGE_OWNER_ONLY`, 주인이 자신을 내보내면 409 `OWNER_CANNOT_LEAVE`, 없는 멤버 404 `FRIDGE_MEMBER_NOT_FOUND`(어느 경우도 기록 안 늘어남). 내보내진 사람이 활동 기록을 조회하면 404 `FRIDGE_NOT_FOUND`. 내보내면 서버가 **초대 코드도 꺼서** 같은 코드로 재참여하면 410 `INVITE_EXPIRED`(매번 새 코드 필요). REMOVE 줄은 주인과 남은 멤버만 봄.
- **BE #65의 치명 결함(실서버 검증으로 발견)**: 기존 DB의 `activity_logs_chk_1` CHECK 제약에 `REMOVE`가 없는데 `ddl-auto: update`는 컬럼은 추가해도 **CHECK 제약은 갱신하지 않음** → 업그레이드 DB에서 내보내기가 500, 같은 트랜잭션이라 내보내기도 롤백. 테스트가 H2·새 DB라 통과했음. 배포 DB는 제약 수동 변경/마이그레이션이 필요. 결함이 해결되기 전 BE 머지 금지로 합의(감사 시점에는 미해결 → 아래 항목에서 해결).
- **BE #65 결함의 해결과 최종 상태 (2026-11-20 09:28 KST 머지, 머지 커밋 `6bab132`, 이슈 #64)**
  - 서버 기동 시 CHECK 제약을 현재 enum 값으로 자동 재생성하도록 `IngredientSourceCheckMigration`을 **`EnumCheckConstraintMigration`**으로 일반화(대상: recipe_ingredients.source, activity_logs.action). 배포 때 수동 작업 없음. `@Order(HIGHEST_PRECEDENCE)`로 다른 시작 runner(시드·시세)보다 먼저 돌지만, `ApplicationRunner`는 웹 서버가 요청을 받기 시작한 뒤에 돌아 그 짧은 사이의 요청은 실패할 수 있음.
  - 구현 요점: 표 이름으로 `information_schema` 조회를 좁히고, 제약 절을 소문자로 바꿔 **식별자 경계 정규식** `(?<![a-z0-9_])action(?![a-z0-9_])`로 "그 칸의 제약"만 고름(`source_id` 같은 칸 오탐 방지, MySQL의 `` `action` in (_utf8mb4'ADD',…)``와 H2의 `"ACTION" IN('ADD',…)` 표기 모두 일치). MySQL 8.4에서는 같은 이름 제약을 한 문장에서 DROP 후 ADD 가능, H2는 두 문장으로 나눔. 칸마다 try를 따로 걸어 한 칸 실패가 다른 칸을 막지 않음. 새 제약 이름은 `activity_logs_action_check`.
  - **enum 값을 추가할 때 체크리스트**: varchar enum 칸은 `EnumCheckConstraintMigration`의 `TARGETS`에 수동으로 넣어야 함(Recipe 2개·NotificationLog·IngredientCatalog·PurchasedItem 칸은 아직 미포함). H2 테스트는 새 DB라 이 문제를 못 잡으므로 develop으로 만든 기존 MySQL DB에 브랜치를 띄워 확인해야 함.
  - 스키마: `activity_logs.target_user_id`(null 허용, FK) 추가, `docs/ERD.dbml` 반영. 이미 `LEAVE`로 남은 과거 내보내기는 누가 내보냈는지 알 수 없어 그대로 둠. `REMOVE`가 아닌 기록도 `targetNickname: null` 키가 나감.
  - **롤백 주의**: `REMOVE` 행이 생긴 뒤 BE를 #65 이전으로 되돌리면 그 냉장고의 활동 기록 조회가 500 → `REMOVE` 행을 먼저 지워야 함.
  - 검증: `./gradlew test` 342개, 독립 재리뷰 APPROVE, FE 세션이 MySQL 8.4에서 기존 DB·새 DB·재기동 시나리오 통과(내보내기 204, 첫 줄 `REMOVE`).
- 시간대(BE PR #62): `BiumApplication.main`에서 `TimeZone.setDefault("Asia/Seoul")`로 JVM 시간대를 고정해 `@CreationTimestamp` 계열 전부를 해결. 응답은 오프셋 없는 `LocalDateTime`이라 FE 변경 없음. 서버가 UTC였던 동안 저장된 옛 행은 9시간 어긋난 채 남을 수 있음.

## 작업 방식에서 얻은 교훈
- **CodeRabbit 무료 한도**는 한 시간에 리뷰 한 건꼴. PR을 한꺼번에 올리면 대부분 리뷰 없이 머지하게 됨 → 한 건씩 `@coderabbitai review`를 걸거나, 한도에 걸리면 lint·build·화면 검증으로 대체. 추가 커밋을 올리면 대기 시간이 다시 잡힘.
- 헤드리스 크롬 + `page.route`로 API를 가로채 빠르게 화면을 확인할 수 있지만, 실서버(BE 브랜치 + 임시 MySQL 컨테이너)로 붙여야 DB 제약 같은 문제가 드러남.
- 에이전트의 "코드 추적만 했다" 보고는 주장일 뿐이라, 스크린샷 확인에서 링크 색(브라우저 기본 파랑·밑줄)·헤더 잘림 같은 문제가 추가로 나옴.
- 일꾼 감사 보고의 담당 추정(시간대=선재 vs 윤호 등)은 틀릴 수 있어 목록에 "추정"을 명시.

## 시연 순서 (develop 기준, 흐름형)
로그인(기본 냉장고 자동 생성) → 냉장고(3구역·D-day·피버타임 배너) → 드래그 이동·만료 일괄 삭제 → 수정 모달·영양 도넛 → 도감·즐겨찾기 → 영수증 등록 → AI 레시피(임박 재료 추천) → 요리 완료·되돌리기 → 만들고 싶은 음식→부족 재료→장보기 담기 → 장보기 시세·장보는 날 → 공유(초대 코드·참여·활동 기록·내보내기) → 피드 → 알림 설정 → 로그아웃.
- 준비: 계정 2개(B는 다른 브라우저), 3일 안 임박 재료 3개 이상, 시세 나오는 이름(양파·감자·달걀)의 장보기 항목, 또렷한 영수증 사진, KAMIS·Gemini·메일 설정 확인.
- 주의: AI 응답은 몇 초 걸리고 한도에 걸리면 오류(미리 한 번 받아 두기), 처음 조회하는 재료의 영양 정보는 4~6초(기본 76개는 미리 있음), 메일 설정 없으면 테스트 메일 실패, BE #65 미머지면 내보내기 기록이 "나갔어요"로 보임.

## 로컬에서 실제 백엔드로 화면 검증하기 (2026-11-22)
- 임시 MySQL 컨테이너(`--rm`, 포트 3308) + bootRun + vite dev로 실제 API 화면을 캡처할 수 있다. 끝나면 컨테이너 중지와 서버 PID 종료, 8080·5173·3308 포트 닫힘을 확인.
- **vite는 반드시 5173**: 5199로 띄우면 백엔드 CORS 허용 목록에 없어 로그인이 실패한다.
- 레시피 추천 엔드포인트는 `POST /api/fridges/{id}/recipes/recommendations`(`src/api/recipe.ts`).
- KAMIS 키가 없으면 BE가 시세 수집 경고만 남기고, 영양 정보에는 영향 없다.
- 비밀값(DB 비밀번호·토큰)은 scratchpad 파일에만 두고 출력·보고하지 않는다.
