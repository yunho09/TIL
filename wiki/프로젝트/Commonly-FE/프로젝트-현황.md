# Commonly-FE 프로젝트 현황

경력증명서 발급 프로토타입. Turborepo/bun 모노레포로 `apps/{admin-web,user-web,civil-web}`(각각 담당자/직원/민원인용) + `packages/{ui,utils,hooks}` 구조. 백엔드는 별도 저장소 `DSM2026-Commonly/Commonly-Backend`(Spring Boot).

## 컨벤션
- 커밋: **제목 한 줄만** — 본문 없음, `Co-Authored-By`/`Claude-Session` 트레일러 없음(사용자 지정 표준). *2026-09-08 세션에서는 세션 자체 지침과 충돌해 예외적으로 트레일러가 붙은 적이 있음.*
- 워크플로: 이슈 생성 → `feature/<이슈번호>-<slug>` 브랜치를 `develop`에서 분기 → `develop`으로 PR.
- **프로토타입 UI 원칙**: 백엔드 API가 없다는 이유로 UI를 숨기거나 제거하지 않는다.

## FE↔BE 갭 (2026-09-07 기준, BE `cb594fd`, FE `develop`=`eea2a7c` 대조)

### BE 엔드포인트 부재로 화면이 막힌 것
- 개별 등록 경력사항 등록: FE는 `POST /api/certificates/create`를 부르지만 BE엔 없음(발급용 `POST /api/certificates`만 존재) → 404. 대상자 생성/수정(`/api/human`)까지는 성공하고 경력 행만 실패.
- 민원인 본인 경력 조회: `GET /api/certificates/self` 없음(`POST`만 매핑) + `/api/certificates/**`가 `ADMIN,USER` 권한만 허용해 민원인(`PETITIONER`)은 차단. **이 백엔드는 권한 부족에도 403이 아니라 401(빈 본문)을 준다** — 실계정으로 `/api/certificates/self`, `/api/certificates/1`, `/api/issuance-histories` 모두 401 확인. 메커니즘: `exceptionHandling`에 `authenticationEntryPoint(401)`만 등록되고 `accessDeniedHandler`가 없어 `AccessDeniedException`도 entry point로 떨어져 401로 나옴(일반 패턴은 [[401을-세션만료로-오인한-로그인-루프]] 참고).
- 민원인 본인 발급: `POST /api/certificates/self`가 `app.certificate.self-issue-enabled=true`(기본 false) 아니면 `SecurityConfig`에서 `denyAll`.
- 결과적으로 civil-web은 로그인/회원가입만 동작하고 증명서 발급 전 과정이 막혀 있었음.

### 심각한 백엔드 버그 (이 세션에서 새로 발견)
**대량 등록(bulk upload) 데이터가 대상자에 연결되지 않는다.** `MappingConfirmService`가 `CertificateEntity`를 `humanId = null`로 저장하는데, 조회(`findAllByHumanId`)와 발급 모두 `humanId` 조건으로 필터링해서 **이 행들은 절대 조회·발급되지 않는다**. 대량 등록은 지금 쓸 수 없는 고아 데이터만 쌓고 있다. 프론트 우회 경로 없음(BE에서 human 매칭/생성 로직 필요) — "개별 등록을 파일 업로드 API로 우회"하는 방법도 이 이유로 성립하지 않는다.

### 프론트로 못 고치는 것
- 헤더에 사용자명 대신 계정 ID가 뜬다: `JwtGenerator`가 JWT에 `subject(accountId)`만 넣고 이름/권한/userId 클레임이 없음. 내 정보 조회 API도 없어 우회 불가(ADMIN만 `/api/admins?keyword=`로 우회 가능). BE에 클레임 추가나 `/api/auths/me` 필요.
- `HumanService.delete`가 human 행만 지우고 관련 certificate는 `human_id`를 그대로 든 채 고아로 남음(BE가 cascade 안 함) — 대상자 삭제 UI에 "등록된 경력 사항은 함께 삭제되지 않습니다" 경고를 넣는 것으로만 완화.
- 세션 연장 버튼(`onExtend`가 세 앱 어디에도 안 넘겨짐, BE에 refresh/연장 엔드포인트 자체가 없음), 로그아웃 서버측 무효화 없음, 아이디/비밀번호 찾기(`href="#login-help"` 죽은 링크), 민원인 본인인증(`window.prompt` 스텁)은 전부 BE 선행 필요.

### FE 코드만으로 되는 것 (BE는 이미 지원)
- 발급 결과 새로고침 복구: 발급 직후 `issuedRef`(useRef)에만 결과를 들고 있어 새로고침하면 다운로드가 죽던 문제. `GET /api/certificates/{certificateId}`가 문서번호·발급일 등을 다 주므로 sessionStorage에 `certificateId`만 보관하고 재조회하면 복구 가능.
- 대상자 삭제: `DELETE /api/human/{humanId}`가 있는데 FE 호출부가 없었음.
- 비밀번호 변경/내 정보 수정은 **admin-web 한정** 가능: `PATCH /api/auths/{userId}`·`PATCH /api/auths/password/{userId}`가 숫자 `userId`를 요구하는데 JWT엔 없음. ADMIN은 `GET /api/admins?keyword=<accountId>`로 자기 `userId`를 얻을 수 있어 구현 가능하지만, user-web(직원)·civil-web은 불가.

### 설정 미비
- 주소 검색: `VITE_JUSO_CONFM_KEY` 미설정으로 실패하던 것을 이 세션에서 키를 발급받아 해결. 발급 절차는 [[도로명주소-검색-API-신청]], 키가 빌드에 인라인되는 메커니즘은 [[Vite-빌드타임-환경변수-인라인]] 참고. **지금 넣은 키는 개발용**(`dev` 접두사, 본인인증 없이 즉시 발급) — 운영 배포 전 배포 도메인으로 운영키를 별도 신청해야 함.

### 스펙 한계로 반쪽인 기능
- `GET /api/admins`, `GET /api/issuance-histories`가 페이지 메타 없이 배열만 반환 → 총 건수 표시 불가, 페이징은 "다음 페이지 존재 여부" 추정 방식.
- 발급이력 `type`(구분) 필터는 FE 쿼리 빌더는 지원하나 BE 파라미터가 없어 무시됨(그래서 UI에 노출 안 함).
- 경력 수정의 `division`(구분)은 BE가 채용/전보/해지/퇴직만 허용해 FE가 원본값을 그대로 되돌려 보냄(사용자가 변경 불가).

## PR 리뷰(CodeRabbit) 대응 — 2026-09-08

#70/#71/#73 세 PR에 대한 CodeRabbit 리뷰 코멘트 4건을 전부 처리. 둘은 실제 버그로 확인되어 수정, 하나는 무의미한 경로라 스킵, 하나는 오탐이라 반박(CodeRabbit이 이후 직접 철회).

- **#71 삭제 버튼 동시성 버그(진짜 버그)**: `handleDeleteApplicant`는 `deletingApplicantId`가 이미 차 있으면 다른 행 삭제 요청도 조용히 `return`하는데(`CareerEdit.tsx:1192`), 버튼의 `disabled`는 `deletingApplicantId === applicant.id`로 **해당 행에만** 걸려 있었다(`:509`). 그래서 한 행을 삭제하는 동안 다른 행 버튼은 그대로 눌리는 것처럼 보이지만 클릭해도 확인창도 에러도 없이 아무 일도 안 일어남. `disabled={deletingApplicantId !== ""}`로 삭제 진행 중엔 모든 행을 잠그도록 수정(커밋 `eb44f8c`). **교훈**: "처리 중" 락 변수가 있으면 `disabled` 조건은 그 락 변수 자체를 봐야지, 락을 쥔 항목의 id와 비교하면 다른 항목에서 조용히 씹히는 버그가 생긴다.
- **#70 문서번호 빈 문자열 통과(진짜 버그, 경미)**: `normalizeCertificateDetail`이 `documentNo: ""`를 그대로 통과시켜(`certificates.ts:343`) 발급 결과 복구 자체는 성공하지만 문서번호 칸이 빈칸으로 뜸. `documentNo.trim() === ""`면 거부하는 조건 추가 + 테스트 1건(커밋 `55f3f8b`).
- **#71 prop 기반 결과 미반영 지적**: 스킵. 유일한 소비자 `StaffCareerEditPage`가 `onSearch`도 함께 넘겨서 해당 코드 경로 자체가 발생하지 않음.
- **#73 juso 승인키 오탐**: CodeRabbit이 웹검색 근거로 "본인인증 없이 승인키 발급 경로가 없다"고 지적했으나, 인용 근거는 계정 생성 단계 QnA일 뿐 신청 폼의 실제 라디오 옵션(`개발(본인인증없이 발급)`, [[도로명주소-검색-API-신청]] 참고)을 반박하지 못함. 실제 dev 키로 `errorCode: "0"` 확인한 근거를 들어 반박했고, CodeRabbit이 재검토 후 해당 지적을 직접 철회함 — dev 키 발급 절차 문서화 내용이 재확인됨.

## 로그인 무한 루프 버그 — 이슈 #74 / PR #75 (2026-09-08)

**증상**: 회원가입 → `/career/issue` 진입 직후 로그인 화면으로 튕기고 토큰이 지워짐. 로그인해도 200 응답 후 다시 같은 화면에서 튕겨 로그인 화면에 갇힘.

**원인**: 위 "민원인 본인 경력 조회" 항목대로 `/api/certificates/self` 권한 부족 응답이 403이 아니라 401인데, FE `packages/utils/src/api.ts`가 401을 무조건 세션 만료로 보고 토큰을 지웠음. `/career/issue` 화면이 진입 즉시 본인 경력을 조회하는 구조라 로그인 직후마다 자기 자신을 로그아웃시켰다. 일반화된 원인·해결 패턴은 [[401을-세션만료로-오인한-로그인-루프]] 참고.

**수정**(`packages/utils`): 토큰이 아직 유효하면 401을 받아도 세션을 지우지 않도록 변경, 본인 조회/발급 401 문구를 "로그인 만료" 대신 권한 안내로 교체, 회귀 테스트 3건 추가. `bun test` 136 pass, typecheck·lint·build 통과. 이슈 #74 → 브랜치 `feature/74-login-loop-401` → PR #75(develop, `Closes #74`).

**남은 진짜 블로커(FE로 못 고침)**: 민원인 본인 경력 조회·발급이 실제로 동작하려면 백엔드가 `GET /api/certificates/self` 신설 + `PETITIONER` 허용, 그리고 `POST /api/certificates/self`용 `CERTIFICATE_SELF_ISSUE_ENABLED=true`가 필요하다(현재 의도적으로 꺼둔 상태 — BE 주석상 본인인증 미구현 때문).

**곁가지**: 이 세션에서 로컬 재현이 안 된다는 제보가 있었는데, 코드는 맞았고 dev 서버가 `packages/utils`의 옛 변환 캐시를 서빙하고 있던 것이었다. 원인·해결은 [[Vite-모노레포-워크스페이스-패키지-dev서버-캐시]] 참고.

## 명세 불일치로 인한 민원인 발급 화면 재설계 — 이슈 #76 / PR #77 (2026-09-10)

**배경**: PR #75까지는 "BE가 `GET /api/certificates/self`를 신설하면 풀린다"고 봤다. 이번 세션에서 노션 API 명세서(`🚽 API 명세서 유성구청`)에 접근이 되어 경력증명서 그룹 7개 엔드포인트를 전수 확인한 결과, **애초에 그런 엔드포인트가 명세에 없었다**. `/api/certificates/self`는 **POST 발급 전용**이고, 민원인 본인 경력 목록을 조회하는 API는 명세 어디에도 없다(목록 조회는 담당자용 `GET /api/humans/{humanId}/certificates` 하나뿐). FE `fetchSelfCertificates()`는 명세에 없는 엔드포인트를 임의로 가정해 만든 코드였다.

**추가 발견**: `issueSelfCertificate()`가 보내던 `certificateIds`(선택 발급 파라미터)도 명세·BE `SelfCertificateIssueRequest` 둘 다 `purpose`/`otherMatters`만 받는다(BE 주석: "humanId와 certificateIds는 인증 주체에서 나오므로 body에 없다"). 서버는 이 필드를 그냥 무시하고 **항상 본인 전체 경력을 발급**한다.

**결론/수정**: 없는 BE 기능을 기다리는 대신 FE를 명세에 맞춰 재정렬(develop 대상 PR #77):
- `fetchSelfCertificates`·관련 메시지 상수·`certificateIds` 필드 제거.
- 민원인 진입 시 자동 경력 조회 effect 제거 → 로그인 직후 401을 유발하던 호출 자체가 사라짐.
- 선택 발급 UI는 그대로 두되(위 "프로토타입 UI 원칙"에 따라 기능을 숨기지 않음), 빈 표에 "본인 경력 목록 조회는 아직 제공되지 않습니다. 신청하시면 본인 전체 경력으로 발급됩니다" 안내를 추가.
- `bun test` 151 pass, lint 0 errors, build 5/5 통과.

**여전히 남은 진짜 블로커**: 발급 자체(`POST /api/certificates/self`)는 BE `app.certificate.self-issue-enabled=false`라 여전히 `denyAll`이라 신청 시 401이 뜬다. BE 플래그를 켜야 풀리며 FE에서 손댈 수 없다. PR #75가 진단했던 "`GET /self` 신설 필요"는 명세 재확인 결과 폐기됨.
