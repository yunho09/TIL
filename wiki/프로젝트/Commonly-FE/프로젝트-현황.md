# Commonly-FE 프로젝트 현황

경력증명서 발급 프로토타입. Turborepo/bun 모노레포로 `apps/{admin-web,user-web,civil-web}`(각각 담당자/직원/민원인용) + `packages/{ui,utils,hooks}` 구조. 백엔드는 별도 저장소 `DSM2026-Commonly/Commonly-Backend`(Spring Boot).

## 컨벤션
- 커밋: **제목 한 줄만** — 본문 없음, `Co-Authored-By`/`Claude-Session` 트레일러 없음(사용자 지정 표준). *2026-09-08 세션에서는 세션 자체 지침과 충돌해 예외적으로 트레일러가 붙은 적이 있음.*
- 워크플로: 이슈 생성 → `feature/<이슈번호>-<slug>` 브랜치를 `develop`에서 분기 → `develop`으로 PR.
- **프로토타입 UI 원칙**: 백엔드 API가 없다는 이유로 UI를 숨기거나 제거하지 않는다.

## FE↔BE 갭 (2026-09-07 기준, BE `cb594fd`, FE `develop`=`eea2a7c` 대조)

### BE 엔드포인트 부재로 화면이 막힌 것
- 개별 등록 경력사항 등록: FE는 `POST /api/certificates/create`를 부르지만 BE엔 없음(발급용 `POST /api/certificates`만 존재) → 404. 대상자 생성/수정(`/api/human`)까지는 성공하고 경력 행만 실패.
- 민원인 본인 경력 조회: `GET /api/certificates/self` 없음(`POST`만 매핑) + `/api/certificates/**`가 `ADMIN,USER` 권한만 허용해 민원인은 403.
- 민원인 본인 발급: `POST /api/certificates/self`가 `app.certificate.self-issue-enabled=true`(기본 false) 아니면 `SecurityConfig`에서 `denyAll`.
- 결과적으로 civil-web은 로그인/회원가입만 동작하고 증명서 발급 전 과정이 막혀 있었음.

### 심각한 백엔드 버그 (이 세션에서 새로 발견)
**대량 등록(bulk upload) 데이터가 대상자에 연결되지 않는다.** `MappingConfirmService`가 `CertificateEntity`를 `humanId = null`로 저장하는데, 조회(`findAllByHumanId`)와 발급 모두 `humanId` 조건으로 필터링해서 **이 행들은 절대 조회·발급되지 않는다**. 대량 등록은 지금 쓸 수 없는 고아 데이터만 쌓고 있다. 프론트 우회 경로 없음(BE에서 human 매칭/생성 로직 필요) — "개별 등록을 파일 업로드 API로 우회"하는 방법도 이 이유로 성립하지 않는다.

### 프론트로 못 고치는 것
- 헤더에 사용자명 대신 계정 ID가 뜬다: `JwtGenerator`가 JWT에 `subject(accountId)`만 넣고 이름/권한/userId 클레임이 없음. 내 정보 조회 API도 없어 우회 불가(ADMIN만 `/api/admins?keyword=`로 우회 가능). BE에 클레임 추가나 `/api/auths/me` 필요.
- `HumanService.delete`가 human 행만 지우고 관련 certificate는 `human_id`를 그대로 든 채 고아로 남음(BE가 cascade 안 함) — 대상자 삭제 UI에 "등록된 경력 사항은 함께 삭제되지 않습니다" 경고를 넣는 것으로만 완화.
- 세션 연장 버튼(`onExtend`가 세 앱 어디에도 안 넘겨짐, BE에 refresh/연장 엔드포인트 자체가 없음), 로그아웃 서버측 무효화 없음, 아이디/비밀번호 찾기(`href="#login-help"` 죽은 링크), 민원인 본인인증(`window.prompt` 스텁)은 전부 BE 선행 필요.

### FE 코드만으로 되는 것 (BE는 이미 지원)
- 발급 결과 새로고침 복구: 발급 직후 `issuedRef`(useRef)에만 결과를 들고 있어 새로고침하면 다운로드가 죽던 문제. `GET /api/certificates/{certificateId}`가 문서번호·발급일 등을 다 주므로 sessionStorage에 `certificateId`만 보관하고 재조회하면 복구 가능.
- 대상자 삭제: `DELETE /api/human/{humanId}`가 있는데 FE 호출부가 없었음.
- 비밀번호 변경/내 정보 수정은 **admin-web 한정** 가능: `PATCH /api/auths/{userId}`·`PATCH /api/auths/password/{userId}`가 숫자 `userId`를 요구하는데 JWT엔 없음. ADMIN은 `GET /api/admins?keyword=<accountId>`로 자기 `userId`를 얻을 수 있어 구현 가능하지만, user-web(직원)·civil-web은 불가.

### 설정 미비
- 주소 검색: `VITE_JUSO_CONFM_KEY` 미설정으로 실패하던 것을 이 세션에서 키를 발급받아 해결. 발급 절차는 [[도로명주소-검색-API-신청]], 키가 빌드에 인라인되는 메커니즘은 [[Vite-빌드타임-환경변수-인라인]] 참고. **지금 넣은 키는 개발용**(`dev` 접두사, 본인인증 없이 즉시 발급) — 운영 배포 전 배포 도메인으로 운영키를 별도 신청해야 함.

### 스펙 한계로 반쪽인 기능
- `GET /api/admins`, `GET /api/issuance-histories`가 페이지 메타 없이 배열만 반환 → 총 건수 표시 불가, 페이징은 "다음 페이지 존재 여부" 추정 방식.
- 발급이력 `type`(구분) 필터는 FE 쿼리 빌더는 지원하나 BE 파라미터가 없어 무시됨(그래서 UI에 노출 안 함).
- 경력 수정의 `division`(구분)은 BE가 채용/전보/해지/퇴직만 허용해 FE가 원본값을 그대로 되돌려 보냄(사용자가 변경 불가).
