# 선생님 피드백(11/20) — 접근 권한 3단계·프로젝트별 키

선생님이 11/17 회의 결정(계정당 키 1개 + 분야별 활용신청 + 전부 자동 승인)에 대해 "방향은 괜찮지만" 하고 보낸 보완 의견과, 그에 따라 바뀌는 점·팀이 정해야 할 10가지를 정리했다. **정해야 할 항목의 "추천"은 Claude 의견이며 팀 합의 전**이다. 생년월일만 사용자가 확정했다.

## 선생님 의견 요지
- 학교 이메일 인증 = 구성원 확인일 뿐, **모든 학교 데이터 접근 권한이 아님**. 개인정보(학생·교직원·자습 감독)는 별도 접근 권한 관리 필요.
- **계정당 키 1개**의 문제: 한 학생의 여러 프로젝트가 같은 키를 공유 → 한 곳에서 유출되면 전 권한 노출, 재발급하면 다른 프로젝트까지 영향. → **계정 아래 프로젝트 여러 개, 프로젝트별 키, 필요한 분야 권한만** 부여 검토.
- 승인: 데이터 성격에 따라 자동/관리자 승인 구분. **관리자 승인만으로 개인정보 제공이 가능해지지 않음** → 실제 연동 전 학교 차원 검토 필요(어떤 데이터를 누구에게 무슨 목적으로).
- 보안 추가: 사용 기록 저장·관리자 조회, 키 유출 시 즉시 폐기·재발급, 키 유효기간(30/60일)·갱신 방식, 프론트 코드에 키 노출 방지, 키별 호출 횟수 제한.
- 맨 먼저 할 일: **API별로 제공할 데이터 항목과 접근 권한을 정리한 표**.

### 3단계 구분
| 단계 | 조건 | 예시 |
|---|---|---|
| ① 공개 Public | 인증 없이 | 급식, 일반 학사 일정, 개인정보 없는 동아리 소개·로고 |
| ② 교내 School | 학교 구성원 인증 후, 공개가 승인된 정보만 | 교내 공지 일정, 일반 시간표, 공개 승인된 동아리 정보 |
| ③ 제한 Restricted | 별도 승인+세부 권한, 목적·대상·법적 근거 확인 | 학생 명단·생년월일·이메일, 동아리 구성원, 교직원 명단, 날짜별 자습 감독 교사 |

## 11/17 결정과 달라지는 점
| 항목 | 11/17 | 선생님 답변 |
|---|---|---|
| 키 | 계정당 1개 | 프로젝트별 키 |
| 승인 | 전부 자동 | 공개·교내 자동 / 제한은 관리자 승인+학교 검토 |
| 키 없이 호출 | 급식만 | 급식·학사 일정·동아리 소개/로고 |
| 호출 한도 | 없음 | 키별 제한 |
| 유효기간 | 만료일 표시만(예시 1년) | 30/60일+갱신 방식 |
| 사용 기록 | 없음 | 저장+admin 조회 |
| 폐기·재발급 | 재발급하면 옛 키 401, 삭제 있음 | 현재 계획으로 충족 |

- 현재 분야 5개를 3단계에 매핑하면 **동아리·일정은 한 분야 안에 세 단계가 섞임** → "분야 단위 신청"을 API/단계 단위로 바꿔야 함.
- 3단계로 가면 **신청이 필요한 건 제한 API뿐**(학생·교직원·자습 감독·동아리 구성원).
- 프로젝트별 키는 가장 큰 변경(11/16 "API마다 키"에 이어 키 1개 방식이 두 번째로 지적됨). 백엔드 구조(계정→프로젝트→키·분야)가 먼저 정해져야 활용신청·마이페이지가 따라옴. Claude 추천: 프로젝트 = 이름+키+분야로 범위를 줄여 수용.
- 승인 기능 현황: admin 활용신청 상세는 "승인 완료(자동승인)"만 표시 → 승인 대기 상태와 승인·반려 버튼이 새로 필요(프론트·백엔드 양쪽).
- 호출 제한·사용 기록·유효기간은 대부분 백엔드, 프론트는 Overview 호출 한도·429 문구와 admin 사용 기록 화면 정도. Overview에 남은 "계정 유형에 따라 호출 한도가 다릅니다" 같은 옛 문구 정리 필요.
- 프론트 키 노출 방지: 문서에 "키는 서버에서만 쓰기" 안내 + 필요하면 백엔드가 브라우저발 키 호출을 CORS로 제한. **포털 자체는 허용**해야 API 테스트 페이지가 동작.

## 정해야 할 것 10가지 (Claude 추천 포함)
1~4가 먼저 정해지면 프론트·백엔드가 시작 가능, 5번부터는 회의 후 담당자가 정해도 됨.
1. API별 데이터 항목·단계 표를 누가·언제까지 — 응답 필드를 아는 백엔드가 초안 → 팀 확인 → 선생님 재확인
2. 프로젝트별 키를 이번에 할지 — 추천: 함(이름+키+신청 분야만)
3. 무엇을 신청받을지 — 추천: 제한 API만
4. 제한 API를 출시 때 열지 — 추천: 닫아 두고 신청만 받아 "승인 대기"(학교 검토 전엔 개인정보를 줄 수 없음), 승인·반려 기능은 검토 후
5. 승인 기준 — 신청서에 목적·대상을 적게 할지
6. 생년월일 — **결정됨**(아래)
7. 키 유효기간 — 추천: 60일, 마이페이지에서 이메일 인증 코드로 갱신
8. 호출 횟수 제한 — 일 한도와 429 응답
9. 사용 기록 — 추천: 키·API·시간·응답 코드 저장, admin 목록 조회
10. 프론트 키 노출 방지 — 위 CORS 방식

## 결정: 생년월일은 빼지 않고 "제한 API + 승인 시에만 제공"
- 사용자가 필요하다고 판단해 제외하지 않기로 함. 선생님 표의 "원칙적으로 제공 제외"와 다르므로 **어디에 쓰는지**를 설명해 다시 말씀드려야 함.
- (Claude 보충) 생일 표시 같은 용도라면 연도를 빼고 월·일만 준다고 하면 설득이 쉬움.

## 팀 결정 (같은 날 사용자가 10가지에 답함)
- **1·2 (표 담당·프로젝트별 키)**: 추천대로. 백엔드가 API별 데이터 항목·단계 표 초안 → 팀 확인 → 선생님 재확인. 프로젝트별 키 도입, 프로젝트 = 이름+키+신청 분야만.
- **3·5 (신청 방식, 단계별 승인 기준)**:
  | 단계 | 이메일 인증 | 신청서 | 승인 |
  |---|---|---|---|
  | 공개 (급식 등) | X | 없음(키 불필요) | X |
  | 교내(중간) | O | 간단한 사용 내용 | 자동 승인 |
  | 제한 | O | **사용 목적 필수** | 관리자 승인 필요 |
- **4 (제한 API 출시 때 열지)**: 열어 둠. 단 선생님 조건(학교 차원 검토 전 개인정보 연동 불가)과 맞추려면 **검토 끝날 때까지 관리자가 승인하지 않는 운영**으로 해결.
- **7 (키 유효기간)**: 60일, 마이페이지에서 **이메일 인증 후 갱신**. 갱신해도 **키 값은 유지**(재발급처럼 바뀌면 학생이 배포한 앱을 60일마다 재배포해야 함), 프로젝트가 여럿이면 인증 한 번으로 한꺼번에 갱신.
  - 갱신에 이메일 인증을 넣는 이유: 포털 로그인은 비밀번호라 학교 메일이 막힌 사람(졸업생)도 로그인 가능 → 갱신 때 학교 메일 코드를 받게 해야 60일마다 "아직 학교 메일을 쓰는 사람인지" 확인되어 유효기간의 의미가 생김. 인증을 빼면 "60일마다 버튼 누르기"라 보안 효과가 거의 없음. (졸업 후 학교 메일이 실제로 막히는지는 미확인 — 안 막히면 걸러지는 사람이 거의 없음)
  - 미정: 만료 전 알림(예: 7일 전 메일, 없으면 만료일에 학생 앱이 갑자기 멈춤).
- **8 (호출 횟수 제한)**: 일단 두지 않음. 학교 계정만 쓰고 호출 기록을 다 남기니 사용량 보며 필요하면 추가. 기존 문구("계정 유형별 호출 한도")는 정리, 429 예외 화면은 지우지 않고 "보류" 표시.
- **9 (사용 기록)**: 호출마다 로그(키·프로젝트·API·시간·응답 코드), 키 없는 공개 API 호출도 포함. admin에서 목록 조회.
- **10 (프론트 키 노출)**: **문서 안내만**("키는 서버에서만 쓰기"), 브라우저발 호출은 막지 않음.
  - 선생님 말씀은 우리 포털이 아니라 **우리 API를 쓰는 학생 앱** 이야기. 서버 없이 React만으로 `X-API-KEY`를 붙여 부르면 개발자 도구 Network 탭에 키가 노출됨(AWS 키 유출 주의와 같은 구조).
  - 대안 비교: 문서 안내만 = 쉽지만 무시하면 못 막음 / CORS로 브라우저 호출 차단 = 확실히 막지만 서버 없는 프로젝트는 키 필요한 API를 아예 못 씀(공개 API는 계속 가능). 전자를 택함.
- **선생님 의견과 다르게 정한 3가지**: 생년월일 제공, 제한 API 출시 때 열기, 호출 제한 안 함 → 답장에 이유를 같이 적기로 함.
- **아직 남음**: 제한 API 신청서에 적을 항목(대상·기간 등), API별 표 기한, 만료 전 알림, 졸업 시 메일 차단 확인, 동아리 담당 선생님 정보의 단계.
- 선생님께 물어볼 것: 학교 차원 검토는 어디서 어떻게 받는지, 제한 신청서에 목적 외 필요한 항목.

## Figma 반영 시 임의로 정한 가정 (팀 확인 필요)
- 프로젝트는 활용신청의 "새 프로젝트 만들기"로 생성, 키는 프로젝트의 **첫 승인 때 발급**.
- 재발급한 키는 재발급일부터 60일(예전 디자인 "1년"을 60일로 변경).
- 승인 대기 → "신청 취소", 반려 → "다시 신청", 반려 사유는 신청자에게 보임.
- 분야별 단계 배지는 임시값 — 같은 분야 안에 단계가 섞여(일반 학사 일정=공개, 동아리 구성원=제한) API 표가 나오면 API 줄마다 다시 표시해야 함.
- 화면 변경: 마이페이지 프로젝트 카드(키·만료일·재발급·삭제)·키 갱신, 신청 상태 3가지(승인 완료/대기/반려+사유), admin 활용신청 단계·상태 열과 승인·반려 상세, admin 사용 기록 화면 신설, 엔드포인트 목록 단계 배지, admin 홈 승인 대기 항목. 수정 전 화면은 Figma "📦 보관" 섹션에 복사.
- 일정 판단: 키 갱신 화면·admin 사용 기록 화면은 첫 키 만료가 출시 60일 뒤라 12월로 미룰 수 있으나, 사용 기록 **저장**은 출시 때부터 필요. 리뷰 중인 BE PR(계정당 키 1개 기준)은 프로젝트 구조로 고친 뒤 머지해야 FE 연동이 두 번 되지 않음.
- (Claude 보충) Figma 작업 환경에 Pretendard 글꼴이 없어 일부 텍스트는 Gothic A1로 대체됐고, Pretendard Variable 제목은 못 건드려 배지를 절대 위치로 올림 → 제목이 바뀌면 배지 위치 수동 조정.
