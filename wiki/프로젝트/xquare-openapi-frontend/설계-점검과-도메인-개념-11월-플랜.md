# 설계 점검(애매한 점)·도메인 개념·11월 플랜

학교 안에서만 쓰는 DSM Open API 포털의 현재 디자인(Figma)·프론트·백엔드 명세를 훑어 정책이 애매하거나 과한 부분을 뽑고, 프로젝트에 필요한 API 도메인 개념과 11/30 오픈까지의 플랜을 정리했다. 대부분 **미결정 제안**이며 팀 합의 전이다. (Claude 판단 위주)

## 먼저 정해야 할 것 (기능·정책)
- **활용신청 구조**: 자동승인인데 신청서·심사 화면·개발/운영 계정·API별 신청·"심의유형"·"이용허락범위" 문구는 공공데이터포털 구조를 그대로 가져온 것. 제안: **"API 키 발급" 한 번으로 모든 조회 API 사용**, 신청서는 프로젝트명·용도만, 관리자 화면은 "발급된 키 목록+차단"으로 축소.
- **학생 개인정보 범위**: `@dsm.hs.kr`로 가입하면 누구나 키를 받아 `GET /students`(USER 권한)로 전교생의 이름·**생년월일**·이메일·학번·동아리를 조회 가능. 제안: 생년월일 제거, 목록은 학번·이름·동아리 정도, 약관에 이용 목적, 선생님께 확인.
- **인증 방식 혼재**: Overview는 "모두 JWT", 분배표는 조회=API 키·관리자=JWT, 명세는 급식만 인증 없음. 제안: 공개 문서에는 **조회 API+API 키만** 노출, 등록·수정·삭제·ADMIN 권한은 내부용이라 제외, 급식 무인증 여부 결정.
- **로그인 기준**: Overview 예시는 이메일, 로그인 화면·백엔드는 username. 학교 이메일로 이미 인증하므로 이메일 로그인 통일 제안(XQUARE SSO 여부도 결정 사항).
- **'공지' 이중 의미**: 포털 공지(서비스 공지: 점검·API 변경)와 학교 공지 API(`/notices`) 분리.
- **일정 API에 목록 조회 없음**(등록 POST와 id 단건만) → 월별·기간별 조회 필요. 급식·일정이 NEIS 출처면 관리자 급식 등록·수정 화면이 필요한지 재검토.
- 정리 수준: 429 화면·"일 10,000회"(요청 제한 계획 없음), 문의하기 모달(받을 API 없음→디스코드/메일/GitHub 이슈 링크 추천), API 테스트 기록 저장 위치(키는 발급 때 한 번만 보여 자동 채움 불가), 응답 형식 혼재(`success/data/error` vs 배열+`totalCount`)·학년 값 형식(`"SECOND"` vs `2`)·Base URL 미확정·`/v1` 없음, Figma "삭제 예정" 프레임·임시 보관 프레임 정리.

## 알아 둘 도메인 개념
| 개념 | 요지 |
|---|---|
| Open API vs OpenAPI | 전자는 외부 공개 API, 후자는 명세 파일 형식(Swagger). `openapi.yaml`로 문서를 자동 생성하면 손글씨 문서와 실제 API가 어긋나는 일이 준다 |
| API 키 vs JWT | 키=앱의 출입증(오래 쓰고 서버 보관), JWT=사람의 로그인 표(단기 만료) |
| 키 보안 | DB에는 해시 저장, 재발급 제공, 문서에 "프론트·공개 레포에 키 넣지 말 것" 경고(학생 프로젝트에서 가장 흔한 사고) |
| 401/403/429 | 401=누군지 모름, 403=알지만 권한 없음, 429=호출 과다 |
| 요청 제한 | 학생 코드의 무한 루프 하나가 서버를 멈출 수 있어 키당 간단한 제한 권장 |
| CORS | 브라우저에서 직접 호출하려면 허용 사이트 필요 — 활용신청의 "서비스 URL"을 허용 목록으로 쓰면 입력칸이 의미를 가짐 |
| 버전·호환성 | 응답 필드 변경은 소비자를 깨뜨림 → `/v1`, 변경은 서비스 공지로 사전 안내 |
| 원본 데이터(source of truth) | 급식·일정=NEIS, 나머지=관리자 입력. 섞이면 무엇이 맞는지 불분명 |

## 태스크 분배 점검과 11월 플랜 (~11/1 스프린트 기준)
- 11/1(일) 마감 분배: 프론트 12개(3명, 퍼블리싱)·백엔드 6개(이메일 인증, API 키 발급·재발급, API 키 인증, 활용신청 등록, 학생·교직원 CRUD). 프론트는 적당하나 **admin 홈·공지는 admin 공통 레이아웃이 먼저 끝나야 시작 가능**. 백엔드는 API 키 인증이 모든 조회 API에 걸려 **빡빡**(CRUD 하나는 넘어갈 가능성). 프론트 비밀번호 찾기 화면은 있는데 **백엔드 비밀번호 재설정 API는 분배에 없음**.
- 병목은 백엔드 → 프론트에 일을 더 주고(admin 화면 6종 1인 2종, mock으로 연동 준비), 백엔드 범위는 위 정책 결정(NEIS 수집·활용신청 단순화)으로 축소.
- 플랜: 11/1 마감+결정 회의 → 11/2~8 남은 퍼블리싱, 자습감독·일정·급식 → 11/9~15 인증 흐름 연동+**스테이징 배포**(첫 배포는 일찍 해 봐야 설정 문제를 조기 발견) → 11/16~22 admin 연동·문서 정리 → 11/23~29 QA·베타 → 11/30 오픈. 팀 속도를 모르고 짠 일정이라 스프린트 후 재조정.
- 이 분배를 Linear에 옮기는 시도는 취소됨(동기화 구성으로 전환) — [[Linear-도입과-GitHub-org-연동-Linear-Code-앱]].
