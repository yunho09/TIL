# ToyVillage-Admin-FE 하네스 시스템 구조

이 저장소는 **퍼블리싱**(Figma → 코드)과 **API 연동**(Notion 명세 → 코드) 두 작업을 각각 승인 게이트가 있는 자체 파이프라인(harness)으로 강제한다. 이 페이지는 그 구조 자체(단계·경로 계약·승인 해시 메커니즘)를 정리한 것이고, 실제 진행 상황·이슈별 기록은 [[ToyVillage-Admin-FE/프로젝트-현황]]을 본다.

## 전체 구조

```
harness/
├─ README.md            # 두 하네스로 가는 라우팅 표
├─ no-progress.md        # 공통 반복 중단(loop-guard) 규칙
├─ shared/code-rules.md  # 공통 프론트엔드 코드 규칙
├─ publishing/           # ① Figma → 코드
└─ api/                  # ② Notion 명세 → 코드
```

- durable 입력/승인(`specs/`, `approvals/`)은 **Git 추적**.
- runtime 산출물(`artifacts/`)은 **Git 비추적**, 스크립트 실행 중 자동 생성.

## ① 퍼블리싱 하네스 (Figma → 코드)

```
행동명세 + Figma 입력
→ Figma 추출(figma.txt) / 시나리오 초안 작성
→ 🚦 개발자 승인 (harness:approve)
→ 승인 게이트 검증 (harness:gate)
→ 퍼블리싱(코드 작성)
→ 정적 검증 (harness:verify → lint/typecheck/style-policy/build)
→ 조건부 Playwright 테스트 (verify:e2e)
→ 반복 가드 (no-progress.md)
→ 개발자 육안 확인
```

경로 계약:

| 산출물 | 경로 |
|---|---|
| 입력 spec | `harness/publishing/specs/<feature>.spec.md` |
| 승인 시나리오 | `harness/publishing/approvals/<feature>.scenario-draft.md` |
| 승인 sentinel | `harness/publishing/approvals/<feature>.approved.json` |
| Figma 덤프 | `harness/artifacts/publishing/<feature>.figma.txt` |
| 토큰 산출물 | `harness/artifacts/publishing/<feature>.token-candidates.json` |
| e2e 테스트 | `tests/e2e/<feature>.spec.ts` |

안전장치: 승인 후 시나리오/e2e가 바뀌면 해시 불일치로 STOP. 명세에 없는 실제 API를 임의 연결 금지. 같은 오류·diff 반복 시 중단.

## ② API 하네스 (Notion 명세 → 코드)

```
API 연동 요청
→ API ID로 Notion API 검색 (1건 정확히 일치해야 함)
→ API 상세 명세 조회
→ API Contract 생성 (JSON, source 출처 기록 포함)
→ Contract 검증 (harness:api:validate)
→ 기존 프로젝트 API 구조 분석
→ 구현 계획 작성
→ 테스트 시나리오 작성
→ 🚦 개발자 승인 (harness:api:approve)
→ API 연동 구현
→ 정적 검증
→ Mock 기반 기능 테스트 (verify:api)
→ (별도 승인된 경우만) staging 실서버 테스트 (verify:api:real --confirm-staging)
→ 실패 시 코드 수정
→ 최종 결과 보고
```

경로 계약:

| 산출물 | 경로 |
|---|---|
| 입력 spec | `harness/api/specs/<feature>.spec.md` |
| runtime Contract/계획 | `harness/artifacts/api/<feature>.*` (Git 비추적) |
| 승인본 | `harness/api/approvals/<feature>.*` (Git 추적) |
| 공통 Axios | `src/shared/api/axios.ts` |

원칙: 명세에 없는 Method/Path/권한/타입/enum/응답 필드를 추측하지 않음. 데이터베이스와 상세 페이지 값이 다르면 중단. 실제 서버 요청·Notion 수정은 자동 실행 안 함.

## 공통: no-progress (반복 중단)

`scripts/loop-guard.mjs`가 `harness/artifacts/loop-state.json`에 scope별(`publishing:<feature>` / `api:<feature>`) 상태를 기록한다.

STOP 조건(하나라도 충족 시 중단, 자동 재시도 안 함):
1. `iteration >= 3`
2. 같은 에러 해시 2회 연속
3. 에러가 남아있는 동안 같은 diff 해시 2회 연속

## Figma 덤프란

`<feature>.figma.txt` (경로: `harness/artifacts/publishing/<feature>.figma.txt`)는 Figma MCP의 **`get_design_context`** 호출 결과를 그대로 텍스트로 떠서 저장한 파일이다. RUNBOOK 문서엔 `get_figma_data`로 적혀 있지만 실제로는 이 계약에 그 도구가 없어서 `get_design_context`를 쓴다.

정체는 **Figma 디자인을 흉내 낸 JSX 코드 텍스트**다. Figma에서 눈으로 보이는 레이아웃(배경·패널·텍스트 등)을 MCP 도구가 좌표·색상·텍스트를 그대로 박은 JSX로 자동 변환해 돌려준 것이고, 실제 코드베이스에 쓸 컴포넌트가 아니라 "이 프레임은 이렇게 생겼다"는 기계가 읽은 설계도다. `left-[80px]`, `bg-[#2b6034]` 같은 값이 곧 Figma 캔버스의 실제 좌표/색상값이다.

이걸 그대로 코드로 복붙하면 안 되는 이유: 픽셀 좌표로 하드코딩돼 있고, 반응형도 없고, 프로젝트 디자인 토큰(색상 변수 등)도 안 쓴다. 그래서 다음 단계(`map-tokens.mjs`)가 이 텍스트를 파싱해 "이 색상은 의미 토큰 후보(예: `brand-green`)"인지 "이 px 값은 그냥 직접 구현값"인지 나눠준다.

한 줄 요약: 화면을 캡처한 스크린샷이 아니라, 그 화면이 어떻게 생겼는지를 좌표·색·텍스트째로 옮겨적은 임시 JSX 텍스트 파일 — 이후 단계가 다시 읽어 실제 프로젝트 컴포넌트로 바꿔나가는 원재료.

## 승인 sentinel(`.approved.json`)이란

**퍼블리싱 쪽** — `harness/publishing/approvals/<feature>.approved.json`. `yarn harness:approve <feature> --by <name> --scenarios S1,S2` 실행 시 생성:

```json
{
  "feature": "...",
  "approvedAt": "...",
  "approvedBy": "yunho09",
  "scenarioIds": ["S1", "S2"],
  "scenarioHash": "<sha256>",
  "e2eHash": null
}
```

`e2eHash`는 `--freeze` 이후에만 채워진다.

**API 쪽** — `harness/api/approvals/<feature>.approved.json`. `yarn harness:api:approve`로 생성. 해시가 여러 개(`taskSpecHash`, `contractHash`, `contractMarkdownHash`, `planHash`, `scenarioHash`, `testHash`)라 각각 다른 산출물의 변조를 독립적으로 감지한다.

sentinel의 역할: "이 시점의 파일 내용을 개발자가 승인했다"는 **증거 문서**. 이게 없으면 다음 단계(코드 작성 등)로 진입 자체가 막힌다(`gate-check.mjs`가 강제).

## 승인 해시는 어떻게 동작하나

핵심은 단순하다 — **파일 내용을 SHA-256으로 찍어서 sentinel에 저장 → 나중에 다시 계산해서 비교**.

```js
function sha256(path) {
  return createHash('sha256').update(readFileSync(path)).digest('hex')
}
```

흐름:
1. **승인 시점**: `scenario-draft.md`(또는 spec, contract, plan, test 파일)의 해시를 계산해 `.approved.json`에 박아넣는다.
2. **게이트 체크 시점**(`gate-check.mjs` / `api-gate-check.mjs`): 지금 디스크에 있는 그 파일을 다시 해시 계산해서 sentinel에 저장된 값과 비교한다.
3. **같으면** → 승인 이후 파일이 안 바뀌었다는 뜻 → 통과.
4. **다르면** → 승인 이후 시나리오/명세/계획/테스트가 고쳐졌다는 뜻 → STOP, 재승인 요구.

즉 "체크박스로 승인"이 아니라, **파일의 지문(hash)을 찍어두고 위변조·사후 수정 여부를 기계적으로 검증**하는 방식이다. 사람이 승인한 그 내용 그대로 구현되는 걸 보장하는 게 목적. `freeze`는 e2e 테스트 파일을 최종 확정할 때 그 파일의 해시를 추가로 찍는 단계(`e2eHash`/`testHash`).

## Contract란

**API 하네스 전용 개념**(퍼블리싱엔 없음). `harness/artifacts/api/<feature>.contract.json` (+ 사람이 읽기 좋은 `.contract.md`).

- **정체**: Notion에 적힌 API 명세를 그대로 옮긴 게 아니라, 정해진 JSON 스키마로 고정한 것 — Method, Path, 인증, 헤더, 쿼리 파라미터, Request Body, 성공/에러 응답, 그리고 `source`(어느 Notion 페이지에서 언제 가져왔는지, 검색 결과가 정확히 1건이었는지 등 출처 증명)까지 포함한다.
- **왜 필요한가**: Notion 명세를 읽고 바로 코드를 짜면 안 된다는 원칙(HARNESS.md) 때문. Notion → Contract(검증 가능한 고정 형식) → 승인 → 코드, 이 순서를 강제해서 "명세에 없는 필드/enum을 추측해서 구현"하는 걸 막는다.
- **검증**: `yarn harness:api:validate <feature>`가 Contract가 스키마를 만족하는지(필수 필드, `없음`/`명세 누락` 구분, 에러 응답 최소 1개 등) 체크한다.
- **승인 이후**: Contract 파일이 `.approved.json`의 `contractHash`/`contractMarkdownHash`로 고정되고, 이후 구현·테스트는 이 Contract만을 기준으로 삼는다 — Notion이 나중에 또 바뀌어도 이미 승인된 Contract는 재승인 전까지 그대로 유지된다.

## 핵심 공통 원칙

- 승인(`approved.json`)이 있어야만 다음 단계 진행 — durable 승인 없이 구현 착수 안 함.
- 승인 후 기준 파일이 바뀌면 재승인 필요(해시 불일치로 게이트 STOP).
- 퍼블리싱에서는 실제 API 임의 연결 금지, API 작업에서는 Figma 퍼블리싱 재수행 금지.
- 두 하네스 모두 agent-agnostic — Claude Code든 다른 코딩 에이전트든 동일 RUNBOOK을 따른다.

## 한 줄 요약

Figma 덤프 = 원본 캡처 스냅샷, Contract = 원본(Notion)을 검증 가능한 고정 JSON으로 재구성한 것, 승인 sentinel = "이 파일들을 이 시점에 승인했다"는 기록, 승인 해시 = 그 기록이 이후 변조되지 않았는지 SHA-256으로 자동 검증하는 장치.
