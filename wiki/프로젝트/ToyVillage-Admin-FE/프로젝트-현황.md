# ToyVillage-Admin-FE 프로젝트 현황

관리자 프론트엔드 저장소. Figma 디자인을 코드로 옮기는 작업을 **자체 harness 파이프라인**(`.claude/skills/publishing`)으로 게이트 처리한다. 진실의 원천은 `harness/publishing/RUNBOOK.md` / `design-rules.md`이고, 이 페이지는 그 구조에서 재사용 가치가 있는 부분만 요약한다.

## 퍼블리싱 harness 구조

파이프라인은 ①추출 → ②시나리오 승인(**사람**) → ③퍼블리싱 → ④검증 루프 → ⑤e2e 변환 → ⑥… → ⑦육안 확인(**사람**) 순서다. AI는 ②·⑦ 게이트를 자동 통과시키지 않는다.

- **`harness/publishing/specs/`** — 화면 스펙. AI가 최신 Figma 반영을 위해 갱신 가능.
- **`harness/publishing/approvals/`** — 승인 상태(시나리오 초안 + `*.approved.json`). AI가 **직접 수정 금지**, 공식 스크립트(`node scripts/approve.mjs`)로만 바뀐다.
- **게이트 판정**: `approved.json`의 `scenarioHash`(승인된 시나리오 초안의 해시)와 `e2eHash`(e2e 테스트 파일의 해시)가 각각 현재 파일과 일치해야 `yarn harness:gate <feature>`가 `valid: true`를 낸다. 둘 중 하나라도 어긋나면(초안을 고쳤는데 재승인 안 함, e2e를 고쳤는데 재freeze 안 함) 게이트가 막힌다.
- **시나리오를 다시 승인하면 `e2eHash`가 `null`로 초기화**된다 — 재승인 직후엔 `e2eFrozen: false` 상태이고, 구현 후 e2e를 승인 시나리오 기준으로 다시 변환하고 `--freeze`해야 게이트가 완전히 닫힌다.
- **공유 컴포넌트 변경 시 영향 범위를 먼저 확인**해야 한다 — `DataTable`은 5개 테이블(공지·자료실·예약·업무 등)이 공유하고, `TaskPriorityBadge`/`TaskStatusBadge`는 `task-report` spec과 공유라, 한 spec의 요구로 전역 기본값을 바꾸면 다른 화면이 깨질 수 있다. `design-rules.md §4` 기준 이런 변경은 중간 게이트 승인 범위. (실제로 업무관리 목록의 우선순위 배지를 pill 모양으로 바꾸자 `task-report`도 같이 바뀌어버려, `TaskReportPriorityBadge`를 신설해 분리한 사례가 있다.)
- **`approve.mjs`는 `approvals/`에 이미 있는 파일을 승인할 뿐, 그 내용이 최신 초안인지는 검증하지 않는다.** 새로 쓴 시나리오 초안은 `harness/artifacts/publishing/<feature>.scenario-draft.md`에 있는데, 이걸 `cp`로 `approvals/`에 옮기는 걸 빼먹고 `approve.mjs`만 돌리면 게이트는 `valid: true`로 뜨지만 실제로는 **옛(폐기된 파일 기준) 초안에 새 시나리오 id만 얹혀 승인된, 의미 없는 통과**가 된다. 이 실수가 한 세션에서 세 번 반복됐다 — cp와 approve를 한 블록으로 묶어 안내하면 사람이 cp 부분만 빠뜨리기 쉬우므로, 재승인을 요청할 땐 `cp` 명령과 `approve.mjs` 명령을 분리해서 순서대로 안내하고 실행 여부를 따로 확인하는 게 안전하다.

## 커밋 컨벤션

`<type>: <한국어 설명>` 형식, 스코프 없음, 본문·트레일러 없이 **제목 한 줄만**(예: `feat: DataTable에 표 외형 옵션(appearance) 추가`). 원자 단위로 나눈다 — 예: DataTable 옵션 API 추가, 표 적용, 탭/버튼 적용, 게이트 해시 재freeze, spec 재작성, 시나리오 재승인을 각각 별도 커밋으로.

이미 원격에 push된 커밋을 `--amend`로 고치면(예: 실수로 본문이 들어간 걸 제목 한 줄로 정리) 로컬과 원격이 같은 내용의 다른 SHA로 갈라진다 — GitHub에는 같은 커밋이 두 개처럼 보이고, 정리하려면 `git push --force`가 필요하다. 같은 브랜치를 이미 pull 받은 사람이 있으면 `git fetch && git reset --hard origin/<브랜치>`로 맞춰야 한다.

**(2026-09-13 확정) 제목의 서술어는 명사형으로 끝낸다.** `~한다` 종결어미(예: `화살표를 그린다`)가 아니라 `추가`/`제거`/`수정` 같은 명사형(예: `화살표 추가`)으로 쓴다. 이미 push된 커밋이 이 문체를 어겨서 `--amend` + `git push --force-with-lease`로 교정한 사례가 있다.

## 업무 목록 필터·페이지네이션 구현 패턴 (`TaskListPage.tsx`)

- **탭 = 문자열, 상태는 룩업 테이블로 매핑**: `tabStatuses: Record<string, TaskStatus | null>`로 탭 이름을 곧바로 상태 키로 쓴다. `null`은 "필터 없음"(전체 업무 탭). 탭 표시 자체는 문자열만 올려주는 `CategoryTabs`(순수 표시용)가 담당.
- **필터링 파이프라인은 `useMemo` 3단 분리**: `allTasks → items(resolveTaskStatus로 표시용 status 부여) → filtered(tabStatuses 일치 여부) → tasks(페이지 slice)`. 각 단계가 별도 `useMemo`라 탭만 바꾸면 `items` 재계산 없이 `filtered`부터 다시 돈다.
- **`today`를 한 번만 `useMemo`로 잡아 필터와 표에 동일하게 전달**: 탭 필터의 기준일과 `TaskTable`의 기한 표시(`today` prop)가 같은 값을 쓰도록 해서, 자정을 넘겨 렌더가 다시 일어나도 필터 기준과 화면 표시가 어긋나지 않게 한다.
- **탭 전환 시 페이지 리셋은 `useEffect`가 아니라 "렌더 중 상태 보정" 패턴**: `const [prevActive, setPrevActive] = useState(active); if (prevActive !== active) { setPrevActive(active); setPage(1) }`. `page` state 자체는 건드리지 않고 `currentPage = Math.min(page, pageCount)`로 clamp하기 때문에, 삭제로 목록이 줄어 페이지 수가 감소해도 빈 화면이 뜨지 않는다.
- 날짜 비교는 `dueDate < today`처럼 `YYYY-MM-DD` 문자열 사전순 비교로 처리 — `Date` 객체 변환 없이 동작한다(`resolveTaskStatus`, `src/entities/task/model/status.ts:16`).

## 업무지시(task) API 연동 착수 (2026-09-09)

퍼블리싱과 별개 harness(`.claude/skills/api`, `harness/api/RUNBOOK.md` ①~⑬ 단계)로 진행. ①spec 작성 → ②③Notion 원문 수집 → ④Contract 생성 → ⑤validate → ⑥기존 구조 분석 → ⑦구현계획·테스트시나리오 → ⑧개발자 승인 → ⑨구현 순서이고, **개발자 승인(⑧) 전에는 API 코드·테스트를 작성하지 않는다.**

- **Notion API 명세서가 세션 도중 DB째로 여러 번 교체됐다** — 처음 조회한 `API 명세서 (1)`은 이미 archived(삭제)된 DB였고, 라이브는 이름이 비슷한 `API 명세서 토이빌리지`였다. 이후로도 라이브 DB 자체가 통째로 새 사본으로 두 차례 더 교체됨(콘텐츠는 유지, 페이지 URL만 갱신). → **spec/Contract 작업 시작 전 매번 "지금 조회한 DB가 살아있는(비-archived) 최신 DB인지"부터 확인해야 한다.** 이름이 같아 보여도 다른 데이터베이스일 수 있다.
- **최종 확정된 API 설계**:
  - `GET /team/tree` (`TEAM_QUERY_TREE`, 신설) — `{ totalMemberCount, teams: [{ id, name, memberCount, members: [{id, name, position}] }], unassigned: {...} }`. 담당자 선택 트리(팀별 그룹 + 3상태 체크박스 + 직급 표시)의 데이터 소스. `position`은 `null` 가능.
  - `GET /tasks/{id}` 응답에 `assignees: [{id, name, position}]` 추가 — 수정 폼이 기존 담당자 선택을 복원하는 데 필요. `POST/PUT /tasks`는 `assigneeIds: number[]`로 저장.
  - 상태 enum이 `IN_PROGRESS`/`COMPLETED`/`EXPIRED`로 확정(서버가 계산해서 내려줌: `COMPLETED`=담당자 전원 APPROVED, `EXPIRED`=미완료+기한초과) — 클라이언트에서 재현 불가능한 조건이라 기존 `resolveTaskStatus`(완료기한 기준 파생)는 **제거 대상**, 코드의 `DONE`→`COMPLETED`, `OVERDUE`→`EXPIRED` 개명 필요.

## 업무지시(task) API 연동 — 승인·구현·검증 완료 (2026-09-10)

⑧ 개발자 승인 → ⑨ 구현 → ⑩ 정적 검증 → ⑪ Mock 테스트까지 5개 feature(`team-query-tree`/`task-query-all`/`task-query`/`task-create`/`task-update`) 전부 완료. 구현 순서는 의존 관계상 `team-query-tree`(담당자 id 유일 출처) → `task-query-all`(상태 모델 확정) → `task-query`(수정 폼 초기값) → `task-create` → `task-update`.

**승인 전 확정한 설계 결정 4가지** (모두 코드에 반영됨):
1. **상태 값 개명**: `DONE→COMPLETED`, `OVERDUE→EXPIRED`. 서버가 세 상태를 모두 계산해 내려주므로 `resolveTaskStatus`·`taskToday`를 삭제했고, `entities/task-report`의 mock `taskStatus` 12곳까지 개명이 파급됨. 목록의 완료기한 위험색 표시는 유지하되 기준일 계산은 `TaskTable` 내부 순수 헬퍼로 옮김.
2. **`src/entities/team` 신설**: entities끼리 import하지 않는 이 저장소 규칙 때문에 팀 트리(`GET /team/tree`)를 task entity에서 분리. 그 여파로 `findTaskMember`가 사라지고 `task-report`의 mock이 `assigneeName`을 직접 가짐(mock 내부에서만 닫히는 변경).
3. **`전체 직원` 체크박스 3상태 판정 분리**: 표기 숫자는 `totalMemberCount`를 쓰되, 체크 판정 분모는 실제로 렌더된 직원 수로 따로 둠. `totalMemberCount`가 미배정 인원을 포함하는지 여부가 백엔드 미확인 상태라, 두 값을 하나로 묶으면 "전체 선택"이 영원히 `mixed`(부분 선택) 상태에 갇히는 걸 막기 위한 안전장치. 두 값이 실제로 같으면 동작 차이 없음.
4. **`AttachmentField` 확장**: 수정 화면이 기존 첨부의 `fileKey`를 재전송해야 하는데 기존 shared 컴포넌트는 파일명만 노출했음. optional prop `initialFiles`/`onFileItemsChange` 2개를 추가하고 실제 업로드 로직은 `TaskForm`(도메인 레이어)이 담당 — shared 컴포넌트는 도메인에 의존하지 않는 원칙 유지, 기존 호출부는 영향 없음.

**백엔드 확인으로 해소된 사항**: `TASK_QUERY.assignees`가 담당자 **전원** 반환임을 개발자가 직접 확인. 일부만 왔다면 수정 화면이 담당자를 복원 못한 채 `PUT` 전체 교체로 담당자가 유실되는 위험이 있었음 — 확정으로 문서(spec/Contract/final-report) 갱신 후 `task-query`/`task-update` 재승인·재동결(`--freeze`)함.

**검증 결과**:
- `harness:api:validate`·`gate`·`policy`(task-delete 포함 6건) 전부 통과, `yarn lint`/`typecheck`/`build` 통과.
- 신규 Mock 시나리오 70건(12·12·14·15·17) 전부 통과.
- 퍼블리싱 회귀: task-list 24·task-detail 19·task-create 20·task-edit 16 통과. 공용 route mock(`tests/e2e/support/task-api.ts`)으로 교체.
- `tests/e2e/api/task-delete.spec.ts`도 함께 손봄 — 상세 조회가 mock에서 API로 바뀌고 삭제 UI가 케밥 메뉴로 옮겨져 진입 경로가 깨져 있었음(이전 퍼블리싱 변경 때부터의 기존 실패). 경로만 고치고 `--freeze` 재동결, 9건 통과.

- **배럴 import 크래시 3개 파일 수정·커밋 완료**: `close-schedule-create`/`close-schedule-edit`/`operating-hours-edit`가 엔티티 배럴을 거치며 axios를 끌어와 수집조차 안 되던 문제. 원인·해결은 [[배럴-Import-함정]] 참고. 이번 파트 범위 밖이지만 "이미 했으니 유지"로 결정, 해당 3개 spec도 함께 재freeze.
- **`task-report` S16 근본 원인 확정**: 이번 파트가 만든 문제가 아니라 `abfd491`(2026-09-08, "업무 상세를 읽기 전용 화면으로 신설")에서 `TaskReportSummaryCard`로 재설계하며 `업무 보고 상세조회` 버튼이 사라진 것이 원인. 동결 스펙은 여전히 그 문구를 찾아 타임아웃한다. 스펙 헤더 규칙(`실패 시 코드를 수정한다`)상 코드 쪽이 접근성 이름을 복구해야 한다(예: 버튼에 `aria-label` 추가) — 아직 미조치. `mockTaskApi(page)` 추가는 #58이 한 게 맞지만, 이는 상세 화면이 API 연동으로 바뀌며 필요해진 별개 조치이고 넣어도 낡은 locator 자체는 여전히 실패한다.
- **⚠️ freeze로 실패가 "승인된 상태"로 굳어짐**: 개발자 지시로 8개 feature(`task-list`/`task-create`/`task-detail`/`task-edit`/`task-report`/`close-schedule-create`/`close-schedule-edit`/`operating-hours-edit`)를 일괄 재freeze했다. 재freeze 전에는 e2eHash 불일치로 게이트가 아예 막아 실패를 가려줬지만, freeze 후에는 게이트는 통과하고 테스트만 실패로 뜨는 상태로 바뀐다 — `task-report`는 게이트 통과·테스트 1건 실패(S16)로 남아 있다.
- **백엔드 미배포를 실제 토큰으로 최종 확인**: 발급받은 액세스 토큰(만료 1시간)으로 스테이징을 직접 호출. `GET /tasks`가 토큰 없이 403(인증 실패), 토큰 있으면 500으로 바뀜(인증은 통과, 경로가 없음). **이 서버는 존재하지 않는 경로도 404가 아니라 500을 반환**한다(`GET /definitely-not-real`도 동일 500) — "미배포"와 "서버 오류"가 응답만으로 구분되지 않는 함정이 있어, 배포 여부 확인은 항상 살아있는 다른 엔드포인트(`/documents`·`/notice`·`/close-day`·`/reservation`·`/team` = 200)와 대조해서 판단해야 한다. `/team/tree`는 400인데, 이는 `/team/{id}`가 `tree`를 정수 id로 파싱 시도해 나는 것(`/team/abc`와 동일 응답)이지 별도 라우트가 존재하는 게 아니다 — 승인된 contract의 `/team/tree` 경로가 실제 배포와 맞는지 **머지 후 백엔드에 재확인 필요**.
- **커밋을 기능별 12개로 분리**: API 클라이언트·mock 헬퍼·스펙 5개·배럴 수정을 각각 별도 커밋으로 나눴다. 단, **`model/types.ts`의 상태 enum 변경이 `mock.ts`를 거쳐 5개 화면에 동시에 물려 있어 `src/` 마이그레이션 자체(`feat: 업무지시 목록·상세·생성·수정·삭제를 API 연동으로 교체하고 목 제거`)는 더 쪼갤 수 없었다** — 구/신 타입을 공존시키는 과도기 코드를 넣는 게 오히려 더 지저분해져 하나의 커밋으로 유지하기로 결정. `entities/team`, `shared/ui/AttachmentField`처럼 단독으로 typecheck되는 조각만 별도 커밋으로 먼저 뗄 수 있었다.

## 목록 스키마 불일치·케밥 메뉴 클리핑·업무보고 연동·develop 대형 머지 (2026-09-12)

## 개체관리(#89) API 연동 설계 조사 — 코드 작성 없이 계획만 (2026-09-16)

PR #88 머지 후 `#89/object-management-api` 브랜치를 `origin/develop` 기준으로 새로 생성(미push). "개발하지 말고 방안만 생각해보라"는 명시적 지시로 이번 세션은 조사·설계·백엔드 질문 정리만 하고 **코드는 한 줄도 안 바꿈**.

- **현재 mock 구조 진단**: 종·개체·관찰 전부 localStorage 기반, 목록은 서버가 아니라 **브라우저에서 전량 필터·정렬·페이지네이션**(`tablePage`, 10행 고정). 사진은 실제로 업로드되지 않고 파일명만 저장하며 화면엔 항상 같은 샘플 이미지(카피바라)가 뜬다. 관찰 첨부의 새 `File`은 전송 전에 버려진다(`ObservationForm.tsx`의 `toUpdateObservationInput`이 `fileKey`만 넘김). API 연동용 harness spec/e2e는 아직 하나도 없다.
- **참고할 기존 연동 패턴**: `entities/task/api/taskApi.ts` 구조(호출+런타임 응답 검사+DTO→모델 변환을 한 파일에), 목록 페이지네이션 응답 형태가 기능마다 다름(`{tasks, totalPageSize}` vs Spring Page `{content, totalPages}`), 파일 업로드는 `POST /file`(multipart, 1개씩) → `{fileKey}` 뒤 폼이 그 키를 배열로 모아 보내는 방식(`TaskForm.tsx` 패턴), 쿼리 키 factory는 개체관리에만 있고 다른 기능은 인라인 배열.
- **Swagger 대조 후 확정된 설계 결정들**:
  - API는 App 그룹 `animal-manage-controller` 하나(`/animal-manage/**`)를 쓴다. Web 그룹의 `/animal` CRUD는 필드 구성(`popularAnimal` 등)으로 봐서 홈페이지 동물 소개용이라 제외.
  - **사진/첨부 URL 문제는 해결됨**: Notion `file-create` 명세에 "fileKey를 base URL 뒤에 붙이면 조회 가능"이라고 적혀 있어, base URL 값 하나만 받아 환경변수(`.env`에 현재 `VITE_API_BASE_URL`만 있음)로 추가하면 된다.
  - **검색 파라미터**: `GET /animal-manage/kind`(종 목록)·`GET /kind/{id}/animal`(종 상세 개체 표)에 `keyword` 파라미터가 없어 서버 페이지네이션과 상충하던 문제 — 백엔드가 추가해주기로 확정(요청 문구를 backend-questions에 정리).
  - **정렬 UI는 백엔드에 sort 파라미터를 요청하는 대신 화면에서 제거하기로 결정**(디자인 정리): 종 목록·종 상세 개체 표의 최신순/오래된순 버튼을 없앰. 목록 순서는 서버 기본 정렬을 그대로 따른다.
  - **페이지네이션은 1부터**(업무지시 목록의 `GET /tasks`가 0부터였던 것과 다름 — 화면 페이지 번호를 그대로 보내면 됨, `page-1` 변환 코드를 복사하면 한 페이지씩 밀림).
  - **응답 코드**: GET 200, POST 201(사용자 확인).
  - **삭제 시 연쇄**: 종 삭제 → 개체·관찰 기록도 함께 삭제됨(사용자 확인). 개체 삭제 시 관찰 기록 연쇄 삭제 여부는 미확인으로 남음.
  - **PATCH는 전체 교체 방식으로 확정**(사용자 확인) — 관찰 수정의 `fileKeys`는 화면에 남은 첨부 전체 목록을 보내야 하고, 목록에서 뺀 파일은 서버가 삭제 처리한다. 새로 추가한 파일만 `POST /file`로 순서대로 올려 기존 `fileKey`와 화면 순서대로 합쳐 보내는 방식으로 프론트를 바꿔야 함(지금은 새 File을 버림).
  - **법정지정분류(id/이름 불일치) 최종 설계**: 상세 조회는 이름 배열만 주고 등록/수정은 id 배열을 받아 서로 안 맞는 문제를, 백엔드에 id 포함을 요청하는 대신 **이름으로 id를 역매칭**하는 프론트 방식으로 해결(중복 이름은 프론트의 기존 "이미 있는 분류입니다" 중복 검사로 사실상 막힘). **서버가 기본값을 내려주지 않는 것도 확인**돼, 화면에 고정 노출하는 기본 3개(`지정관리 야생동물`/`멸종위기 야생생물 I급`/`천연기념물`)는 **종 저장 시점에 서버 목록에 없으면 프론트가 먼저 `POST`로 등록**하고 그 id를 쓰기로 결정. 직접 추가·삭제(`DELETE`)는 폼 저장과 무관하게 **즉시 서버에 반영**되고, 삭제는 그 항목을 쓰던 **모든 종에서 함께 빠진다**(사용자 확인, 별도 "사용 중 삭제 불가" 처리 불필요).
  - **최종 남은 백엔드 질문은 1개**로 좁혀짐: `POST /animal-manage/legal-status`가 같은 이름(`kind`) 중복 등록을 막아주는지.
- **확정된 디자인 작업 목록(Figma 수정 3 + 신규 3)**: ① 종 목록 정렬 버튼 제거 ② 종 상세 개체 표 정렬 버튼 제거 ③ 법정지정분류 기본 3개 pill의 `✕` 제거(Figma 원본엔 그려져 있음) / ④ 법정지정분류 삭제 확인 모달(전체 종에서 함께 빠진다는 안내) ⑤ 법정지정분류 추가·삭제 실패 표시 ⑥ 종 목록·상세·개체 상세·관찰 상세/수정의 조회 실패(서버 오류) 상태 — mock 시절엔 실패가 사실상 없어 이 상태 자체가 화면에 없었음.

## 첨부파일 다운로드(#71) 완료 (2026-09-16)

2026-09-14에 진단만 하고 끝났던 [[크로스오리진-파일-다운로드-a-download-무시]] 버그를 실제로 고치고 머지까지 완료했다(PR #100, 머지 커밋 `3545fb9`).

- **적용 범위**: 처음엔 조회 전용 화면(업무 상세·업무보고 상세)만 고쳤다가, 사용자 요청으로 수정 화면(업무 수정 `AttachmentField`, 자료실 `ResourceUploadField`, 공지 수정 `NoticeForm`)까지 같은 세션에서 확장했다. **관찰·개체 폼은 제외** — 아직 mock 데이터라 `fileKey`가 가짜이고, 같은 컴포넌트(`AttachmentField`)를 쓰는 관찰 수정 e2e가 동결(freeze)돼 있어 지금 공통 코드를 바꾸면 그 테스트가 깨진다. `#89`가 관찰을 실 API로 옮긴 뒤 `storedFiles` prop만 켜면 이어서 고칠 수 있다.
- **공용 인증 axios 대신 `fetch` 사용**: CDN 파일 서버 호출에 공용 인증 인스턴스를 쓰면 토큰이 새고 CDN의 403이 세션 만료로 오인될 수 있어 `fetch`로 우회했다 — 근거와 일반 패턴은 [[공용-인증-axios-외부도메인-토큰유출]] 참고. `harness/shared/code-rules.md` 4번(raw fetch 금지)에 이 예외를 명시했다.
- **e2e 오리진 검증**: mock이 경로만 확인해 서버가 바뀌어도 안 걸리던 구멍을 CodeRabbit 리뷰로 발견·수정 — 자세한 내용은 [[Playwright-mock-오리진-미검증]] 참고.
- **스테이징 실측 검증**(모두 CDN 원본과 바이트까지 일치): 업무 상세·업무 수정 `접근제어자.pptx`(56,894B), 자료실 pdf(322,411B), 공지 png(189,666B, `advil1.png`). 업무 #1의 기존 첨부 `휴관안내.jpg`가 처음엔 이상해 보였지만, CDN에 올라간 원본 자체가 예전 버그가 만든 17바이트 텍스트라 그대로 받아진 것일 뿐 다운로드 경로 문제가 아님을 확인했다.
- **커밋 메시지 재작성 후 강제 푸시**: 사용자 요청으로 이미 push된 커밋 12개의 메시지를 쉬운 말로 전부 바꿔야 해서 `filter-branch`로 재작성 후 `--force` 푸시했다. **커밋 해시가 전부 바뀌므로**, 그 이전에 CodeRabbit 리뷰 답글에 남겨뒀던 옛 해시도 새 해시로 다시 고쳐야 했다. `filter-branch`가 남기는 백업 ref(`refs/original/...`)도 정리 대상이다.
- **CodeRabbit 리뷰 답글 관례**: 리뷰 대응 답글에는 설명을 달지 않고 **커밋 해시만** 남기기로 함(사용자 지시, 이후 세션에도 적용).
- **배포 환경 미해결 사항**: `VITE_FILE_BASE_URL=https://cdn.toyvillage.kr`을 배포 환경변수에 추가해야 한다 — 빠지면 화면은 뜨지만 다운로드만 실패하고 콘솔에 사유가 남는다. 이건 AI가 못 하는 부분으로 남겨둠.
- 머지 후 `#71/attachment-download` 브랜치는 로컬·원격 모두 삭제.
