# ToyVillage-Admin-FE 프로젝트 현황

관리자 프론트엔드 저장소. Figma 디자인을 코드로 옮기는 작업을 **자체 harness 파이프라인**(`.claude/skills/publishing`)으로 게이트 처리한다. 진실의 원천은 `harness/publishing/RUNBOOK.md` / `design-rules.md`이고, 이 페이지는 그 구조에서 재사용 가치가 있는 부분만 요약한다.

## 퍼블리싱 harness 구조

파이프라인은 ①추출 → ②시나리오 승인(**사람**) → ③퍼블리싱 → ④검증 루프 → ⑤e2e 변환 → ⑥… → ⑦육안 확인(**사람**) 순서다. AI는 ②·⑦ 게이트를 자동 통과시키지 않는다.

- **`harness/publishing/specs/`** — 화면 스펙. AI가 최신 Figma 반영을 위해 갱신 가능.
- **`harness/publishing/approvals/`** — 승인 상태(시나리오 초안 + `*.approved.json`). AI가 **직접 수정 금지**, 공식 스크립트(`node scripts/approve.mjs`)로만 바뀐다.
- **게이트 판정**: `approved.json`의 `scenarioHash`(승인된 시나리오 초안의 해시)와 `e2eHash`(e2e 테스트 파일의 해시)가 각각 현재 파일과 일치해야 `yarn harness:gate <feature>`가 `valid: true`를 낸다. 둘 중 하나라도 어긋나면(초안을 고쳤는데 재승인 안 함, e2e를 고쳤는데 재freeze 안 함) 게이트가 막힌다.
- **시나리오를 다시 승인하면 `e2eHash`가 `null`로 초기화**된다 — 재승인 직후엔 `e2eFrozen: false` 상태이고, 구현 후 e2e를 승인 시나리오 기준으로 다시 변환하고 `--freeze`해야 게이트가 완전히 닫힌다.
- **공유 컴포넌트 변경 시 영향 범위를 먼저 확인**해야 한다 — `DataTable`은 5개 테이블(공지·자료실·예약·업무 등)이 공유하고, `TaskPriorityBadge`/`TaskStatusBadge`는 `task-report` spec과 공유라, 한 spec의 요구로 전역 기본값을 바꾸면 다른 화면이 깨질 수 있다. `design-rules.md §4` 기준 이런 변경은 중간 게이트 승인 범위. (실제로 업무관리 목록의 우선순위 배지를 pill 모양으로 바꾸자 `task-report`도 같이 바뀌어버려, `TaskReportPriorityBadge`를 신설해 분리한 사례가 있다.)
- **`harness/publishing/specs/*.spec.md`(화면 스펙 산문 설명)는 게이트 해시 보호 대상이 아니다.** 게이트가 해싱하는 건 `approvals/`의 승인된 시나리오 초안과 실제 e2e 테스트 파일뿐이라, spec.md에 적힌 "무엇을 어떻게 모킹하는지"(예: localStorage 키, 후보 엔드포인트) 같은 서술은 실제 구현이 바뀌어도(예: localStorage 모킹 → `page.route` 가짜 서버 전환) 자동으로는 안 걸리고 게이트는 계속 `valid`로 뜬다. 이런 드리프트는 CodeRabbit 같은 외부 리뷰가 지적해야 드러나는 경우가 있다(2026-09-17, 이슈 #103 세션에서 `resource-edit.spec.md`가 옛 localStorage 모킹 설명을 그대로 갖고 있다가 지적받음).
- **기능을 제거하면서 e2e 파일만 지우고 명세·승인 기록을 안 지우면 게이트가 영구히 막힌다.** e2e가 없어지면 `e2eHash`를 계산할 대상이 없어 `yarn harness:gate <feature>`가 항상 실패 상태로 고정된다. 상세를 수정 폼으로 대체하거나(`reservations-detail`) 양식 수정 기능 자체를 없앤(`work-log-form-edit`) 경우 모두 이 패턴이었다 — 코드가 망가진 게 아니라 harness 쪽 파일 정리를 안 한 것. 해결은 안 쓰는 spec·approval을 지우거나(기능이 완전히 사라졌으면), 그 화면이 다른 디자인으로 다시 생겼으면(예: yot에 읽기전용 상세가 다시 생긴 `reservations-detail`) 새 spec으로 다시 만드는 것 중 하나를 정해야 한다(2026-09-17, 이슈 #80).
- **`approve.mjs`는 `approvals/`에 이미 있는 파일을 승인할 뿐, 그 내용이 최신 초안인지는 검증하지 않는다.** 새로 쓴 시나리오 초안은 `harness/artifacts/publishing/<feature>.scenario-draft.md`에 있는데, 이걸 `cp`로 `approvals/`에 옮기는 걸 빼먹고 `approve.mjs`만 돌리면 게이트는 `valid: true`로 뜨지만 실제로는 **옛(폐기된 파일 기준) 초안에 새 시나리오 id만 얹혀 승인된, 의미 없는 통과**가 된다. 이 실수가 한 세션에서 세 번 반복됐다 — cp와 approve를 한 블록으로 묶어 안내하면 사람이 cp 부분만 빠뜨리기 쉬우므로, 재승인을 요청할 땐 `cp` 명령과 `approve.mjs` 명령을 분리해서 순서대로 안내하고 실행 여부를 따로 확인하는 게 안전하다.

## 커밋 컨벤션

`<type>: <한국어 설명>` 형식, 스코프 없음, 본문·트레일러 없이 **제목 한 줄만**(예: `feat: DataTable에 표 외형 옵션(appearance) 추가`). 원자 단위로 나눈다 — 예: DataTable 옵션 API 추가, 표 적용, 탭/버튼 적용, 게이트 해시 재freeze, spec 재작성, 시나리오 재승인을 각각 별도 커밋으로.

이미 원격에 push된 커밋을 `--amend`로 고치면(예: 실수로 본문이 들어간 걸 제목 한 줄로 정리) 로컬과 원격이 같은 내용의 다른 SHA로 갈라진다 — GitHub에는 같은 커밋이 두 개처럼 보이고, 정리하려면 `git push --force`가 필요하다. 같은 브랜치를 이미 pull 받은 사람이 있으면 `git fetch && git reset --hard origin/<브랜치>`로 맞춰야 한다.

**(2026-09-13 확정) 제목의 서술어는 명사형으로 끝낸다.** `~한다` 종결어미(예: `화살표를 그린다`)가 아니라 `추가`/`제거`/`수정` 같은 명사형(예: `화살표 추가`)으로 쓴다. 이미 push된 커밋이 이 문체를 어겨서 `--amend` + `git push --force-with-lease`로 교정한 사례가 있다.

**(2026-09-17 확정) PR 제목은 브랜치명 그대로 쓴다.** 개발자 지시로 확정 — PR을 열 때 내용 요약 제목(예: `[FIX] 로그인 화면 yot 디자인 반영`)을 붙였다가 브랜치명(`#79/login-design`)으로 다시 고친 사례가 있다.

## 이슈 #134 — `/login` 등 하위 경로 새로고침 404 (Cloudflare Workers SPA fallback)

실서버(`admin.toyvillage.kr`)에서 `/`는 정상이지만 `/login`을 직접 열거나 새로고침하면 404가 나는 문제. 원인은 프론트 코드가 아니라 Cloudflare Workers 배포에 SPA fallback이 꺼져 있던 것(자세한 원인·판별법·해결법은 [[Cloudflare-Workers-SPA-fallback-404]] 참고). 저장소에는 배포 설정이 전혀 없어 대시보드에서 수동 연결된 상태로 추정. 이슈 #134 등록 후 저장소 루트에 `wrangler.jsonc`(Worker 이름 `toyvillage-admin-fe-stag`, `not_found_handling: "single-page-application"`) 추가, 로컬 테스트로 생긴 `.wrangler/`를 `.gitignore`에 추가, PR #135(`#134/spa-fallback` → develop) 생성까지 완료. `wrangler dev`로 `/login`·`/dashboard` 200 확인, `wrangler deploy --dry-run` 통과 확인. 머지 전까지는 실서버가 계속 404이며, 머지 후 대시보드 **Settings → Build**의 배포 명령이 `npx wrangler deploy`인지 확인이 필요(다른 명령이면 이 설정 파일이 반영 안 됨) — 이 부분은 사용자 확인 대기 중.

## 업무 목록 필터·페이지네이션 구현 패턴 (`TaskListPage.tsx`)

- **탭 = 문자열, 상태는 룩업 테이블로 매핑**: `tabStatuses: Record<string, TaskStatus | null>`로 탭 이름을 곧바로 상태 키로 쓴다. `null`은 "필터 없음"(전체 업무 탭). 탭 표시 자체는 문자열만 올려주는 `CategoryTabs`(순수 표시용)가 담당.
- **필터링 파이프라인은 `useMemo` 3단 분리**: `allTasks → items(resolveTaskStatus로 표시용 status 부여) → filtered(tabStatuses 일치 여부) → tasks(페이지 slice)`. 각 단계가 별도 `useMemo`라 탭만 바꾸면 `items` 재계산 없이 `filtered`부터 다시 돈다.
- **`today`를 한 번만 `useMemo`로 잡아 필터와 표에 동일하게 전달**: 탭 필터의 기준일과 `TaskTable`의 기한 표시(`today` prop)가 같은 값을 쓰도록 해서, 자정을 넘겨 렌더가 다시 일어나도 필터 기준과 화면 표시가 어긋나지 않게 한다.
- **탭 전환 시 페이지 리셋은 `useEffect`가 아니라 "렌더 중 상태 보정" 패턴**: `const [prevActive, setPrevActive] = useState(active); if (prevActive !== active) { setPrevActive(active); setPage(1) }`. `page` state 자체는 건드리지 않고 `currentPage = Math.min(page, pageCount)`로 clamp하기 때문에, 삭제로 목록이 줄어 페이지 수가 감소해도 빈 화면이 뜨지 않는다.
- 날짜 비교는 `dueDate < today`처럼 `YYYY-MM-DD` 문자열 사전순 비교로 처리 — `Date` 객체 변환 없이 동작한다(`resolveTaskStatus`, `src/entities/task/model/status.ts:16`).

## 업무지시(task) API 연동 착수 (2026-09-09)

퍼블리싱과 별개 harness(`.claude/skills/api`, `harness/api/RUNBOOK.md` ①~⑬ 단계)로 진행. ①spec 작성 → ②③Notion 원문 수집 → ④Contract 생성 → ⑤validate → ⑥기존 구조 분석 → ⑦구현계획·테스트시나리오 → ⑧개발자 승인 → ⑨구현 순서이고, **개발자 승인(⑧) 전에는 API 코드·테스트를 작성하지 않는다.**

- **Notion API 명세서가 세션 도중 DB째로 여러 번 교체됐다** — 처음 조회한 `API 명세서 (1)`은 이미 archived(삭제)된 DB였고, 라이브는 이름이 비슷한 `API 명세서 토이빌리지`였다. 이후로도 라이브 DB 자체가 통째로 새 사본으로 두 차례 더 교체됨(콘텐츠는 유지, 페이지 URL만 갱신). → **spec/Contract 작업 시작 전 매번 "지금 조회한 DB가 살아있는(비-archived) 최신 DB인지"부터 확인해야 한다.** 이름이 같아 보여도 다른 데이터베이스일 수 있다.
- **최종 확정된 API 설계**:
  - `GET /team/tree` (`TEAM_QUERY_TREE`, 신설) — `{ totalMemberCount, teams: [{ id, name, memberCount, members: [{id, name, position}] }], unassigned: {...} }`. 담당자 선택 트리(팀별 그룹 + 3상태 체크박스 + 직급 표시)의 데이터 소스. `position`은 `null` 가능.
  - `GET /tasks/{id}` 응답에 `assignees: [{id, name, position}]` 추가 — 수정 폼이 기존 담당자 선택을 복원하는 데 필요. `POST/PUT /tasks`는 `assigneeIds: number[]`로 저장.
  - 상태 enum이 `IN_PROGRESS`/`COMPLETED`/`EXPIRED`로 확정(서버가 계산해서 내려줌: `COMPLETED`=담당자 전원 APPROVED, `EXPIRED`=미완료+기한초과) — 클라이언트에서 재현 불가능한 조건이라 기존 `resolveTaskStatus`(완료기한 기준 파생)는 **제거 대상**, 코드의 `DONE`→`COMPLETED`, `OVERDUE`→`EXPIRED` 개명 필요.
- **선례로 확인된 패턴 — 단체예약(PR #66, `develop`에 이미 merge)**: `GET /reservation/assigned-employee/{reservationId}`가 `{ assigned: [...], assignable: [...] }`로 후보 전원 + 초기 배정 상태를 한 번에 주고(`reservationId: -1`이면 "저장 전" 신규 생성용 전원-assignable 규약), 배정 추가/취소는 로컬 state로만 관리하다가 저장 시 `appAdminIds` 배열을 생성/수정 요청 바디에 실어 한 번에 보낸다 — 명세에 있는 개별 권한 부여/삭제 API(`RESERVATION_PERMISSION_CREATE`/`DELETE`)는 실제로 안 쓴다. `usePermissionAssignment` 훅과 `src/entities/reservation/api/` 모듈 구조가 업무지시 구현의 참고 대상.

## 업무지시(task) API 연동 — 승인·구현·검증 완료 (2026-09-10)

⑧ 개발자 승인 → ⑨ 구현 → ⑩ 정적 검증 → ⑪ Mock 테스트까지 5개 feature(`team-query-tree`/`task-query-all`/`task-query`/`task-create`/`task-update`) 전부 완료. 구현 순서는 의존 관계상 `team-query-tree`(담당자 id 유일 출처) → `task-query-all`(상태 모델 확정) → `task-query`(수정 폼 초기값) → `task-create` → `task-update`.

**승인 전 확정한 설계 결정 4가지** (모두 코드에 반영됨):
1. **상태 값 개명**: `DONE→COMPLETED`, `OVERDUE→EXPIRED`. 서버가 세 상태를 모두 계산해 내려주므로 `resolveTaskStatus`·`taskToday`를 삭제했고, `entities/task-report`의 mock `taskStatus` 12곳까지 개명이 파급됨. 목록의 완료기한 위험색 표시는 유지하되 기준일 계산은 `TaskTable` 내부 순수 헬퍼로 옮김.
2. **`src/entities/team` 신설**: entities끼리 import하지 않는 이 저장소 규칙 때문에 팀 트리(`GET /team/tree`)를 task entity에서 분리. 그 여파로 `findTaskMember`가 사라지고 `task-report`의 mock이 `assigneeName`을 직접 가짐(mock 내부에서만 닫히는 변경).
3. **`전체 직원` 체크박스 3상태 판정 분리**: 표기 숫자는 `totalMemberCount`를 쓰되, 체크 판정 분모는 실제로 렌더된 직원 수로 따로 둠. `totalMemberCount`가 미배정 인원을 포함하는지 여부가 백엔드 미확인 상태라, 두 값을 하나로 묶으면 "전체 선택"이 영원히 `mixed`(부분 선택) 상태에 갇히는 걸 막기 위한 안전장치. 두 값이 실제로 같으면 동작 차이 없음.
4. **`AttachmentField` 확장**: 수정 화면이 기존 첨부의 `fileKey`를 재전송해야 하는데 기존 shared 컴포넌트는 파일명만 노출했음. optional prop `initialFiles`/`onFileItemsChange` 2개를 추가하고 실제 업로드 로직은 `TaskForm`(도메인 레이어)이 담당 — shared 컴포넌트는 도메인에 의존하지 않는 원칙 유지, 기존 호출부는 영향 없음.

**백엔드 확인으로 해소된 사항**: `TASK_QUERY.assignees`가 담당자 **전원** 반환임을 개발자가 직접 확인. 일부만 왔다면 수정 화면이 담당자를 복원 못한 채 `PUT` 전체 교체로 담당자가 유실되는 위험이 있었음 — 확정으로 문서(spec/Contract/final-report) 갱신 후 `task-query`/`task-update` 재승인·재동결(`--freeze`)함.

  - **삭제 시 연쇄**: 종 삭제 → 개체·관찰 기록도 함께 삭제됨(사용자 확인). 개체 삭제 시 관찰 기록 연쇄 삭제 여부는 미확인으로 남음.
  - **PATCH는 전체 교체 방식으로 확정**(사용자 확인) — 관찰 수정의 `fileKeys`는 화면에 남은 첨부 전체 목록을 보내야 하고, 목록에서 뺀 파일은 서버가 삭제 처리한다. 새로 추가한 파일만 `POST /file`로 순서대로 올려 기존 `fileKey`와 화면 순서대로 합쳐 보내는 방식으로 프론트를 바꿔야 함(지금은 새 File을 버림).
  - **법정지정분류(id/이름 불일치) 최종 설계**: 상세 조회는 이름 배열만 주고 등록/수정은 id 배열을 받아 서로 안 맞는 문제를, 백엔드에 id 포함을 요청하는 대신 **이름으로 id를 역매칭**하는 프론트 방식으로 해결(중복 이름은 프론트의 기존 "이미 있는 분류입니다" 중복 검사로 사실상 막힘). **서버가 기본값을 내려주지 않는 것도 확인**돼, 화면에 고정 노출하는 기본 3개(`지정관리 야생동물`/`멸종위기 야생생물 I급`/`천연기념물`)는 **종 저장 시점에 서버 목록에 없으면 프론트가 먼저 `POST`로 등록**하고 그 id를 쓰기로 결정. 직접 추가·삭제(`DELETE`)는 폼 저장과 무관하게 **즉시 서버에 반영**되고, 삭제는 그 항목을 쓰던 **모든 종에서 함께 빠진다**(사용자 확인, 별도 "사용 중 삭제 불가" 처리 불필요).
  - **최종 남은 백엔드 질문은 1개**로 좁혀짐: `POST /animal-manage/legal-status`가 같은 이름(`kind`) 중복 등록을 막아주는지.
- **확정된 디자인 작업 목록(Figma 수정 3 + 신규 3)**: ① 종 목록 정렬 버튼 제거 ② 종 상세 개체 표 정렬 버튼 제거 ③ 법정지정분류 기본 3개 pill의 `✕` 제거(Figma 원본엔 그려져 있음) / ④ 법정지정분류 삭제 확인 모달(전체 종에서 함께 빠진다는 안내) ⑤ 법정지정분류 추가·삭제 실패 표시 ⑥ 종 목록·상세·개체 상세·관찰 상세/수정의 조회 실패(서버 오류) 상태 — mock 시절엔 실패가 사실상 없어 이 상태 자체가 화면에 없었음.
- **입력 길이 제한 추가 결정**(Swagger 필드 상한 기준, 표시 문구 없이 입력만 막음): 개체 기타정보 255자, 관찰 제목 100자, 관찰사항 2000자.
- **`Swagger의 `*` 필수 표시는 실제 서버 검증과 다를 수 있다`는 전제로 접근** — `POST`·`PATCH`가 같은 요청 스키마(`AnimalKindRequest` 등)를 공유해서 수정 때도 전체 필드가 필수로 보이는 것과, 그런 자동 생성 문서의 신뢰도 자체를 백엔드 확인 대상으로 분리해서 다룬 판단 기준.

## 첨부파일 다운로드(#71) 완료 (2026-09-16)

2026-09-14에 진단만 하고 끝났던 [[크로스오리진-파일-다운로드-a-download-무시]] 버그를 실제로 고치고 머지까지 완료했다(PR #100, 머지 커밋 `3545fb9`).

- **적용 범위**: 처음엔 조회 전용 화면(업무 상세·업무보고 상세)만 고쳤다가, 사용자 요청으로 수정 화면(업무 수정 `AttachmentField`, 자료실 `ResourceUploadField`, 공지 수정 `NoticeForm`)까지 같은 세션에서 확장했다. **관찰·개체 폼은 제외** — 아직 mock 데이터라 `fileKey`가 가짜이고, 같은 컴포넌트(`AttachmentField`)를 쓰는 관찰 수정 e2e가 동결(freeze)돼 있어 지금 공통 코드를 바꾸면 그 테스트가 깨진다. `#89`가 관찰을 실 API로 옮긴 뒤 `storedFiles` prop만 켜면 이어서 고칠 수 있다.
- **공용 인증 axios 대신 `fetch` 사용**: CDN 파일 서버 호출에 공용 인증 인스턴스를 쓰면 토큰이 새고 CDN의 403이 세션 만료로 오인될 수 있어 `fetch`로 우회했다 — 근거와 일반 패턴은 [[공용-인증-axios-외부도메인-토큰유출]] 참고. `harness/shared/code-rules.md` 4번(raw fetch 금지)에 이 예외를 명시했다.
- **e2e 오리진 검증**: mock이 경로만 확인해 서버가 바뀌어도 안 걸리던 구멍을 CodeRabbit 리뷰로 발견·수정 — 자세한 내용은 [[Playwright-mock-오리진-미검증]] 참고.
- **스테이징 실측 검증**(모두 CDN 원본과 바이트까지 일치): 업무 상세·업무 수정 `접근제어자.pptx`(56,894B), 자료실 pdf(322,411B), 공지 png(189,666B, `advil1.png`). 업무 #1의 기존 첨부 `휴관안내.jpg`가 처음엔 이상해 보였지만, CDN에 올라간 원본 자체가 예전 버그가 만든 17바이트 텍스트라 그대로 받아진 것일 뿐 다운로드 경로 문제가 아님을 확인했다.
- **커밋 메시지 재작성 후 강제 푸시**: 사용자 요청으로 이미 push된 커밋 12개의 메시지를 쉬운 말로 전부 바꿔야 해서 `filter-branch`로 재작성 후 `--force` 푸시했다. **커밋 해시가 전부 바뀌므로**, 그 이전에 CodeRabbit 리뷰 답글에 남겨뒀던 옛 해시도 새 해시로 다시 고쳐야 했다. `filter-branch`가 남기는 백업 ref(`refs/original/...`)도 정리 대상이다.
- **CodeRabbit 리뷰 답글 관례**: 리뷰 대응 답글에는 설명을 달지 않고 **커밋 해시만** 남기기로 함(사용자 지시, 이후 세션에도 적용).
- **배포 환경 미해결 사항**: `VITE_FILE_BASE_URL=https://cdn.toyvillage.kr`을 배포 환경변수에 추가해야 한다 — 빠지면 화면은 뜨지만 다운로드만 실패하고 콘솔에 사유가 남는다. 이건 AI가 못 하는 부분으로 남겨둠.

## 개체관리(#89) API 연동 — Notion/Swagger 최종 갭 확정·백엔드 요청 발송 (2026-09-17)

- **개체관리 API의 Notion 명세 위치가 새로 확인됨**: 명세서(mcp) 아래 새로 생긴 DB(`3dc7…`)에 종 4개(`ANIMAL_KIND_QUERY_ALL`/`QUERY`/`CREATE`/`UPDATE`)·개체 5개(`ANIMAL_MANAGE_QUERY_ALL`/`QUERY`/`CREATE`/`UPDATE`/`DELETE`) 총 9개 API ID가 등록돼 있음을 확인했다. 이전엔 이 DB를 놓쳐 "Notion에 개체관리 API가 없다"고 메모리에 잘못 기록돼 있었다 — [[Git-브랜치-뒤처짐-확인-없이-기능-없다고-단정]]과 같은 계열의, 조회한 원본이 최신인지 먼저 확인하지 않아 "없다"고 오판하는 함정이 Notion DB 쪽에서도 재발.
- **Swagger(App 그룹 `animal-manage-controller`) 대조 결과 총 18개 경로 중 9개가 Notion에 없음**(그중 관찰 등록 1개는 앱 전용이라 웹 관점에서는 8개): 종 삭제, 법정지정분류 조회·추가·삭제 3개, 관찰 목록·상세·수정·삭제 4개.
- **백엔드에 6개 항목으로 정리해 요청 발송**: ① 위 8개 API의 ID·접근권한(ADMIN 전용/USER 가능 여부) 등록 ② 파일 조회 base URL 실값(staging·운영 각각, 종·개체 사진과 관찰 첨부 표시에 필요) ③ 오류 응답 — Swagger엔 18개 경로 전부 200만 있어 없는 id(404)·입력 오류(400)·권한 없음(403)의 상태코드·body 형식 확인 필요 ④ 응답에서 null·빈 값 가능 필드(`otherInfo`, 관찰 `files`, `detailKind`/`legalStatuses`) ⑤ 기존에 요청했던 keyword 검색·종 필수값 완화(`animalDetailKind`/`animalLegalDesignation`)·목록 기본 정렬 순서의 Swagger 반영 여부 ⑥ Swagger 표기 오류 정정(POST 실제 201인데 Swagger엔 200, `Pageable.page`가 0부터로 표기되나 실제는 1부터).
- Swagger 필수 필드·성공 코드·응답 null 여부를 어디까지 신뢰할 수 있는지의 일반 원칙은 [[Swagger-자동생성-문서-필수값-확인과-신뢰-한계]] 참고(신규) — 이번 조사에서 Schema 탭 vs Example Value 탭 구분, `required` 배열의 실제 근거(`@NotBlank`/`@NotEmpty` 등), 응답 DTO엔 검증 어노테이션이 없어 null 여부를 Swagger만으론 알 수 없다는 점을 확인.

## 사이드바 사용자 정보 연동(#77) 완료 (2026-09-17, orca 세션)

- **로그인한 사용자의 이름을 조회하는 별도 API를 새로 부르지 않기로 결정**: Notion 토이빌리지 명세 DB를 확인했으나 "내 정보 조회" API가 없었다. 대신 로그인 응답(`APP_AUTH_LOGIN`)의 `name`이 이미 로그인 시점에 localStorage 세션에 저장돼 있어, 그 값을 그대로 재사용하기로 함 — 새 API 없이 기존에 받아둔 데이터를 재사용하는 것도 선택지로 먼저 확인해볼 가치가 있다는 사례.
- **구현**: `Sidebar.tsx`가 열릴 때마다 `readSessionUser()`로 저장된 값을 읽어 이름·아바타 접근성 이름(`{이름} 프로필`)을 표시 — 다른 계정으로 재로그인해도 새로고침 없이 바로 반영됨. 프로필 이미지 URL이 명세에 없어 아바타 모양(원)은 그대로 두고 텍스트만 실제 값으로 교체. `mockSidebarUser`와 `SidebarUser` 타입은 제거.

## 개체 상세 먹이 급여 기록 버튼 연결(#119) 완료 (2026-09-17)

- **연결 방식 결정**: 개체 상세의 `먹이 급여 기록 확인하기` 버튼은 개체관리 슬라이스 퍼블리싱(2026-09-15) 당시 먹이 급여 화면이 아직 없어 `aria-disabled`로 막아 둔 상태였다(코드 주석에도 명시). 이후 `/feeds`·`/feeds/:id`가 실제 API와 연결됐지만, `/feeds/:id`는 개체 번호가 아니라 **급여 기록 번호(feedLogId)**로 여는 화면이라 개체 상세에서 바로 연결할 주소가 없었다. 그 화면이 이미 해당 개체의 급여 이력 전체를 보여주는 구조이고 개체별 급여 이력 화면 자체가 Figma에 없어서, **새 화면을 만드는 대신 그 개체의 최신 급여 기록 상세로 보내는 쪽으로 결정**(리뷰어에게 결정 근거로 명시). 개체 번호(animalManageId) 기준 이력 조회는 기존 `getFeedHistory`(`/feed-log/admin/history/{animalManageId}`)를 공개해 재사용, 404를 빈 이력으로 처리하는 로직을 함수 안으로 이동, `feedQueryKeys.history` 신설. 급여 상세의 `뒤로가기`는 개체 상세에서 들어온 경우 개체 상세로 돌아가도록 `backPath` state를 추가했다.
- **버튼 동작을 "미리 비활성화" → "클릭 시 조회 후 분기"로 정정**: 처음엔 이력 로딩 중·이력 없음·조회 실패 시 버튼이 눌러도 반응하지 않는 구현이었는데, 스테이징에서 실제로 눌러 봐도 반응이 없어 사용자가 예외 처리 필요성을 지적함 → **버튼은 항상 눌리게 두고, 클릭 시점에 이력을 조회**해서 기록이 있으면 최신 기록 상세로 이동, 기록이 없으면(404 포함) `급여 기록이 없습니다`, 조회에 실패하면(500 등) `급여 기록을 불러오지 못했습니다` 오류 토스트를 띄우는 방식으로 바꿨다. "화면이 없으면 막아 둔다"는 기존 관례와 달리, 화면은 있지만 데이터가 없을 수 있는 경우엔 클릭을 막지 않고 결과에 따라 토스트로 알리는 쪽이 사용자에게 더 명확하다는 사례.
- **검증**: 타입 검사·lint·빌드·harness 유닛 테스트(18개) 통과. 관련 e2e(`individual-detail`·`feed-detail`·`api/feed-log-query-detail`) 48개 통과. 시나리오는 S17(비활성→이동)·S31(기록 없음 토스트)·S32(조회 실패 토스트)로 갱신·재승인. 브랜치 `#119/feed-history-link`, PR #122로 develop에 머지 완료.
- **스테이징 QA 데이터 함정**: 개체 1(무궁이)·2(해피)·3(토리)은 각각 급여 기록이 7건씩 있지만, 세 개체 모두 **최신 기록이 `2026-12-31` 날짜의 `[QA-STAG] 미래 예약 급여` 테스트 데이터**라, 버튼을 눌러도 실제 최근 급여가 아니라 그 미래 테스트 기록이 먼저 열린다 — "최신 급여 기록으로 이동" 기능을 스테이징에서 확인할 때 유의할 것.

## 이슈 #129 등록 — access token 만료 시 재발급 없이 로그아웃(401 vs 403) (2026-09-17 밤)

- **문제 재확인**: 토큰 리프레시 자체는 이미 구현돼 있다 — 앱 시작 시 `src/app/main.tsx`에서 설정을 켜고, 실제 처리는 `src/app/config/configureApiAuthentication.ts`. localStorage의 access token을 `Authorization: Bearer`로 붙이고, 401을 받으면 refresh token으로 재발급 후 원 요청을 한 번 재시도한다. 동시에 여러 요청이 401이어도 재발급은 `pendingReissue`로 한 번만 호출된다. 그런데도 "계속 로그아웃된다"는 제보가 들어와 staging(`https://api-stag.toyvillage.kr`)에 curl로 직접 확인했다.
- **curl 진단**: 토큰 없이 `/app/tasks`·`/app/teams`·`/app/auth/logout`·존재하지 않는 경로를 호출하면 **전부 403**. 반대로 `/app/auth/reissue`에 잘못된 refresh token을 보내면 **401**을 정상 반환한다(`{"message":"유효하지 않은 토큰입니다.","status":401,...}`). 즉 이 서버는 reissue 엔드포인트만 예외적으로 401을 쓰고, 나머지는 인증 실패(토큰 없음·위조)를 401이 아니라 403으로 응답한다. 앱 없이 curl만으로 401/403 사용처를 빠르게 구분할 수 있는 진단법.
- **원인**: 응답 인터셉터(`configureApiAuthentication.ts:47`)는 403을 권한 거부로 보고 재발급 없이 바로 `endSession()`을 부른다. 재발급 로직은 401에만 걸려 있어, access token이 만료될 때마다(서버가 403으로 응답하므로) 재발급 흐름을 한 번도 타지 못하고 강제 로그아웃된다.
- **한계**: 서명이 유효하지만 실제로 만료된 access token으로는 확인하지 못했다(테스트에 쓴 "만료 토큰"은 서명이 틀린 토큰). 다만 무인증 요청이 전부 403으로 오는 걸 보면(Spring Security `AuthenticationEntryPoint` 미설정 추정) 진짜 만료 토큰도 같을 가능성이 높다고 보고 "(추정)"으로 남겼다.
- **결정 — 백엔드가 아니라 프론트에서 고친다**: 처음엔 "백엔드가 인증 실패=401/권한 부족=403으로 나누게 고쳐야 한다"는 백엔드 이슈 초안을 준비했으나, 사용자가 "아니 프론트에서 수정해야지"로 방향을 정정했다. 403도 401처럼 한 번 재발급 후 재요청하도록 프론트 인터셉터를 고치는 쪽으로 확정(백엔드가 나중에 401로 바뀌어도 그대로 동작). 같은 문제 계열은 [[401을-세션만료로-오인한-로그인-루프]] 참고 — 그 페이지에는 이 프로젝트가 같은 날 낮에 내린 다른 403/401 판단(쿠키 기반 재발급 조건 재조정)이 이미 실려 있는데, 이번 건은 그와 별개로 staging 전체가 인증 실패를 403으로 준다는 사실을 curl로 재확인하고 대응 방향(프론트 vs 백엔드)을 다시 정한 것이다.
- **이슈만 등록, 구현은 아직**: 사용자 요청대로 수정 방향(체크리스트)은 빼고 문제 상황·재현 방법만 담아 프론트 레포에 등록했다 — [이슈 #129](https://github.com/ToyVillage/ToyVillage-Admin-FE/issues/129).

## 대시보드(#107) API 연동·행 상세 이동 완료, PR #131 (2026-09-17 밤, orca `develop` 세션)

- **API 4개 확정 — Swagger보다 Notion이 우선**: 처음엔 staging Swagger(Basic Auth라 이미 로그인된 Chrome 탭으로 우회 확인)로 4개 API(`DASHBOARD_COUNT`/`DASHBOARD_OVERALL_OPERATIONS`/`DASHBOARD_FEED_LOGS`/`DASHBOARD_ANIMAL_OBSERVATIONS`)를 뽑아 Contract를 만들었는데, 사용자가 "노션에 명세서를 새 페이지로 가져왔다"고 알려줘 새 DB(`API 명세서 토이빌리지`, `3de7a4d6…`)에서 공식 명세를 찾아 전부 다시 만들었다. Swagger만으론 알 수 없던 항목이 Notion엔 있었다 — 집계 기간(이번 주 일요일 00:00~다음 주 일요일 00:00 전), 권한(ADMIN 전용), `overall-operations`의 `TOTAL`(세 상태 합), 목록 두 개(`feed-logs`/`animal-observations`)의 페이지는 **1부터**(Swagger만 보고 0부터로 잡았던 걸 정정). [[Swagger-자동생성-문서-필수값-확인과-신뢰-한계]]와 같은 계열로, Notion 명세가 있으면 항상 Swagger보다 우선해야 한다는 사례가 한 번 더 쌓였다.
- **화면 7개 조회 중 3개는 신규 API 대신 기존 API 재사용**(휴관일 `GET /close-day`, 업무보고 `GET /work-report?page=1&size=3`을 `status` 없이, 업무일지 `GET /work-log?date=today&page=0&size=3`) — 사용자 선택. 업무보고 조회 함수는 `status`를 optional로 바꾸고 대시보드 행 표시용 `title` 매핑을 추가하는 부수 변경이 필요했지만 업무보고 목록 화면 자체 동작은 안 바뀜.
- **행 클릭 시 상세 이동 — id가 있는 섹션부터 단계적으로 확장**: 처음엔 휴관일·업무보고·업무일지 3개(대시보드 전용 API가 아니라 재사용 API라 원래부터 id가 있었음)만 연결. 먹이 급여·개체관리는 대시보드 API 응답(`DashBoardQueryFeedLogResponse`/`DashBoardQueryAnimalManageResponse`)에 id가 없어 보류하고, 백엔드에 `feedLogId`/`animalKindId`+`animalManageId`+`observationId` 추가를 요청.
- **백엔드 PR 오인 함정**: 사용자가 "#170에서 넣었다는데 왜 안 되냐"고 물었을 때, PR #170(`내 급여일지목록조회에서 feedLogId 컬럼추가`)은 **다른 응답 타입**(`FeedLogQueryResponse`, "내 급여일지 목록 조회"용)에 id를 추가한 것이었고, 대시보드가 쓰는 `DashBoardQueryFeedLogResponse`는 그대로였다 — 같은 데이터(급여 기록)를 내려주는 API가 여러 개일 때, PR 설명만 보고 "추가했다니까 되겠지"로 판단하지 말고 실제로 쓰는 응답 타입까지 대조해야 한다는 사례.
- **뒤이은 PR #172**(`먹이급여관리와 개체관리에 id컬럼추가`)로 `feedLogId`와 `animalObservationId`가 추가됐지만, 개체관리 쪽은 처음엔 관찰 기록 id 하나뿐이라 여전히 상세로 못 감 — 관찰 상세 API가 `GET /animal-manage/{animalManageId}/observations/{id}`라 개체 id가 필요하고, 화면 주소(`/species/:speciesId/individuals/:individualId/observations/:observationId`)엔 종 id까지 필요했다. 같은 날 밤 **핫픽스**(`대시보드 개체관리에 id 추가`)로 개체 id(`animalId`)까지 반영됐다(종 id는 끝까지 응답에 없음). staging이 핫픽스 배포 도중이라 Swagger 문서를 못 보여준 시점에 확인해 "아직 안 됨"으로 한 차례 오판했다가, 배포가 끝난 뒤 다시 봐서 정정한 해프닝도 있었다.
