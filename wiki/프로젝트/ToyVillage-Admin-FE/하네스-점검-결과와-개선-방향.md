# 하네스 점검 결과와 개선 방향

[[하네스-시스템]]을 구조 분석(파일·git)과 실제 AI 세션 기록으로 점검한 결과와 "새로 만들기보다 개선 먼저"로 정한 근거. 대부분의 문제가 10분~2시간짜리 수정이고, 정정 지시의 약 42%가 하네스로 막을 수 있었다는 측정이 판단 근거다. 측정 방법과 함정은 [[Claude-Code-세션-기록으로-정정-지시-측정]].

## 결정: 새로 만들기 vs 개선 (멘토 질문)
- **개선 먼저.** 점검 항목 대부분이 10분~2시간 수정이고 구조 개편은 맨 마지막 하나(A2·A3)뿐. 개선 후 같은 기준으로 재측정하고, 구조 개편이 필요한지는 그 뒤에 판단. 재측정은 개선 4주 뒤(노션 기준 ~11/4), 두 사람 모두 같은 스크립트·기준으로.
- 문제는 "구조"보다 **"규칙 누락"과 "갱신 절차 없음"**에 가깝다.

## 구조 점검에서 나온 주요 문제 (사용자가 정리한 목록, 일부만 Claude가 재확인)
Claude가 직접 맞다고 확인한 것: C5(승인자 `approvedBy`가 `claude (…위임)` 4건·`user` 1건, `--by` 검증 없음), D2(퍼블리싱 스킬 파일에 `component-map` 0회), D3(`.claude` API 스킬은 ⑬단계까지·`.codex`는 ⑭단계까지), E2(`.github/workflows`·`.husky` 없음). 나머지는 미검증(로컬 develop이 원격보다 16커밋 뒤처진 상태에서 확인).
- **A 설계**: 해시 동결이 git 재발명(스크립트 4개 574줄, 무엇이 바뀌었는지는 모름 → 승인 시점 commit SHA 1개+`git diff <sha>..HEAD`로 대체하면 ~50줄) / 승인 게이트가 PR 리뷰보다 약함 / 사전 승인 워터폴이 자주 바뀌는 Figma와 미스매치(같은 명세 최대 14회 재작성, 하네스 커밋 비율 37% = 459/1,228) / 기계·AI·사람 역할 3군데 역전(시각 검증을 기계가 아니라 사람 눈이) / 기계가 읽을 데이터를 Markdown으로 관리 / Playwright가 118개 파일에서 `page.route()`로 서버를 재구현하면서 `toHaveScreenshot` 0건 / 제품 단위 테스트 0개인데 하네스 테스트 640줄 / 4층 문서 구조에서 요약층이 원본보다 먼저 썩음.
- **B 퍼블리싱**: 화면을 실제로 비교하는 검사 없음(B1, 가장 효과 큼) / "blocking"이라 선언한 component-map 게이트에 구멍 3개(`artifacts/` gitignore·승인 시 해시 안 함·스킬에 언급 없음) / 프롬프트가 없는 섹션(§7)을 가리킴 / 명세가 Figma 픽셀 전사로 비대(최대 528줄) / 명세 Status와 `approved.json` 불일치 21건 / `scenarioIds`가 장식(승인 ID가 실제 e2e에 있는지 아무도 안 봄) / 게이트가 자발적(호출처가 `run-scenarios.mjs` 한 곳) / 죽은 경로 4개. **loop-guard가 안 쓰인 이유**: AI가 성실히 에러 해시를 기록해야 작동하는데 그렇게 협조적인 AI는 애초에 무한루프에 안 빠진다 — 비협조 상황에서 작동 안 하는 가드는 가드가 아니다.
- **C API**: 실서버 파이프라인 전체가 죽은 코드(`real_server.enabled` 61/61 false, 407줄) / mock이 서버처럼 필터·정렬·페이징을 재구현해 "명세대로 짰다"까지만 증명(추측이 틀려도 초록불) / Notion을 단일 진실원이라 하면서 실제로는 Swagger와 교차검증(정식 단계 아님) / 기능당 승인 산출물 5종(301파일, 승인 커밋 191건) / 14단계 RUNBOOK이 실질 8단계 / 같은 규칙이 3곳에 중복·충돌(raw fetch 금지, `fileStorage.ts` 예외).
- **D 스킬·진입점**: 스킬이 2026-07-26 스냅샷으로 멈춤(그 사이 하네스 189커밋) / 4중 복제(`.claude`·`.codex`)가 이미 불일치 / 진입 경로 이중화.
- **E 횡단**: ESLint가 이미 강제하는 규칙(FSD 경계·`any`)을 산문으로 재선언해 어디까지 진짜 강제인지 헷갈림 / CI·훅 전무로 모든 게이트가 자발적 / 문서 35,070줄(md 512개)·스크립트+테스트 2,747줄·추적 파일 568개.

## 세션 기록에서 드러난 실제 막힘 (F)
- **F4 팀 규칙이 하네스에 없고 개인 AI 메모리에만 있음 — 윤호 쪽 최다 원인.** PR 제목=브랜치 이름, 이슈 먼저 만들고 브랜치 파기, 백업 브랜치 금지, CodeRabbit 답글 방식 등. 하네스·스킬·CLAUDE.md에서 "PR 제목"·"브랜치 이름" 검색 0건 → 지환의 AI는 모르고 새 세션마다 다시 말해야 함. 처방: `harness/shared/workflow.md`를 만들고 **지환과 합의한 것만** 채움(5173 포트·작업 폴더 같은 개인 환경 규칙은 개인 메모리에 남김). 대상: PR 제목·이슈 먼저·브랜치/백업 금지·커밋 형식·쪼개기·CodeRabbit 답글·e2e 격리 포트·스테이징 500 판별법.
- **F1 입력 기준이 바뀌어도 하네스에 반영 안 됨**: 9/7 명세가 폐기된 Figma 파일을 가리켜 전부 재작성, 9/17에도 AI가 폐기 파일을 조회해 "yot를 봐야지"로 재지시. 처방: Figma 파일 키·Notion DB 위치를 한 곳에만 두고 명세는 참조, 폐기 키가 남으면 검사 실패(폐기 키 13곳을 yot로 교체).
- **F2** 코드의 page 0→1 수정 뒤에도 명세·구현 계획에 0이 남아 CodeRabbit 지적 → 계약값은 JSON 한 곳. **F3** 승인 명령의 `--by <이름>`을 그대로 복사해 셸 오류 → `git config user.name`으로 채워 보여주기. **F5** Notion 명세의 옛 스키마·오타·반영 지연 → Swagger 교차검증 정식화. **F6** 규칙 문서(RUNBOOK·규칙·스킬)는 약 12번 수정에 8/26 이후 1번뿐인데 같은 기간 명세·승인 파일은 수십 번 — 규칙 변경 시 문서 갱신 절차(예: PR 템플릿 "하네스 영향 있음" 체크) 필요.
- **F7 화면 불일치**가 팀 전체 정정 원인 1위(37건), **F8 게이트 절차 비용**(게이트 때문에만 쓴 프롬프트 6%)은 하네스가 오히려 비용이 된다는 증거.

## 개선 순서 (우선순위, 비용)
1. **D2+D3** 스킬 두 줄 수정(⑭ 단계 추가, 퍼블리싱 스킬에 component-map 게이트) 10분 — 지금 품질을 깎는 중
2. **B3** `§7`→`§1`, 고아 규칙 흡수 10분
3. **C5+F3** `--by`에 AI 이름 거부(허용 목록)+명령 자동 채움 20분
4. **F4** 팀 규칙을 하네스로 — 30분+지환 합의
5. **F1** 입력 기준 한 곳으로 1시간
6. CI 1개(커밋·PR 형식·하네스 게이트 자동 검사) — 먼저 깨진 e2e를 처리해야 켜자마자 실패하지 않음(e2e 현황은 [[ToyVillage-Admin-FE/프로젝트-현황]])
7. **B1 스크린샷 게이트** — 원래 8순위였으나 화면 불일치 1위 근거로 7위로 상향 / **F8** 게이트 절차 줄이기(승인 명령 자동 채움·시나리오 ID 손입력 제거)
8. C1+B8 죽은 경로 삭제(521줄 이상), B2 component-map 승격+코드 검사, A1 해시→git SHA(574줄 제거), C3·C4·C6, B4·B5·D1·D4
9. 마지막: A2·A3 구조 개편(PR·CI 이전, 승인을 구현 뒤로) — 1~8 후 재측정하고 결정

## API 하네스 측정과 분담 결정 (2026-10-08 세션, 기준 `a3e941c`)
- **분담: 윤호 = API 하네스, 지환 = 퍼블리싱.** 지환은 e2e 때문에 퍼블리싱을 원했다. 윤호가 퍼블리싱을 맡는 쪽이 포폴에 유리하다는 분석(화면 불일치 38건=원인 2위를 스크린샷 게이트로 직접 줄임, API는 서버 사정에 의존)이 있었지만 협상 결과 API로 확정. 공통 작업(CI·깨진 e2e 정리·승인자 검증·팀 규칙)은 윤호가 가져간다. 두 하네스는 "AI 결과가 진짜 기준(Figma 화면 / 실제 서버)과 맞는지 기계가 확인하지 않는다"는 같은 병을 앓는다 — 퍼블리싱은 스크린샷 비교 0건, API는 실서버 검증 0건.
- **API RUNBOOK 14단계**: ②③이 "API ID로 Notion DB를 검색해 정확히 1건 일치"를 요구한다. 그래서 **Notion에 명세가 없는 API(업무일지·먹이 급여 admin 조회·팀 관리)는 계약을 못 만들고 승인 게이트도 못 통과해 계약 없이 연동**됐다(9/15 "Swagger에만 있으니까 Swagger 보고 해"). 처음 "절차가 무거워서 우회"라 해석했다가 지환의 확인으로 정정 — 절차를 시작할 수 없었던 것. 개선 방향: 입력을 "Notion 또는 Swagger"로 넓히고 OpenAPI에서 `contract.json`을 자동 생성(수동 ②③④ 삭제), 산출물 5종→3종(`contract.md`는 json과 중복, `implementation-plan.md`는 구현 후 낡음).
- **계약 65개 vs 스테이징 Swagger(API 144개) 자동 비교**: 완전 일치 43개(66%), 하나 이상 다름 **22개(34%)** — 성공 응답 코드 14(계약 201 vs Swagger 200이 13, 삭제 200 vs 204가 1)·응답 필드 5·쿼리 파라미터 3, 경로 없음/요청 필드 차이 0. **"다르다"≠"계약이 틀림"**: 생성 API는 실서버가 201을 주는데 Swagger가 200으로 잘못 적은 경우가 확인돼 있어([[Swagger-자동생성-문서-필수값-확인과-신뢰-한계]]) 자동 수정하지 않고 차이만 드러내 사람이 판단한다. GET인데 201로 적힌 계약 2개(자료실 상세·운영시간 조회)는 계약 오류 가능성이 높다. 스테이징 Swagger는 로그인 없이 401이라 CI에서 돌리려면 백엔드에 접근 방법을 물어야 한다(브라우저에서 로그인한 탭의 `fetch('/v3/api-docs')`로 비교했다).
- **명세 정정 14건(지환 기록) 중 7건은 Swagger 자동 비교로 구현 전에 잡힘**(enum 3갈래·타입별 규칙·상태코드 2건·nullable·불필요 필드·응답 필드 누락), 나머지 7건(Notion 미등록·프론트 구현 누락 3건·사용 범위 결정·변경 시점 감지·조회 조건 불일치)은 스펙 비교로 안 잡혀 e2e의 영역.

## 게이트 검사가 하는 일과 CI 단계 계획 (2026-10 세션)
- **게이트 검사** = 사람이 승인한 시나리오·테스트가 승인 뒤 바뀌지 않았는지 확인하는 스크립트. `harness:approve` 때 `approved.json`에 승인자·시각·시나리오 ID·파일 sha256을 저장하고, 검사는 현재 파일 지문을 다시 계산해 비교, 하나라도 다르면 "다시 승인받으라"며 실패. 퍼블리싱(`gate-check.mjs`)은 승인 기록·시나리오 문서·e2e 파일, API(`api-gate-check.mjs`)는 task 명세·API 계약(JSON·MD)·구현 계획·테스트 시나리오·API e2e를 본다. 목적은 AI가 구현을 통과시키려 승인된 테스트를 몰래 약화하는 것을 막는 것.
- **검사하지 않는 것**: 승인자가 실제 사람인지, 테스트 통과 여부(지문만 비교), `src` 변경, Figma 일치. 호출하는 사람이 없어 e2e를 고치고 재freeze 안 한 채 머지된 것이 쌓여 **111개 중 41개(37%)가 깨져 있고**(퍼블리싱 13/46·API 28/65, 승인은 있는데 e2e 파일이 없는 기능 3개 포함) 기준 커밋 `fd42462`에서도 33%였다 — "게이트가 자발적"(B7)의 수치 증거.
- **e2e와 CI는 같은 문제**: e2e 실패 53개 중 49개(92%)는 테스트 오류가 아니라 다른 작업(401·403 전역 로그아웃·스켈레톤)의 변경을 못 따라간 드리프트인데 전체 e2e CI가 없어 4주간 몰랐다. 또 e2e 파일을 고치면 `e2eHash` 때문에 기능별 재freeze가 필요해 F8·C5가 같이 터지므로 **승인자 검증·명령 자동 채움이 e2e 수정보다 먼저**.
- **재정렬한 18단계**(노션 반영): 1 스킬 두 줄 → 2 §7 참조 → 3 승인자 검증+명령 자동 채움 → 4 e2e "동작 차이" 2건(목록 복귀 `?page=2` 유지·업무일지 2페이지 요청 안 나감)이 실제 버그인지 확인 → 5 CI 1단계(verify) → 6 e2e 일괄 수정 24(전역 로그아웃 11·스켈레톤 9·작성 방식 4) → 7 e2e 개별 수정 27(휴무일 12·개체 9·기타 6) → 8 CI 2단계(PR마다 전체 e2e) → 9 팀 규칙 합의→형식 검사 → 10 Figma·Notion 기준 한 곳 → 11 스크린샷 게이트 → 12 게이트 절차 줄이기 → 13~17 죽은 경로 삭제·component-map·해시→git SHA·API 하네스 정리·명세 감량 → 18 구조 개편. 바뀐 점은 CI를 둘로 쪼개 e2e 결정이 CI 전체를 막지 않게 한 것, e2e는 "기존 실패 목록으로 빼기"보다 고치기 추천(패턴 몇 개로 묶여 비용이 작고 빼면 감시 밖). 스크린샷 게이트는 CI의 같은 환경이 있어야 기준 이미지를 찍을 수 있고 애니메이션을 끄고 비교해야 한다.
- **CI job 5개**: verify(lint·typecheck·style-policy, 빌드는 Cloudflare 필수 지정으로 대체)·harness-test(`yarn test:harness` 18개)는 지금 통과해 바로 켬 / e2e(샤딩 4)는 53개 정리 뒤 / harness-gate는 "PR에서 바뀐 파일→기능" 매핑 스크립트와 승인 검증 수정 뒤 / pr-format은 팀 규칙 합의 뒤(당시 PR 제목 준수 71.4%·커밋 형식 84.4%). 설계 근거(job 분리·샤딩·훅과 토큰)는 [[PR-CI-설계-job-분리-e2e-샤딩-훅과-AI-토큰]]. 저장소 상태: Actions 없음, PR 검사는 Workers Builds·CodeRabbit뿐(필수 아님), develop 보호는 PR 필수·승인 1명·강제푸시 금지지만 필수 상태 검사 0개·관리자 우회 가능. `yarn verify` 15초 통과, 번들 메인 JS 1,031.20 kB로 +8%, lint에 `boundaries/element-types`(v6 폐기→`boundaries/dependencies`) 경고.
- **디스코드 공유문 교훈**: 팀 합의가 필요한 항목(커밋·PR 제목 형식, Co-Authored-By 허용, e2e 53개 고치기 vs 제외, 관리자 우회)은 "같이 정해야 할 것"으로 분리해 쓰지 않으면 이미 결정된 것처럼 읽혀 "좋아요"로 끝난다. 각 항목에 켜는 시점을 붙인다.

## e2e 수정 후 재승인 절차 (2026-10-15, #237)
- e2e·시나리오를 고치면 `approved.json` 해시가 어긋나 게이트가 "시나리오가 승인본과 다름 + 테스트 해시 불일치"로 실패한다. 순서: 로컬 산출물을 승인본과 먼저 맞춤(오래된 로컬 산출물은 백업 후 교체) → 테스트·시나리오 수정 → 사람이 `yarn harness:api:approve <기능> --by <이름>` → `--freeze` → `node scripts/api-gate-check.mjs <기능> --require-test`.
