# 하네스 점검 결과와 개선 방향

[[하네스-시스템]]을 구조 분석(파일·git)과 실제 AI 세션 기록으로 점검한 결과와 "새로 만들기보다 개선 먼저"로 정한 근거. 대부분의 문제가 10분~2시간짜리 수정이고, 정정 지시의 약 42%가 하네스로 막을 수 있었다는 측정이 판단 근거다. 측정 방법과 함정은 [[Claude-Code-세션-기록으로-정정-지시-측정]].

## 결정: 새로 만들기 vs 개선 (멘토 질문)
- **개선 먼저.** 점검 항목 대부분이 10분~2시간 수정이고 구조 개편은 맨 마지막 하나(A2·A3)뿐. 개선 후 같은 기준으로 재측정하고, 구조 개편이 필요한지는 그 뒤에 판단. 재측정은 개선 4주 뒤(노션 기준 ~11/4), 두 사람 모두 같은 스크립트·기준으로.
- 문제는 "구조"보다 **"규칙 누락"과 "갱신 절차 없음"**에 가깝다.

## 구조 점검에서 나온 주요 문제 (사용자가 정리한 목록, 일부만 Claude가 재확인)
Claude가 직접 맞다고 확인한 것: C5(승인자 `approvedBy`가 `claude (…위임)` 4건·`user` 1건, `--by` 검증 없음), D2(퍼블리싱 스킬 파일에 `component-map` 0회), D3(`.claude` API 스킬은 ⑬단계까지·`.codex`는 ⑭단계까지), E2(`.github/workflows`·`.husky` 없음). 나머지는 미검증(로컬 develop이 원격보다 16커밋 뒤처진 상태에서 확인).
- **A 설계**: 해시 동결이 git 재발명(스크립트 4개 574줄, 무엇이 바뀌었는지는 모름 → 승인 시점 commit SHA 1개+`git diff <sha>..HEAD`로 대체하면 ~50줄) / 승인 게이트가 PR 리뷰보다 약함 / 사전 승인 워터폴이 자주 바뀌는 Figma와 미스매치(같은 명세 최대 14회 재작성, 하네스 커밋 비율 37% = 459/1,228) / 기계·AI·사람 역할 3군데 역전(시각 검증을 기계가 아니라 사람 눈이) / 기계가 읽을 데이터를 Markdown으로 관리 / Playwright가 118개 파일에서 `page.route()`로 서버를 재구현하면서 `toHaveScreenshot` 0건 / 제품 단위 테스트 0개인데 하네스 테스트 640줄 / 4층 문서 구조에서 요약층이 원본보다 먼저 썩음.
- **B 퍼블리싱**: 화면을 실제로 비교하는 검사 없음(B1, 가장 효과 큼) / "blocking"이라 선언한 component-map 게이트에 구멍 3개(`artifacts/` gitignore·승인 시 해시 안 함·스킬에 언급 없음) / 프롬프트가 없는 섹션(§7)을 가리킴 / 명세가 Figma 픽셀 전사로 비대(최대 528줄) / 명세 Status와 `approved.json` 불일치 21건 / `scenarioIds`가 장식(승인 ID가 실제 e2e에 있는지 아무도 안 봄) / 게이트가 자발적(호출처가 `run-scenarios.mjs` 한 곳) / 죽은 경로 4개. **loop-guard가 안 쓰인 이유**: AI가 성실히 에러 해시를 기록해야 작동하는데 그렇게 협조적인 AI는 애초에 무한루프에 안 빠진다 — 비협조 상황에서 작동 안 하는 가드는 가드가 아니다.
- **C API**: 실서버 파이프라인 전체가 죽은 코드(`real_server.enabled` 61/61 false, 407줄) / mock이 서버처럼 필터·정렬·페이징을 재구현해 "명세대로 짰다"까지만 증명(추측이 틀려도 초록불) / Notion을 단일 진실원이라 하면서 실제로는 Swagger와 교차검증(정식 단계 아님) / 기능당 승인 산출물 5종(301파일, 승인 커밋 191건) / 14단계 RUNBOOK이 실질 8단계 / 같은 규칙이 3곳에 중복·충돌(raw fetch 금지, `fileStorage.ts` 예외).
- **D 스킬·진입점**: 스킬이 2026-07-26 스냅샷으로 멈춤(그 사이 하네스 189커밋) / 4중 복제(`.claude`·`.codex`)가 이미 불일치 / 진입 경로 이중화.
- **E 횡단**: ESLint가 이미 강제하는 규칙(FSD 경계·`any`)을 산문으로 재선언해 어디까지 진짜 강제인지 헷갈림 / CI·훅 전무로 모든 게이트가 자발적 / 문서 35,070줄(md 512개)·스크립트+테스트 2,747줄·추적 파일 568개.

## 세션 기록에서 드러난 실제 막힘 (F)
- **F4 팀 규칙이 하네스에 없고 개인 AI 메모리에만 있음 — 윤호 쪽 최다 원인.** PR 제목=브랜치 이름, 이슈 먼저 만들고 브랜치 파기, 백업 브랜치 금지, CodeRabbit 답글 방식 등. 하네스·스킬·CLAUDE.md에서 "PR 제목"·"브랜치 이름" 검색 0건 → 지환의 AI는 모르고 새 세션마다 다시 말해야 함. 처방: `harness/shared/workflow.md`를 만들고 **지환과 합의한 것만** 채움(5173 포트·작업 폴더 같은 개인 환경 규칙은 개인 메모리에 남김). 대상: PR 제목·이슈 먼저·브랜치/백업 금지·커밋 형식·쪼개기·CodeRabbit 답글·e2e 격리 포트·스테이징 500 판별법.
- **F1 입력 기준이 바뀌어도 하네스에 반영 안 됨**: 9/7 명세가 폐기된 Figma 파일을 가리켜 전부 재작성, 9/17에도 AI가 폐기 파일을 조회해 "yot를 봐야지"로 재지시. 처방: Figma 파일 키·Notion DB 위치를 한 곳에만 두고 명세는 참조, 폐기 키가 남으면 검사 실패(폐기 키 13곳을 yot로 교체).
- **F2** 코드의 page 0→1 수정 뒤에도 명세·구현 계획에 0이 남아 CodeRabbit 지적 → 계약값은 JSON 한 곳. **F3** 승인 명령의 `--by <이름>`을 그대로 복사해 셸 오류 → `git config user.name`으로 채워 보여주기. **F5** Notion 명세의 옛 스키마·오타·반영 지연 → Swagger 교차검증 정식화. **F6** 규칙 문서(RUNBOOK·규칙·스킬)는 약 12번 수정에 8/26 이후 1번뿐인데 같은 기간 명세·승인 파일은 수십 번 — 규칙 변경 시 문서 갱신 절차(예: PR 템플릿 "하네스 영향 있음" 체크) 필요.
- **F7 화면 불일치**가 팀 전체 정정 원인 1위(37건), **F8 게이트 절차 비용**(게이트 때문에만 쓴 프롬프트 6%)은 하네스가 오히려 비용이 된다는 증거.

## 정정 지시 재집계 결과 (2026-10-01, 윤호는 전수 읽기, 지환은 별도 집계)
| 지표 | 윤호 | 지환 | 팀 합계 |
|---|---|---|---|
| 프롬프트 | 980 | 277 | 1,257 |
| 정정 지시 | 180 (18.4%) | 63 (23%) | 243 (19.3%) |
| 그중 하네스가 막았어야 할 것 | 65 (36%) | 38 (60%) | **103 (42%)** |
| 최다 원인 | 팀 규칙 누락 34 | 화면 불일치 21 | 화면 불일치 37 |
| 게이트 절차에만 쓴 프롬프트 | 51 (5.2%) | 24 (9%) | **75 (6.0%)** |
- 윤호 65건 내역: 팀 규칙 34(커밋 쪼개기 7·PR 양식 6·커밋 메시지 형식 5·이슈 먼저 5 등, 규칙 10종 모두 하네스에는 0종) / 화면이 Figma와 다름 16 / 입력 기준 11 / 절차 안 지킴 2 / 안내 틀림 2. 하네스 대상에서 뺀 것: 개인 환경 13·기능 버그 10·소통·범위·판단 92.
- **상충하는 정보 — 폐기된 첫 수치**: "26건/917개(2.8건/100개)"는 "아니·다시" 같은 키워드로 먼저 거른 값이라 누락이 많아 폐기. 지환의 13.7건/100개와 5배 차이도 세는 기준 차이(지환은 모든 정정을 센 뒤 "막을 수 있던 것"을 분류)였다. 세션에 따라 36%/60% 차이 일부도 분류 주체(윤호 쪽은 Claude, 지환 쪽은 본인 집계) 차이일 수 있음. 위키에는 한때 "팀 규칙을 넣으면 48%, 빼면 28%"라는 기준 미확정 메모가 있었고 팀 합의 후 노션·위키를 맞추기로 함(미해결).
- 개선 후 비교 지표: 정정 중 하네스로 막을 수 있던 비율 42%, 게이트 절차 프롬프트 6.0%, PR 제목 준수율 72.4%, 승인자 표기 6종, 사람 아닌 승인자 5건, 스킬-RUNBOOK 불일치 2곳, 해시 스크립트 574줄·죽은 경로 407줄(실서버 사용 0건)·스크린샷 비교 0건·최장 명세 528줄·CI 없음(기준 커밋 `fd42462`에서 재측정해 일치).

## 개선 순서 (우선순위, 비용)
1. **D2+D3** 스킬 두 줄 수정(⑭ 단계 추가, 퍼블리싱 스킬에 component-map 게이트) 10분 — 지금 품질을 깎는 중
2. **B3** `§7`→`§1`, 고아 규칙 흡수 10분
3. **C5+F3** `--by`에 AI 이름 거부(허용 목록)+명령 자동 채움 20분
4. **F4** 팀 규칙을 하네스로 — 30분+지환 합의
5. **F1** 입력 기준 한 곳으로 1시간
6. CI 1개(커밋·PR 형식·하네스 게이트 자동 검사) — 먼저 깨진 e2e를 처리해야 켜자마자 실패하지 않음(e2e 현황은 [[ToyVillage-Admin-FE/프로젝트-현황]])
7. **B1 스크린샷 게이트** — 원래 8순위였으나 화면 불일치 1위 근거로 7위로 상향 / **F8** 게이트 절차 줄이기(승인 명령 자동 채움·시나리오 ID 손입력 제거)
8. C1+B8 죽은 경로 삭제(521줄 이상), B2 component-map 승격+코드 검사, A1 해시→git SHA(574줄 제거), C3·C4·C6, B4·B5·D1·D4
9. 마지막: A2·A3 구조 개편(PR·CI 이전, 승인을 구현 뒤로) — 1~8 후 재측정하고 결정

## 변경 시 부작용과 대비
| 변경 | 부작용 | 대비 |
|---|---|---|
| A1 해시→git SHA | 기존 승인 기록 ~100건 형식 변경 | 한 번에 변환 스크립트, PR 하나 |
| C1·B8 죽은 경로 삭제 | 지환의 작업 중 브랜치가 삭제된 스크립트를 참조하면 깨짐 | 사전 공지, 열린 PR부터 머지 |
| D1~D4 스킬 정리 | `.claude`/`.codex` 한쪽만 고치면 또 어긋남(D3 재발) | 원본 1개를 양쪽이 참조 |
| A3 승인을 구현 뒤로 | 명세 없이 시작해 방향이 틀어질 위험 | 목적 한 줄만 먼저 합의 |
| F4 팀 규칙 추가 | 합의 없이 쓰면 한 사람의 취향이 규칙 | 합의한 것만 |
| 공통 | 동료가 바뀐 줄 모르고 옛 방식으로 작업 | PR 본문에 적고 공지 |
