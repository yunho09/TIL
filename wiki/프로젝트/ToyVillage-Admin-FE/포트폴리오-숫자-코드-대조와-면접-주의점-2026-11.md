# 포트폴리오 숫자 코드 대조와 면접 주의점 (2026-11-16~19)

토빌 포트폴리오(Figma 1~5쪽)를 면접 대비용으로 코드·GitHub·노션과 하나씩 대조해 **숫자를 고치거나 말할 때 붙일 조건**을 정리한 기록. 핵심 교훈: 포폴 숫자는 "센 기준"을 한 줄로 말할 수 있어야 하고, 코드로 다시 세면 다른 값이 나오는 항목이 있다(저장소 링크가 걸려 있어 면접관이 직접 셀 수 있음). 하네스 쪽 상세는 [[하네스-시스템]], 정정 측정 방법은 [[Claude-Code-세션-기록으로-정정-지시-측정]], 구조 설명은 [[FSD-lite-계층-구조와-배치-기준]].

- 꼬리질문: 업무·공지 화면 몇 개는 팀원이 7월에 처음 파일을 만들었고 본인이 다시 퍼블리싱·연동 → "처음 만든 화면을 다시 퍼블리싱하고 API 연동까지 했다".

## 정정 지시 측정: 팀 합산 결과와 포폴 반영 (11/16)
- 같은 스크립트·기준(rubric)으로 두 사람을 다시 센 결과(before 7/27~9/29 → after 10/21~11/9): 프롬프트 1,393 → 360, **하네스로 막을 수 있던 정정 103건 → 9건**, 100개당 **7.4 → 2.5건(−66%)**, 정정 중 비율 36.4% → 15.0%, **팀 규칙 재지시 55 → 0**, 화면이 Figma와 다름 32 → 6, 게이트 절차 프롬프트 6.0% → 7.5%(오히려 늘어남). 사람별 100개당: 윤호 5.7 → 1.7, 지환 13.4 → 3.9. 코드 고친 세션만 보면 8.4 → 4.0(−53%) — after에 포폴·글쓰기 세션이 많아 분모가 커졌기 때문.
- **옛 "1,257개·48%·49번"은 폐기**: 10/6에 한 사람은 키워드로 걸러(정정 64건 중 53건=83%) 다른 한 사람과 **세는 방식이 달랐고**, 그 평균이 48%였다. 같은 스크립트로 둘 다 다시 세니 개선 전이 1,393개·36%·55번. 결과만 새 값으로 바꾸면 문제 칸(48%)과 기준이 어긋나 면접에서 걸리므로 문제 칸도 같이 교체(5쪽: 문제 칸 "1,393개·36%·55번", 결과 카드 "100개당 7.4건 → 2.5건 / 팀 규칙 재지시 55 → 0").
- **100개당을 고른 이유**: ① 비율은 정정 전체가 같이 줄면 덜 움직이고 after 정정이 60건뿐이라 1건에 15.0 → 16.7%로 출렁임 ② 노션 계획(10월 초)에 "세션은 메시지 100개당으로 비교"라고 **측정 전에 정해 둔 기준**이라 "결과 보고 고른 게 아니라 미리 정한 기준"이라 답할 수 있음 ③ 작업량 기준 비교. 약점: 낯선 단위(한 줄 설명 준비), 글쓰기 세션 때문에 분모가 커짐. 문제 칸은 진단이라 비율(36%), 결과 칸은 100개당으로 둘을 나눠 쓴다.
- 해석 주의: 팀 규칙 55 → 0이 가장 확실한 근거(규칙 문서화+커밋·PR 형식 CI와 직결). 화면 불일치 32 → 6은 before 약 9주·after 약 3주라 그 사이 새 퍼블리싱이 적었다면 하네스 덕이 아닐 수 있음. 표본(after 하네스 대상 9건)이 작아 "360개 중 9건"으로 말한다. 분류는 Claude로 했다(공개 시 밝힘). 분류가 안정적인지: 같은 기준으로 다시 센 윤호 before 하네스 대상 62건 vs 10/1 최초 65건.
- 분류 실행 팁: `claude -p --output-format json --tools "" --setting-sources "" --strict-mcp-config --no-session-persistence`에 `CLAUDE_WIKI_CAPTURE=1 DISABLE_OMC=1`을 줘 훅·캡처가 끼지 않게 하고, 묶음(chunk)을 **하나씩 순차로** 돌려 `n` 순서가 맞는지 검증(토큰 절약 위해 병렬 서브에이전트를 피함). 프롬프트 원문에 JWT가 섞이므로 마스킹하고 저장소·공유에 올리지 않는다.

## 첫 로딩 성능 주장 7개 코드 대조 결과 (origin/develop 기준)
- **구현은 1~6 모두 확인**, 7(측정 방법)만 스크립트 없이 메모뿐. 이슈 번호: 코드 분할 #252/PR #254, 라이브러리 청크 #257/PR #261, 녹화 해시 #267/PR #268, WebP #262/PR #265, 팀 트리 캐시 #253/PR #260(모두 2026-10-19~20).
- **수치 차이(말할 때 기준 밝히기)**: 메인 JS가 PR #254에는 1,031 kB(gzip 282) → 247 kB(gzip 80)로, 메모에는 배포 빌드 1,307 kB(gzip 372)로 적혀 있다. 차이는 Sentry DSN 유무(DSN이 없으면 `initSentry`의 `if (!dsn) return` 이후가 빌드 때 죽은 코드로 제거) — 배경은 [[어드민-SPA-번들-성능-baseline과-최적화-우선순위]]. "693 kB → 0"은 react 287 + sentry 172 + vendor 107 + replay 126 ≈ 692~693 kB로 추정(보고자 계산).
- **라이브러리 청크 "장기 캐싱"**: 저장소에 캐시 헤더 설정이 없고(`wrangler.jsonc`만, `_headers` 없음) Cloudflare 기본 정책을 따른다 → "immutable"이라 단정하기 전에 실제 응답 헤더를 확인(ETag로 304여도 본문은 0 kB).
- **replay 해시 연쇄 버그(#267)**: 녹화 청크 `sentryReplay-*.js`(127 kB) 안의 설정 코드가 앱 공통 청크 `index-*.js`의 함수를 import → 청크 내용에 `./index-<hash>.js` 문자열이 들어가 앱 코드가 바뀌면 `index` 이름 → 녹화 청크 내용 → 해시가 연쇄로 바뀜. 해결은 `replay` 그룹(`@sentry/replay`만, `$initial` 없음)을 **맨 뒤**에 추가해 설정 청크만 0.66 kB로 남기고 라이브러리(126.19 kB)는 해시 고정 `sentry` 청크만 import하게 함(앞에 두면 `@sentry/core` 등 첫 화면 모듈까지 끌어와 녹화 청크가 첫 로딩에 붙음). 상세는 [[Vite-청크-그룹으로-라이브러리-분리와-해시-캐시]].
- **PDF 지연 로딩은 성능 작업 때 한 게 아니다**: `AttachmentPreviewDialog`의 `import type`(빌드에서 삭제)·`?url` 워커(경로 문자열만)·`await import('pdfjs-dist')`(PDF를 열 때만) 구조는 9/25 첨부 미리보기 최초 구현부터 있었다([[첨부파일-미리보기-모달]]). 크기 431,191 B + 워커 1,265,413 B는 주장과 일치.
- **WebP**: 핵심은 포맷보다 **표시 크기(136×114)의 2배(레티나)인 272×228로 축소** — 로고 PNG 390×328 142,732 B → 13,836 B, 프로필 64 kB → 8.3 kB. 빌드 플러그인 없이 미리 변환한 파일을 커밋. 이슈 #262가 이 로고를 로그인 LCP 후보로 지목.
- **업무 등록 화면 캐시**: `teamTreeQueryOptions`(`GET /team/tree`, p95 9초대)에 `staleTime 30분`·`gcTime 1시간`(전역 기본 staleTime은 60초), 업무 목록·상세 **mount 시 `useEffect`로 `prefetchQuery`**(hover·사이드바 방식 아님). 업무 등록의 `useQuery`가 같은 키라 캐시를 바로 씀. 낡는 문제는 팀 설정·직원 계정 생성/삭제/비밀번호 초기화에서 무효화로 해결. 병목이 화면 코드가 아니라 API 대기라 코드 분할 대신 캐시를 택함. e2e `team-tree-cache.spec.ts`가 요청 1회/계정 변경 뒤 2회를 확인. 한계: 0.37초는 **목록에 머문 뒤 들어갔을 때** 기준 — 주소로 바로 들어오면 그대로 9초를 기다리고, 서버가 빨라진 게 아니라 대기를 가린 것.
- **측정 방법**: 측정 스크립트·throttling/CDP 설정은 저장소에 없다. 기록은 이슈 #271과 노션 메모(사무실 Wi-Fi 가정: 지연 20 ms·30 Mbps·CPU 2배, 배포 빌드, 캐시 끔, 5회씩 전·후 번갈아, 측정 중 Sentry·GA 차단), 9/22 측정은 Slow 4G 1.6 Mbps/CPU 4x 중앙값. **로그인 LCP 356 → 216 ms는 "개선 전 5회 중 가장 느린 값 → 개선 후 5회 중 가장 빠른 값"**(10/21 본인이 정한 기준)이고 같은 측정의 중앙값은 344 → 224 ms(−35%). 포폴에 기준 괄호를 적어 두고, "중앙값인가요?"에는 중앙값을 같이 답할 수 있게 한다(대조 세션이 "중앙값으로 바꾸라"고 했다가 철회 — 기준을 숨기지 않는 것이 핵심).
- **트레이드오프 질문 대비**: 코드 분할 뒤 대시보드 재방문 LCP 552 → 818 ms로 느려짐. 처음엔 로컬 빌드(Sentry 빠짐, 1,031 kB)로 잘못 쟀고 번들 안 Sentry가 27 kB뿐인 걸 보고 발견 → 가짜 DSN을 넣은 배포 빌드(1,306 kB)로 재측정("실수한 경험" 답으로 재사용).

## 그 밖의 정확히 말해야 할 점
- Swagger 불일치 "22 → 0": 백엔드가 #232·#236으로 고쳐 11/4 스테이징에서 해소 확인했지만 `harness/api/swagger-known-diffs.json`에는 9건이 남아 있음(전부 실서버 201인데 Swagger가 200). 면접: "백엔드 수정은 11/4에 확인했고 예외 목록 파일만 정리 안 했다".
- 승인 일치율(63% → 89%, 99/111, API 65/65) 계산 스크립트는 없다(API는 `yarn harness:api:gate --all`, 퍼블리싱은 기능마다 `gate-check.mjs`로 집계 추정, CI엔 API 쪽만). e2e 1,483개 = `tests/e2e/**/*.spec.ts` 147개 파일의 정적 `test(` 호출 수(최상위 `for` 루프 36개 파일이라 실제 실행 수는 더 많을 수 있음), 4 shard ≈ 7분.
- 브랜치 보호(develop): 필수 검사 3개 + 승인 1명, strict=false (`gh api …/branches/develop/protection`으로 조회; 저장소 파일엔 기록 없음).
- 커밋 형식 83% → 100% 수치는 계산 스크립트가 없고 같은 검사기에 `COMMIT_RANGE`를 줘 재현. 버튼 라벨 "37곳"은 코드로 다시 세면 39·46곳.
- 노션 「첫 방문 회고」가 비어 있어 자기소개의 "비개발자와 업무 장면으로 이야기했다" 사례는 기록으로 확인 불가 → 본인 경험을 따로 준비.

## 맡은 일 설명 문구 (면접용 요약)
- 파일 CDN 분리: 공통 Axios는 "우리 API 서버 전용"(토큰 부착+401·403 재발급·로그아웃)이라 CDN 요청을 태우면 토큰이 CDN으로 새고 CDN 403이 로그아웃으로 번진다 → `fetchStoredFile`만 기본 `fetch`([[공용-인증-axios-외부도메인-토큰유출]]). 9/16 첨부 다운로드를 실제 파일로 바꾸며 도입. CDN = Content Delivery Network(정적 파일을 사용자 가까운 서버에서 전송).
- Swagger 22곳 해소: 계약과 Swagger가 다를 때 스테이징에 직접 요청(예: POST는 실제 201, Swagger는 200)해 어느 쪽이 틀렸는지 판정 → 계약 오류는 수정, Swagger 오류는 백엔드에 정정 요청(11/4 반영) + 화면 버그 2건·잘못된 API 경로 1건 발견.
- 스테이징 500 판별의 **가짜 주소** 정리([[팀-작업-규칙-하네스-문서]] 규칙 10): 알 수 있는 것은 ① 토큰이 정상인가(가짜 주소가 403이면 토큰 문제) ② 서버가 지금 없는 주소에 뭘 주는가(현재 500)뿐이다. "배포됨"은 500이 아닌 응답이면 가짜 주소 없이도 확정, "미배포"는 같은 500일 때 가능성이 높다까지만(최종은 백엔드 확인). 비중이 큰 작업이 아니고 포폴 PDF엔 없어 먼저 꺼내지 않는다.
- 하네스 명세 "없음" vs 빈칸: 값이 원래 없는 섹션은 지우지 말고 **"없음"**으로 쓰게 하고(Notion 명세 11개 섹션 순서 고정), 빈칸은 명세 누락으로 보고 AI가 추측하지 않고 멈춰 백엔드 질문 목록을 반환 — 설문의 "해당 없음" 체크 vs 미기재 차이. 규칙은 스크립트가 아니라 프롬프트·규칙 문서로 강제.
- CI 구성: `ci.yml`(정적 검사 job: lint·typecheck·style-policy·`test:harness`·`harness:api:gate --all` / e2e 4 shard + 결과 취합 job `e2e-result`로 shard 수를 바꿔도 필수 검사 설정 불변)과 `pr-format.yml`(커밋·PR 제목 형식, "~한다/~해요" 종결어미 금지). 상세는 [[PR-CI-설계-job-분리-e2e-샤딩-훅과-AI-토큰]], [[커밋-PR-형식-CI-검사-구현과-함정]].
