# backdrop-filter/blur + 애니메이션 배경 = 스크롤 끊김

`backdrop-filter: blur()`나 `filter: blur()`가 걸린 레이어의 **아래 배경이 매 프레임 바뀌는 상태**(줌/크로스페이드 사진, `scale()` 애니메이션 블롭 등)라면, 블러 레이어 자체는 가벼워 보여도 브라우저가 매 프레임 그 아래를 다시 래스터화해야 해서 스크롤·애니메이션이 눈에 띄게 끊긴다. sticky 헤더에 `backdrop-filter`를 걸어둔 경우 **스크롤할 때마다** 같은 재계산이 반복된다.

## 진단 순서

끊김의 범인을 추측하지 말고 측정 순서대로 좁힌다.

1. 캔버스/JS 렌더 루프가 있다면 먼저 의심하기 쉽지만, `requestAnimationFrame`이 안 도는 환경(숨겨진 브라우저 팬 등, [[브라우저-팬-숨김-상태-rAF-정지-테스트-우회]] 참고)에서도 **같은 draw 함수를 동기로 여러 번 호출해 걸린 시간을 재면** 실측 프레임당 비용을 알 수 있다. 이 방식으로 "캔버스는 프레임당 0.38ms(16.7ms 예산의 1% 미만)"처럼 캔버스가 범인이 아님을 먼저 배제할 수 있었다.
2. 캔버스가 아니라면 DOM을 훑어 `backdrop-filter`/`filter:blur()`가 걸린 요소를 전수 조사하고, 그 요소의 배경이 애니메이션 중인지(줌/크로스페이드 사진, `scale()` 트랜지션 등) 확인한다.
3. 캔버스 자체의 백킹 스토어 크기도 `devicePixelRatio`를 그대로 곱하면 예상보다 훨씬 커질 수 있다(예: DPR 2에서 1280×720 캔버스가 실제로는 2048×1152로 렌더링). DPR을 1로 캡하는 것도 비용을 줄인다.

## 해결

- `blur()`/`backdrop-filter`를 걷어내고, 같은 시각 효과(흐릿하게 겹쳐 보이는 유리 느낌)는 **배경색 불투명도를 높이는 것으로 보상**한다(예: `rgba(..,0.72)+blur(16px)` → `rgba(..,0.86)`, 블러 없음).
- 페이지마다 블러가 걸린 요소의 클래스가 다르면, CSS로 일일이 잡는 대신 런타임에 `getComputedStyle`로 `backdrop-filter`/`filter`가 `none`이 아닌 요소를 전수 탐색해 제거하고 배경색을 보정하는 함수를 만들어두면 재사용할 수 있다.
- 프레임 비용이 실측으로 임계값(예: 8ms)을 넘으면 스스로 품질을 낮추는 자가 저하(self-degrade) 로직을 넣어두면, 측정이 불가능한 원격 환경에서도 각 기기가 알아서 적정 수준으로 낮춘다.
