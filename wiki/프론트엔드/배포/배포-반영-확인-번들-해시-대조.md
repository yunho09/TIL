# 배포 반영 여부는 번들 해시와 번들 내 문자열로 확인한다

"고쳤는데 사이트에선 그대로"일 때, 소스(`develop`)가 아니라 **배포된 번들**을 직접 받아 본다. Vite 빌드 산출물의 파일명 해시(`assets/index-XXXX.js`)가 바뀌었는지, 수정으로 새로 생긴/사라진 문자열이 번들에 있는지가 가장 확실한 증거다.

## 방법
1. `curl`로 사이트 HTML에서 `assets/index-*.js` 경로를 얻고 번들을 내려받는다(Basic 인증이 앞에 있어도 브라우저가 이미 통과했으면 같은 자격으로 접근 가능했음).
2. **수정 전 해시와 비교** — 같으면 미배포.
3. 수정으로 **새로 생긴 식별자**(예: `fieldErrors`)는 있어야 하고 **지운 코드**(예: `employmentType:""`)는 0건이어야 한다. `scrollIntoView`, `role="alert"` 같은 흔한 문자열은 라이브러리 코드에서도 나와 **오탐**이라 근거로 쓰지 않는다.
4. 번들에서 요청 본문 생성부를 추출해 보면 "소스는 맞는데 배포본은 구버전"을 바로 가린다(예: 배포본이 `division:n.department.trim(), employmentType:""` 전송).

## 배포는 `main`만 트리거한다
- Commonly-FE는 `develop` 머지만으로는 배포되지 않고 `develop → main` PR 머지가 필요. 감사 당시 배포본이 `main` 734a65e(3주 전)라 `develop`에서 이미 고친 버그가 운영에 그대로 있었다. 소스(develop)만 보고 감사하면 라이브 결과와 어긋난다 → **감사 기준은 배포 커밋/번들**.
- 반영 소요: PR #88 머지(19:56 KST) → 새 번들 20:03, **약 7분**. 해시 변경이 보일 때까지 폴링.
- PR 머지(`#87` → develop)와 배포용 PR(`#88` → main)을 혼동하지 않는다 — `origin/main`이 안 움직였으면 배포 트리거가 없었던 것이다.

## 배포 방식 (정정)
- 처음에 커밋 메시지(`ci: use Portainer polling for deployment`)만 보고 "폴링"이라 단정했으나, 사용자가 **웹훅 방식**이라고 정정. 배포 문서(`deploy/PORTAINER.md`)와 실제 동작을 근거로 확인하지 않고 커밋 제목만으로 단정한 게 문제였다. 기존 [[Commonly-FE/프로젝트-현황]]의 "폴링" 서술과 충돌하므로 그 페이지에 병기해 뒀다.
- 이 레포엔 GitHub Actions(CI)가 없어 PR에 빌드 체크가 안 붙는다 → 타입 오류가 머지돼도 배포 빌드에서야 드러난다. 로컬에서 `turbo run lint build`로 검증하고, 캐시 영향 의심 시 `dist`를 지우지 말고 `--force`를 쓴다.
