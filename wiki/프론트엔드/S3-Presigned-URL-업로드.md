# S3 Presigned URL 업로드

서버가 파일을 대신 받지 않고, **서명된 임시 업로드 URL만 발급**해주면 브라우저(클라이언트)가 그 URL로 S3에 직접 파일을 PUT하는 방식. 일반적인 흐름:

1. 클라이언트 → 서버: `{ type, file_name }` 등으로 presign 요청 (보통 인증 필요)
2. 서버 → 클라이언트: `{ file_path, pre_signed_url }` 응답 (URL에 만료시간·서명 포함)
3. 클라이언트 → S3: `pre_signed_url`로 파일 바이너리를 직접 `PUT`
4. 클라이언트 → 서버: 업로드 완료 후 `file_path`만 본 요청(예: 지원서 제출)에 포함해서 전송

## 지키지 않으면 깨지는 규칙

- **presigned URL에는 이미 서명(쿼리스트링의 `X-Amz-Signature` 등)이 들어있다.** 이 요청에 애플리케이션의 `Authorization` 헤더(JWT 등)를 붙이면 서명이 깨져서 S3가 요청을 거부한다. 따라서 "presign 발급"은 인증이 걸린 HTTP 클라이언트로, "S3로의 실제 PUT"은 **인증 헤더가 없는 별도 클라이언트**(순수 axios 인스턴스 등)로 분리해야 한다.
- **브라우저가 S3에 직접 요청하므로 버킷에 CORS 설정**(`PUT`/`OPTIONS` 허용 + 프론트 origin이 allow-list에 있어야 함)이 없으면, 파일 자체는 S3에 정상적으로 올라가는데도 브라우저가 응답을 CORS 위반으로 막아버려서 클라이언트 입장에서는 "업로드 실패"로 보인다. 로컬 재현 가능한 흔한 함정.
- presigned URL은 **만료시간이 짧을 수 있다**(예: `X-Amz-Expires=119` ≈ 2분). 대용량 파일이나 느린 회선에서는 업로드 도중 만료될 수 있어 고려가 필요하다.
- 공통 HTTP 클라이언트에 전역 `timeout`(예: 10초)이 걸려 있으면, 업로드처럼 오래 걸리는 요청에는 별도로 더 긴 timeout(예: 60초)을 지정해야 한다. 그러지 않으면 서버가 정상 수신 중인데도 클라이언트가 먼저 타임아웃으로 끊는다.

## 테스트로 검증할 때의 함정

Playwright 같은 도구로 route를 가로채 목킹할 때, **요청의 Blob 바디는 읽을 수 없다**(`postDataBuffer()`가 `null`을 반환). 파일이 실제로 몇 바이트, 어떤 내용으로 전송되는지 확인하려면 목킹 대신 **presigned URL 자리에 실제 로컬 HTTP 서버를 띄워** 요청을 직접 받아서 바이트 수·내용을 비교해야 한다. 이 방식은 부수적으로 실제 CORS preflight가 타는지도 함께 확인할 수 있다.
