Playwright의 `webServer.reuseExistingServer`(보통 `!CI`로 설정)가 켜져 있으면, 지정한 baseURL 포트에 이미 떠 있는 아무 서버나 그대로 재사용한다. 그 서버가 어떤 백엔드를 향하는지는 Playwright가 확인하지 않으므로, mock으로 막지 않은 요청이 조용히 실제 서버로 새어 나갈 수 있다.

## 함정 두 가지

- **다른 프로젝트가 같은 포트를 점유**: 엉뚱한 앱이 응답해 관련 없는 404가 쏟아진다.
- **자기 프로젝트의 dev 서버가 실서버를 향하고 있을 때**: `.env`의 `VITE_API_BASE_URL`이 staging 같은 실 주소면, e2e에서 mock으로 안 막은 요청이 로그인 mock 등으로 만든 **가짜 토큰을 단 채로 실제 staging에 나간다**. "이번 e2e는 실 서버 요청 없이 mock으로만 검증했다"고 보고했다가, 나중에 이 재사용 구조 때문에 그 보고가 틀렸다는 걸 알게 된 사례가 있다.

## 판별법

같은 스위트를 **격리 포트(예: 5199) + 도달 불가능한 API 주소**로 새로 띄운 서버에서 다시 돌려 실패 개수를 비교한다.

- 실패 개수가 같으면 → 재사용/유출과 무관한 기존 실패.
- 실패 개수가 다르면 → 유출이 실패에 영향을 주고 있었다는 뜻.

`PLAYWRIGHT_BASE_URL=http://localhost:5199 CI=1 <test command>`처럼 `CI=1`을 강제하면 `reuseExistingServer`가 꺼져 항상 새 서버를 띄운다.

## 대응

- 로컬에서 전체 e2e를 돌릴 땐 CI와 같은 조건(새 서버 + 격리된/도달 불가 API 주소)을 강제한다.
- "실 서버 호출 없음"을 보고할 땐 mock 커버리지만이 아니라, 그 mock을 검증한 서버가 재사용된 것인지도 확인해야 한다.

## 같은 코드인데 실행마다 결과가 갈릴 때: 머신 부하 (2026-09-21 추가)

전체 e2e를 여러 번 돌리면 같은 코드가 1230·1232 passed(실패 0)였다가 어떤 실행에선 1233 passed / **45 failed**가 나왔다. 실패 대부분은 5초 타임아웃에 걸리는 "응답 전에는 로딩 상태를 표시한다" 류였고, 실행 당시 load average가 11을 넘었다. 병렬로 여러 spec을 동시에 돌릴 때 생기는 **부하 의존 실패**였다.

- **판별 3종 세트** (내 변경 탓인지 가르는 법):
  1. 실패한 spec들만 모아 **내 코드로** 재실행 → 17~18 failed
  2. 같은 spec들을 **변경 이전 베이스 커밋**(worktree/체크아웃)으로 재실행 → 16 failed (거의 같은 수면 내 변경과 무관)
  3. 실패 spec 하나만 **단독** 실행 → 전부 통과(부하 없이는 안 깨짐)
- 베이스라인 16 vs 내 코드 17~18의 차이는 노이즈 범위지만 0은 아니다. 전환마다 0.12~0.24초를 더하는 변경은 **타이밍이 빡빡한 테스트를 더 불안정하게 만들 여지**가 있다(증거는 없고 가능성만).
- 이전에 기록된 "94개 무관 실패"(2026-09-13 기준)도 같은 계열의 기존 불안정으로 메모돼 있었다. 필요하면 "부하 상황에서 흔들리는 e2e 안정화"를 별도 이슈로 판다(Claude 제안, 사용자 결정 대기).
- **주의**: 백그라운드로 돌린 e2e가 세션 종료로 `[killed]`만 남기고 끝나는 경우가 있다. 이 상태를 "통과"로 보고하면 안 되고, 마지막 커밋에 대한 결과가 없다고 밝힌 뒤 다시 돌려야 한다. 이전 커밋의 통과 수치를 새 커밋의 검증으로 쓰지 않는다.
