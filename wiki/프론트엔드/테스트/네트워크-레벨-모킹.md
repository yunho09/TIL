# 네트워크 레벨 모킹

프론트엔드 e2e 테스트에서 서버 응답을 흉내 낼 때, **어느 계층에서 가짜를 끼우느냐**로 방식이 갈린다. 네트워크 레벨 모킹은 `fetch`/`XMLHttpRequest` 직전, 즉 요청이 실제로 네트워크에 나가기 직전에 가로채 응답만 대신 만들어주는 방식이다.

## 어느 레벨에서 가로채는가

```
컴포넌트 → 데이터 계층(React Query 등) → HTTP 클라이언트(axios) → fetch/XHR → 네트워크 → 서버
```

- **함수 교체** (`getTasks()` 자체를 가짜 함수로 바꿔치기) — 쉽지만 axios 설정·헤더·응답 파싱·에러 처리가 전혀 검증되지 않는다. "테스트는 통과하는데 실제로는 깨지는" 원인이 되기 쉽다.
- **네트워크 레벨 가로채기** (`fetch`/`XHR` 직전에서 끊음) — 앱 입장에서는 진짜로 요청을 만들어 보내고 응답을 파싱하고 실패하면 에러 처리를 한다. axios 인터셉터(토큰 부착 등)까지 전부 실제 코드가 돈다. **여기서 다루는 방식.**
- **진짜 서버** — 가장 정확하지만 느리고 백엔드가 있어야 하며 500/타임아웃 같은 상황을 임의로 만들기 어렵다.

## 구현 기술 (도구별)

| 방식 | 대표 도구 | 특징 |
|---|---|---|
| Service Worker | MSW (브라우저) | 앱 코드 전혀 안 건드림, 개발 중 브라우저에서도 재사용 가능 |
| 브라우저 제어 프로토콜 (CDP) | Playwright `page.route`, Cypress `cy.intercept` | 문서·이미지·스크립트 요청까지 다 가로챌 수 있음 |
| Node 모듈 패치 | nock, MSW(Node) | Node에서 도는 코드(SSR 등)용, `http`/`fetch`를 런타임에 패치 |
| 프록시 서버 | WireMock, Mockoon | 별도 프로세스, 언어 무관이라 팀 간 공유 쉬움 |

## 가로챈 뒤 취할 수 있는 행동 (Playwright 기준)

```ts
route.fulfill({ status, body })   // 내가 답한다 — 서버로 안 나감
route.continue()                  // 그대로 통과시킨다 — 요청을 고쳐서 보낼 수도 있음
route.abort()                     // 네트워크 에러로 실패시킨다
route.fallback()                  // 다음 핸들러에게 넘긴다 (조건부 가로채기에 사용)
```

## 응답을 만드는 세 가지 패턴

- **고정 응답** — 가장 단순, 항상 같은 답.
- **대본형(scripted)** — 호출 순서에 따라 다른 답을 미리 못박아둔다. "삭제 후 재조회하면 줄어든 목록이 온다"처럼 **계약 준수**를 검증하는 데 적합. 앱이 재조회를 안 하면 호출 카운트가 안 늘어 테스트가 실패한다.
- **상태형(stateful)** — 메모리에 배열 등으로 상태를 들고 진짜 서버처럼 CRUD를 반영한다. "생성 후 목록에 뜨는지" 같은 **사용자 흐름**을 검증하는 데 적합하다.

대본형은 계약 검증에, 상태형은 흐름 검증에 맞는다 — 한 프로젝트에 두 방식이 공존할 수 있다(예: 승인된 contract를 검증하는 API 스펙은 대본형, 화면 흐름을 검증하는 기능 스펙은 상태형 공유 헬퍼).

## 실제로 걸리는 함정들

- **등록 순서**: Playwright는 **나중에 등록한 route가 먼저 매칭**된다. 공통 기본값을 먼저 걸고 개별 테스트가 필요한 것만 나중에 걸어 덮어쓰는 구조가 성립하는 이유다. 반대로 알고 있으면 덮어쓰기가 안 먹는다.
- **등록 시점**: 페이지가 이미 요청을 보낸 뒤에 route를 걸면 못 잡는다. 반드시 `page.goto()` 전에 걸어야 한다.
- **Service Worker 우회**: 페이지에 서비스 워커가 떠 있으면 요청이 그쪽으로 새서 가로채기를 우회할 수 있다. 실제 서버를 때리는 테스트 레인에서는 `serviceWorkers: 'block'` 설정으로 아예 막아두는 경우가 있다.
- **안 잡힌 요청은 조용히 진짜로 나간다**: 패턴에 안 맞으면 실제 네트워크로 나간다. 테스트가 의도치 않게 외부 서버를 때리는 사고의 원인이다. 민감한 레인에서는 `**/*`로 전부 잡아놓고 화이트리스트만 통과시키는 가드가 필요하다. 추가 안전장치로 e2e용 API base URL 자체를 `https://api.e2e.invalid`처럼 **DNS에 존재할 수 없는 도메인**으로 잡아두면, route 매칭에서 빠져나간 요청이 있어도 실제 스테이징으로 새는 대신 확실하게 실패한다 — 위 화이트리스트 가드와 이중으로 걸 수 있는 방어선이다. `reuseExistingServer`로 격리 포트를 안 쓰는 상황과 함께 쓰면 유출을 더 확실히 막는다([[Playwright-reuseExistingServer-실서버-유출]]).
- **패턴 정확도**: 쿼리스트링 유무로 매칭이 어긋나는 경우가 흔하다. `/\/api\/tasks(?:\?.*)?$/`처럼 쿼리스트링을 옵셔널로 열어두고, 컬렉션 경로와 아이템 경로가 서로 겹치지 않게 `[^/?]+`로 끊어야 한다.
- **오리진 미검증**: pathname만 보고 origin(스킴+호스트+포트)을 안 보면, 요청이 엉뚱한 서버(API 서버, 앱 자기 오리진 등)로 새도 경로 문자열만 같으면 mock이 그대로 잡아버려 테스트가 계속 통과한다. 특정 외부 서버로 가야 한다는 것 자체를 검증하려면 매처와 기대값 양쪽에 origin을 넣어야 한다 — 자세한 사례는 [[Playwright-mock-오리진-미검증]].

## 이 방식으로 검증되는 것 / 안 되는 것

```
✅ 요청 URL·쿼리·메서드가 명세대로인가
✅ Authorization 헤더가 붙는가 (인터셉터 동작 포함)
✅ 요청 본문이 계약대로인가
✅ 응답 파싱·형식 검증
✅ 400·401·500 에러 화면 처리
✅ 로딩/빈 상태/재조회 타이밍, 캐시 무효화

❌ 서버가 실제로 그렇게 응답하는가  ← 가장 큰 구멍 (contract drift)
❌ 인증 토큰이 실제로 유효한가
❌ CORS·프록시·인프라 설정
❌ 성능·동시성
```

마지막 항목들이 이 기법의 한계다. 실무에서는 이를 보완하기 위해 **계약(contract) 승인 + 해시 동결로 가짜 응답이 승인된 명세에서만 파생되도록 강제**하거나(개발자가 임의로 가짜 데이터를 지어내지 못하게), 별도의 **실 서버 호출 레인**을 두어 가끔 진짜로 검증하는 구조를 함께 쓴다. 더 엄격하게 가려면 **Pact** 같은 contract testing 도구로, 프론트가 기대하는 응답을 파일로 내보내고 백엔드 CI가 그걸 검증하게 만들 수도 있다.

### 해시 동결의 목적: 테스트를 고쳐서 통과시키는 걸 막는다

승인 워크플로에서는 사람이 계약·구현계획·테스트 시나리오를 검토·승인한 뒤, 실제로 작성된 e2e 파일의 해시를 기록해 "동결"한다. 이후 검증 스크립트는 파일 해시가 기록과 다르면 테스트를 아예 돌리지 않고 실패시킨다.

목적은 **구현이 테스트를 통과하지 못할 때, 코드 대신 테스트 쪽을 고쳐서 통과시켜 버리는 행위**(특히 AI 코딩 에이전트가 하기 쉬운 지름길)를 막는 것이다. "승인된 시나리오 = 실제로 도는 테스트"라는 대응 관계를 해시로 강제한다.

**한계**: 해시가 테스트 파일 자체만 잡고, 그 파일이 import하는 공용 헬퍼/모듈까지는 포함하지 않으면 구멍이 남는다 — 테스트 파일은 그대로 둔 채 헬퍼만 고쳐서 사실상 검증 내용을 바꿔치기해도 동결을 우회할 수 있다.

## 요약

앱은 평소대로 요청을 만들고 파싱하고 처리한다 — 마지막 순간에 답하는 주체만 서버에서 테스트 코드로 바뀐다. 그래서 함수 교체 모킹보다 실제 코드 경로를 훨씬 많이 통과하면서도, 진짜 서버 호출보다 빠르고 결정적이며 에러 상황을 임의로 만들 수 있다.
