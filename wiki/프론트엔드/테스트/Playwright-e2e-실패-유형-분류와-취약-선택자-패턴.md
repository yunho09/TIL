# Playwright e2e 실패 유형 분류와 취약 선택자 패턴

e2e 실패를 "테스트를 짠 방식 때문"과 "구현이 바뀌었는데 테스트가 안 따라간 것(드리프트)"으로 나누면 대응이 갈린다. 전자는 **작성 규칙**으로, 후자는 **전체 스위트를 도는 CI**로 막는다. 아래는 ToyVillage-Admin-FE에서 팀원이 로그 250여건을 분석한 결과와 develop 전체 재측정(53/1,387)을 합친 정리다.

## 취약 선택자 패턴 (팀원 분석, 요소 못 찾음 109건 중 51건)
공통점: **바뀔 수 있는 값이 선택자 안에 들어 있다** (항목 번호, mock 데이터 이름, 데이터 개수, DOM 깊이).
- **토스트·에러 배너 (15건)**: `getByRole('alert')`는 토스트가 몇 초 뒤 사라지면 확인 시점에 이미 없고, alert이 여러 개 떠 있으면 strict mode로 실패. → 나타나는 시점에 바로 확인.
- **번호로 조합한 라벨 (14건)**: 폼 편집기가 접근성 라벨을 `N번 항목 M번 선택지`로 만들고 테스트도 그 문자열로 찾으면, 항목을 중간에 추가·삭제할 때 번호가 밀려 엉뚱한 입력칸을 가리킨다.
- **mock 값이 선택자에 박힘 (10건)**: 라벨이 `직원 이름 + 배정 추가`이면 mock 이름만 바꿔도 실패. 페이지 번호 버튼은 전체 페이지가 2 이상일 때만 생겨서 데이터 개수·페이지 크기를 바꾸면 사라진다.
- **범위가 너무 넓음 (6건)**: 본문 전체에서 버튼을 찾으면 하나만 늘어도 여러 개가 매칭돼 Playwright가 실행을 거부(strict mode). → `region`·`dialog`·`row` 안에서 찾기.
- **DOM 계층을 순서로 탐색 (3건)**: 행 인덱스 → 자식 → span 순으로 더듬으면 감싸는 요소 하나 추가에 깨진다.
- **필수 별표 텍스트 (3건)**: 별표가 (공백 없음/공백 있음/다른 컴포넌트) 세 형태로 그려지고, 한 화면에 필수 항목이 여럿이면 별표도 여럿이라 "정확히 `*` 한 글자" 매칭이 실패.

## 드리프트 실패 (develop 전체 재측정, 53건 중 49건)
- **여러 화면에 걸친 변경이 다른 기능의 테스트를 깬다**: 401·403이면 로그인 화면으로 보내는 전역 로그아웃 반영 누락 11건(약 4주 방치), 스켈레톤 도입으로 `~를 불러오는 중입니다` 문구가 소스에서 사라져 9건.
- 기능별로 자기 e2e만 돌리고 전체를 돌리는 CI가 없으면 아무도 모른다 → **전체 e2e를 PR마다 돌리는 CI가 해법**. 단 CI를 켜려면 기존 실패부터 정리해야 켜자마자 빨갛지 않는다.
- 구분: 팀원 분석의 "구현 상태 때문의 실패 58건"은 화면을 만들거나 디자인 개편 중에 돌려서 난 **일시적** 실패(문구는 소스에 그대로 있었음)라 작업이 끝나면 통과한다. 재측정의 49건은 **방치형** — 고칠 때까지 계속 실패.

## 그 밖에 재측정에서 나온 테스트 작성 함정
- `getByRole('status')`가 스켈레톤 표와 성공 토스트를 동시에 잡아 strict mode 위반, 또는 스켈레톤 표의 제목 글자를 읽음.
- 케밥 메뉴가 닫히는 **퇴장 애니메이션 동안 메뉴가 2개** 남아 `수정` 항목이 2개 매칭([[퇴장-애니메이션-언마운트-지연과-useExitAnimation]]).
- 모달 크기를 열리는 애니메이션 도중에 재서 600×300이 593.96×296.98로 측정 → 크기는 애니메이션이 끝난 뒤 잰다.
- 로그인 화면 S11처럼 **병렬 실행에서만 흔들리는 테스트**가 있어 재실행 시 실패 수가 한두 개 달라질 수 있다 (관련: [[Playwright-오토스크롤-화면기준-위치측정-오염]]).

## 숫자를 비교할 때의 함정
- "실패 로그 250여건"은 여러 번 돌린 로그를 모은 **로그 건수**, "53개"는 한 시점에 한 번 돌린 **실패 테스트 개수**라 같은 테스트가 3번 실패하면 3건 vs 1개 — 직접 비교 불가. 같은 단위(한 번 돌린 결과끼리)로만 비교: 9/17 96/1,068(9.0%) → 10/6 53/1,387(3.8%).
- 퍼센트의 분모를 명시해야 한다: 250건 기준이면 요소 못 찾음 109건은 44%, 선택자 문제 51건은 20%(팀원의 "30%"는 기준 확인 필요).
- 누적 실패 건수(윤호 세션 9/7~10/6, 실패 1,980건)에는 전체 실행 10번에서 같은 기존 실패 약 94건이 반복된 648건이 포함 — 같은 실패를 계속 다시 만나는 비용의 지표로는 쓸 수 있지만 "실패 비율 43%"는 작업 중 정상 실패가 섞여 개선 지표로 부적절.
- 유형 비율(에러 내용이 남은 176건 기준): 값이 다름 37%, 요소 못 찾음 28%(시간 초과 중 요소 대기 24건 합치면 41%), 시간 초과 23%, 주소 다름 9%, strict mode 4%. 출력이 `tail`/`grep`으로 잘린 나머지 91%는 건수만 남아 표본 편향이 있다.
