# Playwright e2e 실패 유형 분류와 취약 선택자 패턴

e2e 실패를 "테스트를 짠 방식 때문"과 "구현이 바뀌었는데 테스트가 안 따라간 것(드리프트)"으로 나누면 대응이 갈린다. 전자는 **작성 규칙**으로, 후자는 **전체 스위트를 도는 CI**로 막는다. 아래는 ToyVillage-Admin-FE에서 팀원이 로그 250여건을 분석한 결과와 develop 전체 재측정(53/1,387)을 합친 정리다.

## 취약 선택자 패턴 (팀원 분석, 요소 못 찾음 109건 중 51건)
공통점: **바뀔 수 있는 값이 선택자 안에 들어 있다** (항목 번호, mock 데이터 이름, 데이터 개수, DOM 깊이).
- **토스트·에러 배너 (15건)**: `getByRole('alert')`는 토스트가 몇 초 뒤 사라지면 확인 시점에 이미 없고, alert이 여러 개 떠 있으면 strict mode로 실패. → 나타나는 시점에 바로 확인.
- **번호로 조합한 라벨 (14건)**: 폼 편집기가 접근성 라벨을 `N번 항목 M번 선택지`로 만들고 테스트도 그 문자열로 찾으면, 항목을 중간에 추가·삭제할 때 번호가 밀려 엉뚱한 입력칸을 가리킨다.
- **mock 값이 선택자에 박힘 (10건)**: 라벨이 `직원 이름 + 배정 추가`이면 mock 이름만 바꿔도 실패. 페이지 번호 버튼은 전체 페이지가 2 이상일 때만 생겨서 데이터 개수·페이지 크기를 바꾸면 사라진다.
- **범위가 너무 넓음 (6건)**: 본문 전체에서 버튼을 찾으면 하나만 늘어도 여러 개가 매칭돼 Playwright가 실행을 거부(strict mode). → `region`·`dialog`·`row` 안에서 찾기.
- **DOM 계층을 순서로 탐색 (3건)**: 행 인덱스 → 자식 → span 순으로 더듬으면 감싸는 요소 하나 추가에 깨진다.
- **필수 별표 텍스트 (3건)**: 별표가 (공백 없음/공백 있음/다른 컴포넌트) 세 형태로 그려지고, 한 화면에 필수 항목이 여럿이면 별표도 여럿이라 "정확히 `*` 한 글자" 매칭이 실패.

## 드리프트 실패 (develop 전체 재측정, 53건 중 49건)
- **여러 화면에 걸친 변경이 다른 기능의 테스트를 깬다**: 401·403이면 로그인 화면으로 보내는 전역 로그아웃 반영 누락 11건(약 4주 방치), 스켈레톤 도입으로 `~를 불러오는 중입니다` 문구가 소스에서 사라져 9건.
- 기능별로 자기 e2e만 돌리고 전체를 돌리는 CI가 없으면 아무도 모른다 → **전체 e2e를 PR마다 돌리는 CI가 해법**. 단 CI를 켜려면 기존 실패부터 정리해야 켜자마자 빨갛지 않는다.
- 구분: 팀원 분석의 "구현 상태 때문의 실패 58건"은 화면을 만들거나 디자인 개편 중에 돌려서 난 **일시적** 실패(문구는 소스에 그대로 있었음)라 작업이 끝나면 통과한다. 재측정의 49건은 **방치형** — 고칠 때까지 계속 실패.

## 숫자를 비교할 때의 함정
- "실패 로그 250여건"은 여러 번 돌린 로그를 모은 **로그 건수**, "53개"는 한 시점에 한 번 돌린 **실패 테스트 개수**라 같은 테스트가 3번 실패하면 3건 vs 1개 — 직접 비교 불가. 같은 단위(한 번 돌린 결과끼리)로만 비교: 9/17 96/1,068(9.0%) → 10/6 53/1,387(3.8%).
- 퍼센트의 분모를 명시해야 한다: 250건 기준이면 요소 못 찾음 109건은 44%, 선택자 문제 51건은 20%(팀원의 "30%"는 기준 확인 필요).
- 누적 실패 건수(윤호 세션 9/7~10/6, 실패 1,980건)에는 전체 실행 10번에서 같은 기존 실패 약 94건이 반복된 648건이 포함 — 같은 실패를 계속 다시 만나는 비용의 지표로는 쓸 수 있지만 "실패 비율 43%"는 작업 중 정상 실패가 섞여 개선 지표로 부적절.
- 유형 비율(에러 내용이 남은 176건 기준): 값이 다름 37%, 요소 못 찾음 28%(시간 초과 중 요소 대기 24건 합치면 41%), 시간 초과 23%, 주소 다름 9%, strict mode 4%. 출력이 `tail`/`grep`으로 잘린 나머지 91%는 건수만 남아 표본 편향이 있다.

## 간헐 실패 원인 확정 (2026-10-21, #264): 기다림 누락 2종과 CI 재시도
앱 결함이 아니라 **테스트가 기다려야 할 때 안 기다려서**, CI 머신이 느린 날에만 실패했다.
- **클릭 전부터 이미 참인 조건을 대기 조건으로 쓴 경우** (로그인 401 테스트): 클릭 뒤 "아이디 값 유지·URL `/login`"을 확인했는데 둘 다 클릭 전부터 참이라 즉시 통과 → 응답 오기 전에 저장소(토큰)를 읽음. 해결: 앱이 **세션을 지운 뒤 띄우는** 실패 안내 문구가 보일 때까지 기다린 뒤 토큰 확인 (결과가 나타난 뒤에야 참이 되는 신호를 기다린다).
- **`확인` 버튼 → 다음 프레임 포커스 이동과 입력의 경합** (휴무일 생성·수정 검증 테스트): 앱은 검증 다이얼로그 `확인` 직후 다음 프레임(약 16ms 뒤)에 문제 칸으로 포커스를 옮기는데, 테스트가 바로 다른 칸에 입력하면 느린 머신에서 포커스가 입력 도중 옮겨져 글자가 엉뚱한 칸에 들어가고 기대한 오류가 안 뜸. 해결: `확인` 뒤 `toBeFocused()`로 포커스 이동을 기다린 뒤 입력. 사람은 16ms 안에 입력 못 하므로 **앱 코드는 안 고침**.
- **실패 로그가 가리킨 증거 (10/11~10/19 CI)**: 로그인 401 테스트는 3번 모두 `expect(received).toBeNull()` / `Received: "expired"` — `"expired"`는 테스트가 시작할 때 넣어 둔 이전 토큰이라 "지워지기 전에 읽었다"는 직접 증거. 서버는 진짜가 아니라 `page.route`의 가짜 서버(CI 머신 안에서 즉시 401)라 **네트워크가 느린 게 아니라** 401 수신→axios 에러→`catch`→`clearSession()`까지 앱 내부 처리가 CI 머신이 바쁠 때 늦는 것이다("서버 응답이 느려서"라고 쓰면 틀림).
- **휴무일 건의 로그**: `Expected substring: "제목을 입력해 주세요"` / `Received string: "데이터 생성에 실패했습니다"`. 공백을 넣으려던 제목 입력이 늦은 포커스 이동에 밀려 종료일 칸(`<input type="date">`라 공백은 무시됨)으로 가고, 제목은 앞 단계에서 넣은 "날짜 순서 오류"가 그대로 남아 검증을 통과해 **등록 요청이 나간다**. 이 테스트는 "서버로 요청이 가면 안 되는 상황"이라 요청이 나가면 `route.abort()`로 끊는 함정을 걸어 뒀고, 화면은 등록이 실패한 줄 알고 `데이터 생성에 실패했습니다`를 띄운 것(실서버였다면 "날짜 순서 오류" 제목으로 휴무일이 등록됐을 것). 로그로 확정된 건 "제목이 안 바뀌었고 요청이 나갔다"까지이고 "공백이 종료일 칸으로 갔다"는 그 순간 포커스 위치에서 추론한 것. 두 테스트 모두 확인하려는 기능은 정상이었고 타이밍만 문제.
- **설명할 때 "앱"이라고 하면 직원용 모바일 앱으로 읽힌다** → 어드민 웹은 "화면", e2e는 "테스트"로 구분해 쓴다. 한쪽(화면)이 늦게 끝내는 일을 다른 쪽(테스트 = 사람 흉내 로봇)이 기다리지 않은 순서 꼬임이라는 구조로 설명하면 두 사례가 같은 종류임이 보인다.
- **같은 패턴 전수 점검**: "`확인` → 곧바로 입력" 순서를 테스트 전체에서 찾아 2곳 추가 수정(휴무일 수정 퍼블리싱, 업무 수정). 이미 포커스를 확인하거나 거기서 끝나는 테스트는 무해.
- **CI 재시도 1회**: 원인 불명 흔들림(`page.goto` 30초 타임아웃 등)이 남아 `retries` 1회 도입. 재시도로 통과하면 로그에 `flaky`로 표시되고 진짜 버그는 두 번 다 실패해 여전히 막힘. 로컬에서 켜지면 불안정한 테스트가 "통과"로 가려지고 오래 걸림.
- **`CI` vs `GITHUB_ACTIONS` 함정** (CodeRabbit 지적): 처음 `retries: process.env.CI ? 1 : 0`으로 썼으나 팀 규칙은 로컬 e2e에도 `CI=1`을 붙이게 한다(`reuseExistingServer: !process.env.CI`로 5173 개발 서버 재사용 방지). 그래서 로컬에서도 재시도가 켜졌다. `CI`는 대부분의 CI 서비스가 붙이고 **사람이 로컬에서도 붙일 수 있는** 관례, `GITHUB_ACTIONS`는 **GitHub Actions 러너가 모든 단계에 자동으로만** 넣는다(`ci.yml` 설정 불필요, 러너 폐기 시 소멸). `retries: process.env.GITHUB_ACTIONS ? 1 : 0`으로 바꿔 GitHub 1회·로컬 0회 달성. 읽는 주체는 Playwright가 시작할 때 `playwright.config.ts`에서 보는 `process.env`. 한 환경 변수가 다른 뜻("개발 서버 재사용 금지" vs "GitHub에서 도는 중")으로 쓰이면 더 좁은 신호를 고른다. CodeRabbit이 제안한 재시도 전용 환경 변수 신설은 `ci.yml` 수정이 필요해 채택하지 않음.
- **진단 전 집계 (10/11 CI 도입~10/19)**: 결과가 나온 37회 중 13회가 첫 시도 e2e 실패(lint·타입 검사는 0회). 그중 2회만 진짜 버그(#252 지연 로딩으로 주소가 늦게 바뀜, #253 mock 순서), **나머지 11회(약 30%)는 코드 문제 없는 흔들림**. develop 푸시는 9번 중 4번 빨강인데 모두 PR에선 통과한 코드. 원인별: 로그인 401 3회, 휴무일 검증 1회(두 테스트 동시), 대시보드 3회, 페이지 열기 30초 초과 3회(테스트 4개).
- **휴무일 건의 증거**: CI 실패 스냅샷에서 제목 칸이 이전 값 그대로 → 공백이 다른 칸으로 들어가 검증을 통과하고 API까지 호출됨. Playwright 입력이 "칸 선택 → 글자 입력" 2단계라 그 사이 포커스가 넘어가면 벌어진다. 공지·자료실·업무·예약 폼에도 같은 지연 포커스가 있어 전수 점검 대상.
