API 응답 검증은 엄격할수록 좋은 게 아니다. 너무 엄격하면 서버에서 성공했는데 화면이 실패로 보이고, 너무 느슨하면 네트워크·서버 오류가 "데이터 없음"으로 보여 사용자가 삭제된 것으로 오해한다. 기준은 "이 화면이 무엇을 반드시 알아야 하는가"다.

## 너무 엄격해서 생긴 문제 (ToyVillage-Admin-FE 사례)
- 공지 목록이 날짜 형식·분류 값이 명세와 조금만 달라도 **목록 전체를 오류 화면**으로 처리했다.
- 휴관일 삭제가 "상태 201 + message 본문"만 성공으로 인정해서, 서버에서 실제로 지워졌는데도 화면엔 실패로 표시됐다.
- 해결:
  - 검증 대상을 **화면에 꼭 필요한 필드**(id, 제목 등)로 좁히고 나머지는 기본값(예: "미분류")으로 대체한다.
  - 삭제처럼 본문이 중요하지 않은 요청은 **요청이 성공했으면 캐시에서 바로 제거**한다.
- **회귀 주의 (2026-09-20)**: 삭제 성공 판정을 "2xx면 성공"으로 한 번 완화해도, 이후 디자인 반영 같은 큰 커밋이 옛 엄격 검사(201+message)를 되살릴 수 있다. 휴관일 삭제가 7/29에 완화됐다가 재발한 실사례다. 엄격한 동작을 기대하는 e2e·계약 문서가 남아 있으면 코드만 고쳐선 안 되고 함께 반전해야 한다.
- 성공 판정 테스트는 토스트만 보지 말고 **삭제 후 재조회 mock이 빈 목록을 주게 하고 대상 카드가 사라졌는지**까지 확인한다(목록 mock이 그대로면 카드가 남아 있어도 통과한다). 상세는 [[ToyVillage-Admin-FE/프로젝트-현황]]의 이슈 #170.

## 너무 느슨해서 생긴 문제
- 종·개체·관찰 조회가 네트워크·서버 오류로 실패해도 "존재하지 않는 종입니다"로 표시됐다.
- 해결: **404만 "없음"**으로 처리하고, 나머지는 **재시도 가능한 오류**로 분리한다. 프로필 사진 로딩 실패도 깨진 이미지 대신 "사진 없음"으로 표시.

## 일반 원칙
- "없음(404)"과 "조회 실패(네트워크/5xx/형식 오류)"는 다른 상태로 모델링한다.
- 두 문제 모두 정상 흐름만 보고 화면을 만든 데서 나왔다. 로딩 중·실패·연속 클릭 같은 경계 상황을 테스트 시나리오에 **먼저** 적고 구현하면 걸러진다.
- 관련: 명세와 실제 응답이 다른 경우는 [[ToyVillage-Admin-FE/프로젝트-현황]]의 staging 실서버 검증 단계 참고. 로딩 중 편집 문제는 [[TanStack-Query-placeholderData-이전탭-데이터-조작-가능]].
