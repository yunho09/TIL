# API 에러 메시지가 사용자에게 안 닿는 세 가지 경로

BE가 정확한 사유를 줘도 화면에는 "입력값이 올바르지 않습니다" 같은 일반 문구만 뜨거나, 문구가 **화면 밖에 렌더링**돼 사용자가 못 보는 경우가 있다. Commonly-FE 감사에서 확인한 세 가지를 정리한다.

## 1. 검증 400의 필드별 사유(`error` 맵)를 파서가 버림
- Spring 검증 실패 응답이 `{status, timestamp, error: {필드키: 메시지}}` 형태이고 **최상위 `message`가 없다**(예: `{"error":{"divisionValid":"구분 값은 채용/전보/해지/퇴직 중 하나여야 합니다."}}`).
- `parseErrorBody`가 `code`/`message`/`detail`만 읽고 `error` 맵을 무시하면 사유가 전부 사라지고, `message`가 없으니 기본값 "일시적인 오류가 발생했습니다"(서버 장애처럼 보임)로 떨어진다.
- 수정: `error` 맵을 읽어 `ApiError.fieldErrors`에 담고 문구에 결합. 우선순위를 `body code 매핑 → error 맵 → 상태코드 매핑 → body message → 기본값`으로. 배포 후 실제로 "채용일이 퇴직일보다 늦습니다."가 화면에 뜨는 것까지 확인.

## 2. 상태코드 매핑이 BE 본문 message보다 우선
- 기존 우선순위가 `body code → errorMessages[status] → body message → 기본값`이면 BE가 구체 사유("재직 이력이 10건을 넘어…")를 줘도 FE의 뭉뚱그린 404 문구에 덮인다.
- 반대로 본문이 0바이트인 401([[Spring-Security-403이-본문-없는-401로-바뀌는-ERROR-디스패치]])에서는 이 구조 덕에 FE 자체 문구가 채택돼 사용자 눈에 띄지 않게 버텼다. 의도한 방어가 아니라 우연.
- 호출부가 모든 401을 "로그인이 만료되었습니다"로 매핑해 두면 권한 거부가 세션 만료로 오안내된다 — 401 문구는 호출부 맥락(조회/발급 등)에 맞춰 따로 둔다.

## 3. 에러 요소가 트리거 버튼과 멀리 떨어져 화면 밖에 렌더링
- 사례: 발급 미리보기에서 "다음으로" 버튼은 긴 문서 뷰어 **위**, 에러(`role="alert"`)는 뷰어 **아래**. DOM 조회 결과 `getBoundingClientRect().top = 1875px`(뷰포트 1025px) → 버튼을 눌러도 아무 반응 없는 것처럼 보임. 실패 시 `view` 상태가 안 바뀌어 "view 변경 시 스크롤" 훅도 안 돈다.
- 처음엔 "에러가 안 뜬다"로 오진했으나, **"에러가 없다"와 "에러가 보이는 위치에 없다"는 고칠 곳이 다르다** — DOM에 `[role=alert]`가 있는지, `top`이 뷰포트 안인지부터 확인한다.
- 수정: 에러를 뷰어 위로 이동 + 나타날 때 `scrollIntoView`. 배포 후 `top: 383px`(화면 안)로 확인.
- 주의: **JS로 클릭하면 페이지 스크롤이 맨 위에 머물러** 측정값이 부풀려진다. 경력 수정 화면의 에러가 `top: 1731px`로 나와 "같은 버그"라 했다가, 소스상 에러 바로 아래가 저장 버튼이라 실사용자는 보인다는 걸 확인하고 철회했다. 위치 측정은 실제 사용 흐름(스크롤 상태)을 반영해야 한다. 관련: [[Playwright-오토스크롤-화면기준-위치측정-오염]].
