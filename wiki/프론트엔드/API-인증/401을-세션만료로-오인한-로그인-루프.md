# 401을 세션 만료로 오인한 로그인 루프

백엔드가 **권한 부족**(원래 403이어야 함)까지 **401**로 내려주는데, 프론트가 "401 = 세션 만료"로 무조건 처리하면 로그인 직후 진입 화면이 스스로 로그아웃을 유발해 로그인 화면에 갇히는 무한 루프가 생긴다.

## 증상

- 회원가입/로그인은 200으로 정상 응답한다.
- 그런데 로그인 직후 이동한 화면이 뜨자마자 API를 호출 → 그 응답이 401 → 프론트가 토큰을 지우고 `/login`으로 리다이렉트 → 다시 로그인해도 같은 화면에서 같은 401 → 다시 로그인 화면. **로그인 자체는 멀쩡한데 매번 튕긴다.**

## 원인 체인

1. 계정 권한(예: `PETITIONER`)이 특정 엔드포인트에 대한 권한이 없다.
2. 백엔드가 인증 실패(토큰 없음/만료)와 인가 실패(권한 부족)를 구분하지 않고 **둘 다 401**을 반환한다(원칙적으로 인가 실패는 403이어야 함). Spring Security에서 흔한 원인: `exceptionHandling`에 `authenticationEntryPoint`만 등록하고 `accessDeniedHandler`를 안 넣으면, `AccessDeniedException`(인가 실패)도 entry point로 떨어져 401로 나온다.
3. 프론트의 공용 API 클라이언트가 401을 받으면 무조건 `UNAUTHORIZED_EVENT`를 쏘고, 이를 구독하는 세션 가드가 토큰을 지우고 로그인 페이지로 보낸다.
4. 로그인 직후 진입하는 화면이 **진입 즉시** 그 권한 없는 API를 호출한다.

→ 위 네 조건이 겹치면 "권한 부족"이 "세션 만료"로 오인되어 로그아웃이 반복된다.

## 해결 원칙

401을 받았다고 무조건 로그아웃시키지 말고, **저장된 토큰이 아직 유효한지 먼저 확인**한다.
- 토큰이 없거나 만료됐으면 → 진짜 세션 만료. 로그아웃 이벤트를 쏜다.
- 토큰이 아직 유효한데 401이 왔으면 → 권한 부족(백엔드가 403 대신 401을 준 것)일 가능성이 높다. 세션을 지우지 말고, 해당 API 호출부에서 "권한 없음" 문구로 따로 안내한다.

```ts
function notifyUnauthorized(): void {
  if (hasValidAuthToken()) return; // 권한 부족 401 ≠ 세션 만료
  dispatchWindowEvent(UNAUTHORIZED_EVENT);
}
```

근본 해결은 백엔드가 인가 실패에 403을 쓰는 것이지만, 백엔드를 못 바꾸는 상황에서도 프론트 쪽에서 이 판단 기준(토큰 유효성)만으로 로그인 루프는 끊을 수 있다.

## 언제 다시 의심할지

- "로그인은 되는데 특정 화면 진입 시 바로 로그인 페이지로 튕긴다"는 제보를 받으면, 그 화면이 진입 즉시 호출하는 API의 응답 코드부터 확인한다. 200이 아니라 401이면 이 패턴을 의심한다.
- 공용 API 클라이언트에서 401 처리가 "무조건 로그아웃"으로 하드코딩되어 있는지 먼저 본다.
- 백엔드가 Spring Security라면 `SecurityConfig`의 `exceptionHandling`에 `accessDeniedHandler`가 등록돼 있는지 확인한다(없으면 인가 실패도 401로 새어나간다).

## 관련 함정: 403도 재발급 후 재시도하면 중복 요청 위험

같은 부류의 실수로, 공용 axios 인터셉터가 **401뿐 아니라 403에도** 토큰 재발급 후 원 요청을 재시도하도록 짜여 있는 경우가 있다.

```ts
if ((statusCode === 401 || statusCode === 403) && !originalRequest._retry) { /* 재발급 후 재시도 */ }
```

401(미인증)은 재발급으로 해결될 수 있지만, **403(권한 없음)은 새 토큰을 받아도 그대로 거부된다.** 그런데도 재시도 로직을 타면 같은 요청이 서버에 **두 번** 나간다 — 조회(GET)면 낭비로 끝나지만, **생성(POST)류 요청이면 서버가 첫 번째 요청에서 이미 리소스를 만들어 놓고 403을 반환하는 경우 같은 데이터가 두 번 등록되는 위험**이 있다.

해결은 재시도 조건을 401로만 좁히는 것. 이 판단은 한 번 정해지면 끝이 아니라 **리팩터링 중에 조건이 다시 넓어지는 회귀**가 흔하다 — 팀이 이미 `403 -> 401`로 좁혀놓은 커밋이 있었는데, 이후 별개의 리팩터링 커밋에서 403이 도로 섞여 들어간 사례가 있었다. 인터셉터의 상태 코드 분기를 고칠 때는 `git blame`/`git log -p`로 그 줄에 대해 과거에 의도적인 결정이 있었는지부터 확인하는 게 안전하다.
