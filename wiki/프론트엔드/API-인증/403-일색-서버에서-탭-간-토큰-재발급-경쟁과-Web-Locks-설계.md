# 모든 인증 실패가 403인 서버에서 탭 간 토큰 재발급 경쟁 — 가설과 Web Locks 설계

서버가 만료·토큰 없음·권한 없음을 전부 본문 없는 403으로 주고 재발급 토큰(refresh token)은 한 번 쓰면 폐기되는 환경에서, 탭 안에서만 동작하는 재발급 중복 방지(`pendingReissue`)는 **탭 두 개가 동시에 재발급**하는 경우를 못 막는다. 실패한 탭이 저장소를 통째로 비우면서 성공한 탭의 새 토큰까지 지워 둘 다 로그아웃될 수 있다는 **가설**이다. 2026-10-28 기준 **재현·수정 모두 안 했다.**

## 배경
- 로그인하면 access token(API 호출용, 약 1시간)과 refresh token(교환권, 약 7일)을 localStorage에 둔다.
- **refresh token은 일회용**: 재발급하면 새 access+새 refresh를 받고 쓴 refresh는 서버에서 지워진다. 지워진 것을 다시 내면 404 `refreshToken이 존재하지 않습니다`(서버 계약에 적힌 동작).
- 이 서버는 인증 실패를 **전부 403**으로 줘서 프론트는 "403 = 일단 재발급 후 재시도"로 만들어 둔다(`src/app/config/configureApiAuthentication.ts`).
- 한 탭 안: 대시보드 진입 시 API 7개가 동시에 나가 모두 403이면 각자 재발급하면 첫 번째만 성공하고 나머지는 404 → 그래서 `pendingReissue`(모듈 변수)로 재발급을 하나로 묶어 7개가 같이 기다렸다 새 토큰으로 재시도한다. **이 묶음은 탭(JS 컨텍스트) 하나 안에서만** 동작한다. 스테이징 실측으로 한 탭 동시 7개에 reissue 1번만 호출됨은 확인됨.

## 가설: 탭 두 개가 동시에 재발급
노트북 덮개를 닫았다 열어 두 탭이 깨어나는 상황.
```
네트워크 복귀 → React Query의 refetchOnReconnect(기본값 true)로 두 탭이 동시에 재조회
→ 자는 동안 access 만료 → 두 탭 모두 403
탭 A: 저장소에서 R1을 읽어 재발급 요청
탭 B: 같은 R1을 읽어 재발급 요청 (A 응답 전)
탭 A: 성공 → T2/R2 저장
탭 B: R1은 이미 사용됨 → 404 → "세션 끝"으로 판단 → clearSession()이 저장소 전체 삭제
      (A가 막 저장한 T2/R2까지 삭제) → /login 이동
탭 A: 다음 요청 때 저장소가 비어 있음 → 403 → 교환권 없음 → /login
```
- Sentry 모양과 맞는다: 강제 로그아웃 사유가 대부분 재발급 404, 막힌 요청이 전부 대시보드 동시 API. 코드는 처음 세션을 끝낸 탭(B의 404)만 Sentry에 보내고 A는 저장소가 이미 비어 기록이 없다. 관련 선행 가설은 [[ToyVillage-Admin-FE/프로젝트-현황]]의 10/2·10/7 절.

## 아직 모르는 것 — 원인 둘을 구분해야 한다
| 재발급 404의 원인 | 프론트에서 고칠 수 있나 | 상태 |
|---|---|---|
| 다른 기기·다른 로그인이 refresh를 바꿈(계정 공유) | 아니오(서버 정책) | 개발자들이 같은 관리자 계정을 쓰던 건 테스트 계정 분리로 정리 |
| 같은 브라우저의 탭끼리 경쟁 | 예 | **미확인, 고칠 대상** |

Sentry에는 사용자·탭이 안 남아 강제 로그아웃 19건 중 재발급 404 17건 가운데 **몇 건이 탭 경쟁인지 알 수 없다.** "17건이 탭 문제였다"고 쓰면 안 되고, 재현 → 수정 → 원인 태그 → 0건 확인 순서로 가야 한다(이 수치는 이 세션에서 다시 조회하지 않고 포트폴리오 값을 그대로 쓴 것).

## 고치는 방법(설계)
1. **재현부터**: e2e에서 같은 브라우저 컨텍스트에 탭 2개. 가짜 서버가 R1을 처음엔 성공, 두 번째부터 404로 응답. 두 탭에서 동시에 요청을 내 둘 다 `/login`으로 가는지 확인(CI).
2. **탭 간에도 한 줄로**: Web Locks(`navigator.locks.request`)로 "재발급 중" 잠금을 탭 전체가 공유.
3. **차례가 오면 저장소부터 확인**: 실패한 요청이 쓴 토큰과 지금 저장소의 토큰이 다르면 다른 탭이 이미 재발급한 것 → 재발급하지 않고 저장된 새 토큰으로 재시도.
4. **지울 때는 비교한 뒤**: 저장소의 refresh가 내가 보낸 것과 같을 때만 `clearSession()`. 그 사이 다른 탭이 새 토큰을 넣었으면 그것을 쓴다(compare-before-clear).
5. **원인 태그**: 재발급 404를 "다른 탭이 이미 바꿈" vs "그 외"로 Sentry 태그를 붙여, 고친 뒤 탭 원인이 0건이 되는지 본다.
규모는 `configureApiAuthentication.ts` 30줄 안팎 + e2e 1개.

## 다른 방법을 고르지 않은 이유(면접용)
- **`storage` 이벤트**: 다른 탭이 저장한 **뒤에야** 알 수 있어 동시 출발은 못 막는다.
- **BroadcastChannel로 결과 공유**: 어느 탭이 재발급할지 정하는 대표 탭 선출을 직접 만들어야 해 복잡. Web Locks는 그 역할을 브라우저가 해 준다.
- **서버가 쓴 refresh를 몇 초 더 받아 주기(grace period)**: 가장 깔끔하지만 백엔드 작업 → 제안은 가능.

## 같은 뿌리의 다른 문제
"모든 인증 실패가 403"이라는 서버 제약 때문에 **공통 axios 인터셉터가 파일 서버(CDN) 요청에도 붙으면** Bearer 토큰이 외부 도메인으로 나가고, CDN의 403도 세션 만료로 보고 로그아웃시킨다. 그래서 파일 요청만 `fetch`로 분리했다(`src/shared/api/fileStorage.ts`, 커밋 `9753013`) → [[공용-인증-axios-외부도메인-토큰유출]]. 두 문제를 "403만 주는 서버에서 세션 지키기"라는 하나의 설계 이야기로 묶는 게 포트폴리오 이슈 후보로 가장 강하다는 판단(숫자가 아니라 원인 추적·설계 판단이 드러남). 단 탭 경쟁은 고친 뒤에 써야 한다.
