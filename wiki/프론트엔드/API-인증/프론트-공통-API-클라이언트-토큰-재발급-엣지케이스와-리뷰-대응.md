# 프론트 공통 API 클라이언트 — 토큰 재발급 엣지케이스와 리뷰 대응

fetch만으로 만든 공통 API 클라이언트(`packages/api`, `@xquare/api`)가 "401이면 재발급 후 1회 재시도"를 안전하게 하려면 **동시 요청·탭 여러 개·재발급 중 로그아웃·계정 전환**까지 막아야 한다. xquare-openapi-frontend의 OPN-55(PR #57)에서 서브에이전트 리뷰 12건과 CodeRabbit 리뷰 여러 라운드를 거치며 정리된 규칙이다. 탭 간 경쟁의 가설·설계 배경은 [[403-일색-서버에서-탭-간-토큰-재발급-경쟁과-Web-Locks-설계]]에서 이어진다.

## 서버 전제 (이 프로젝트)
- 재발급 토큰(refresh)은 **한 번 쓰면 폐기**. 로그인 실패·access 만료·refresh 만료가 **전부 401**이라 상태 코드로는 구분 불가 → **`code`(`INVALID_CREDENTIALS`/`INVALID_TOKEN`/`INVALID_REFRESH_TOKEN`)로 재발급 여부를 판단**한다.
- **없는 경로도 401 `INVALID_TOKEN`** → 경로 오타면 재발급이 한 번 돈 뒤 401이 남는다. 401이 계속 나면 경로부터 확인(README에 명시).
- 서버에 로그아웃 API가 없어 로그아웃 = 저장 토큰 삭제 + `/login` 이동.
- 로그인마다 토큰에 `UUID.randomUUID()` 고유 id가 들어가(백엔드 `JwtProvider`) **다시 로그인하면 refresh 토큰이 항상 달라진다** → "같은 refresh로 재로그인" 시나리오는 실제로 불가능(CodeRabbit 우려를 이 근거로 반박해 철회받음).

## 핵심 규칙
- 오류는 `ApiError(status, code, message)` 하나로 통일, 서버에 못 닿으면 status 0 + `NETWORK_ERROR`.
- **재시도는 딱 1번**. 다시 보내도 401이면 던진다.
- **single-flight**: 동시에 만료된 요청들은 재발급 1번을 같이 기다린다. 단, "같은 refresh 토큰 **+ 같은 로그인 회차**"끼리만 공유(이전 계정의 재발급을 새 계정이 기다리면 안 됨).
- **로그아웃 판단**: 재발급이 **400·401로 거절**될 때만 세션 종료. 네트워크 오류·5xx·429는 토큰을 그대로 두고 에러만 던진다(서버 일시 장애로 로그아웃 방지). 첫 구현은 `status !== 0`을 "거절"로 봐 502에도 로그아웃되던 게 리뷰 HIGH였다.
- **지우기 전 재확인**: 거절 응답 본문을 `await`로 읽는 사이 다른 탭이 새로 로그인할 수 있으므로, 본문을 읽은 **뒤** 저장된 refresh가 "거절된 바로 그 토큰"일 때만 삭제. 바뀌었으면 지우지 말고 새 토큰으로 재요청.
- **재발급 중 로그아웃**: 저장하기 직전에 로그인 상태·로그인 회차(login generation)를 다시 확인해, 끝난 재발급이 토큰을 되살리지 않게 한다. 거절 쪽도 회차를 확인.
- **다른 계정 토큰으로 재전송 금지**: 이전 계정의 요청이 새 계정 토큰으로 다시 나가면 안 된다. 재발급마다 "새 토큰은 어느 토큰에서 이어졌나" 기록을 남기고, 재시도 때 이 체인을 거슬러 처음 보낸 토큰이 나오는지 확인. 아니면 두 토큰의 사용자 id가 같을 때만 재전송.
- **탭 간 경쟁**: `navigator.locks`(Web Locks)로 재발급을 탭끼리 직렬화, 잠금을 기다린 탭은 저장소를 다시 읽어 이미 바뀐 토큰이 있으면 재발급 없이 그걸 쓴다. 잠금 이름은 토큰 저장 키와 같게. 지원: Chrome·Edge 69, Firefox 96, Safari 15.4, HTTPS/localhost. 없으면 탭마다 따로 재발급(최악이 재로그인), localStorage로 직접 잠금 구현은 버그가 더 나기 쉬워 안 넣음.
- **요청 본문**: `FormData`/`Blob`/`URLSearchParams`는 JSON으로 바꾸지 않고 그대로(첫 구현은 `"{}"`로 보내 파일 업로드가 깨짐), `Content-Type`은 브라우저가 정하게 둔다. 재시도가 변형된 본문을 보내지 않게 **첫 전송 때 `ArrayBuffer`·`FormData`·`URLSearchParams`를 복사**. 헤더는 `Headers`로 정규화해 대소문자 다른 `Content-Type` 중복 방지.
- **경로는 항상 `/`로 시작**하게 보정: `baseUrl + "students"`가 다른 호스트가 되어 Bearer 토큰이 새는 경로를 막는다.
- **토큰 검증**: 로그인·재발급 응답의 두 토큰이 **비어 있지 않은 문자열**인지 검사(빈 `accessToken`이 "로그인 성공"이 되면 이후 요청에 Bearer가 안 붙음). 저장소 쓰기 실패(시크릿 모드·용량)는 삼키지 말고 던져 로그인 실패로 처리.
- **취소**: 이미 취소된 요청이 401을 받으면 재발급을 시작하지 않고, 취소 사유가 400·401 에러여도 재발급 거절로 오인하지 않는다. 재발급을 기다리다 취소하면 그 요청만 끝내고 공유 재발급은 계속.
- **로그인 화면**: 제출 중 입력 잠금(이전 입력의 에러가 다음 입력 아래 뜨는 것 방지), 화면을 떠나면 요청 취소(`/signup`으로 이동했는데 뒤늦게 `/`로 끌려가거나 토큰이 저장되는 것 방지), 실패 메시지는 `role="alert"`로 스크린 리더에 알림(입력의 `aria-describedby`만으로는 낭독 안 됨).
- 로그인 안 된 상태의 401은 자동으로 `/login`으로 보내지 **않음**(API 상세처럼 비로그인 화면이 있음). 보호 화면은 `useEffect`에서 `isLoggedIn()` 확인 — 렌더 중 호출하면 SSR과 달라 hydration 불일치.
- 서버 주소 `NEXT_PUBLIC_API_BASE_URL`을 비우면 스테이징 사용(운영이 502라 일부러). 프로덕션 빌드에서 env 누락 시 조용히 스테이징을 쓰는 점은 위험으로 남김. `node --test`로 `.ts`를 직접 돌리려면 Node ≥ 22.18.

## 리뷰 대응 방식에서 얻은 것
- **회귀 테스트 증명**: 지적마다 테스트를 하나 추가하고 "이전 커밋에서 실패·지금 통과"를 확인(테스트 10→34개). 시간(25ms 제한)에 기대는 테스트는 느린 PC에서 깨지므로 가짜 서버가 응답을 쥐고 있다가 테스트가 직접 놓아주는 방식으로 바꾼다.
- CodeRabbit은 같은 영역을 **후속 지적으로 계속 파고들며** 점점 드문 경우로 간다. 매번 현재 코드와 대조해 (a) 진짜 버그 → 수정+실패 테스트, (b) 이미 고침 → 근거 답글, (c) 가정 확인 요청 → 코드 근거(예: JWT UUID, Web Locks 지원표)로 답해 철회를 받는 식으로 분류하면 코드 변경 없이 끝낼 수 있다. 이 반복은 어디선가 머지 판단으로 끊어야 한다.
- 무료 플랜은 리뷰 한도("Review limit reached")가 있어 최신 커밋이 검토되지 않을 수 있다(약 1시간 뒤 해제).
- **PR 본문을 통째로 덮어쓰면 CodeRabbit이 붙인 "Summary by CodeRabbit"이 지워진다** → 본문 수정 시 그 블록은 보존.
- `develop`의 user 앱 빌드가 원래 깨져 있었다: 모달 설명 컴포넌트에 `align`이 필수가 된 뒤 만든 문의하기 모달이 이를 안 넘김. 화면이 안 바뀌게 선택값(미지정 시 모달 정렬 `inherit`)으로 고치고 커밋을 따로 분리.
