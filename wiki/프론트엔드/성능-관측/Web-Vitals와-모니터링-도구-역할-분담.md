# Web Vitals와 모니터링 도구 역할 분담 (Sentry vs GA4 vs CI 게이트)

Web Vitals는 도구가 아니라 **지표 이름(규격)**이고, 재는 것은 라이브러리·SDK, 모아 보여주는 것은 Sentry/GA4다. 어드민 SPA에 모니터링을 붙일 때 "Sentry 하나로 에러·Web Vitals·API 계측이 다 되므로 GA4는 사용량 분석이 필요할 때만" 이라는 결론에 이른 과정과 근거를 정리한다(ToyVillage-Admin-FE 도입 검토, 2026-09-22 전후).

## Web Vitals가 뭔가
- 구글이 정한 "사용자 체감 성능" 3대 지표. `load` 이벤트가 끝나도 화면이 비었거나 버튼이 안 눌릴 수 있어서 기존 '로딩 시간'이 체감과 안 맞던 문제를 보완.

| 지표 | 재는 것 | 좋음 | 나쁨 |
|---|---|---|---|
| **LCP** | 가장 큰 요소가 그려진 시점(얼마나 빨리 보이나) | ≤ 2.5s | > 4.0s |
| **INP** | 클릭·입력 후 화면이 바뀌기까지(얼마나 빨리 반응하나) | ≤ 200ms | > 500ms |
| **CLS** | 레이아웃이 밀리는 정도(덜컥거리나) | ≤ 0.1 | > 0.25 |

- **판정은 평균이 아니라 p75**: "4명 중 3명이 이 정도 이상 경험". 평균은 빠른 기기 몇 대가 구형 노트북 사용자의 느린 경험을 가린다.
- **랩 측정 vs 필드 측정**: Lighthouse·Playwright 같은 랩은 LCP·CLS(일부)만 가능하고, **INP는 실제 사람이 클릭해야 나오므로 랩/CI로는 원리상 측정 불가** → 실사용자 수집(Sentry SDK 등)으로만 얻는다.
- 어드민(하루 종일 폼 입력·목록 넘김, `useMutation` 33곳)은 첫 화면 LCP보다 **INP가 체감에 더 중요할 가능성**이 높다. 스켈레톤으로 빈 공간을 미리 잡는 작업은 CLS 개선에 해당.
- Search Console의 Core Web Vitals 보고서는 CrUX(공개 사이트 Chrome 사용자 데이터) 기반이라 **로그인 뒤 어드민은 안 잡힌다**. 구글 검색 랭킹 반영도 해당 없음.

## 용어 층위: Web Vitals / web-vitals / SDK
| 이름 | 정체 |
|---|---|
| Web Vitals | 지표 이름(규격) — 체온·혈압 |
| `web-vitals` | 지표를 재는 구글 제작 npm 라이브러리 — 체온계 |
| Sentry / GA4 | 잰 값을 모아 보여주는 도구 — 차트 |
| SDK | 서비스 사용에 필요한 것을 한 세트로 묶은 패키지(라이브러리와 거의 같은 말, 뉘앙스만 다름). `@sentry/react`는 에러 가로채기·Web Vitals 측정·전송·`ErrorBoundary`·민감정보 스크럽 설정을 포함 |

## GA4로 Web Vitals를 보내는 경로의 불편함
- GA4는 **받아서 쌓아주는 곳**이지 측정기가 아니다. `web-vitals`의 `onLCP/onINP/onCLS` 콜백에서 `gtag('event', name, { value, metric_id })`로 직접 보내야 하고(`metric_id`가 있어야 p75를 제대로 계산), 라우트별로 보려면 정규화된 경로도 파라미터로 붙여야 한다.
- 표준 보고서는 평균 중심이라 p75는 탐색(Exploration) 보고서 구성이나 BigQuery 내보내기가 필요하고, 보고서 지연이 약 24시간.
- Sentry는 SDK가 측정·전송·저장·조회를 한 번에 하고 p75가 기본 대시보드에 나오며 지연이 없다. 같은 값을 양쪽에 보낼 이유는 없다.
- 처음엔 "Sentry 무료 티어 span 절약"을 이유로 Web Vitals를 GA4로 몰자고 했다가, 직원 몇 명이 쓰는 어드민은 트래픽이 적어 한도에 걸릴 가능성이 낮다는 이유로 **Sentry로 정정**(한도가 실제로 걸리면 `tracesSampleRate`를 낮추면 됨).

## API 계측(instrumentation)
- 요청마다 보낸 시각·받은 시각·소요·상태코드를 기록하고 엔드포인트별 호출 수·p50·p95·실패율로 쌓는 것. p50=중간값, p95=100번 중 95번이 이 안에 끝나는 시간(느린 쪽 체감).
- 효용: 대시보드가 7개 API를 동시에 부를 때 어느 것이 병목인지 알 수 있고, 백엔드에 "느린 것 같다" 대신 "`/dashboard/feeds` p95 1,840ms" 식으로 말할 수 있다.
- **Sentry 브라우저 SDK가 `fetch`/XHR을 가로채 자동 기록**하고 axios도 XHR이라 잡힌다 → 직접 인터셉터 계측 코드는 거의 불필요하고, 커스텀(401을 실패율에서 제외, Authorization 헤더 스크럽)만 얹으면 된다. 단 한계는 [[Sentry-React-SPA-에러추적-도입]]의 "성능(Web Vitals) 추적" 절 참고(페이지 로드·이동 구간 밖 요청 누락 등).

## 역할 분담 (최종)
| 도구 | 담당 | 못 하는 것 |
|---|---|---|
| **Sentry** | 에러(소스맵 스택트레이스·breadcrumb·릴리즈 연결·회귀 재오픈), Web Vitals, API 계측, ErrorBoundary 포착 | 머지 전 차단, 사용 행태 분석(대략만) |
| **GA4** | 화면별 사용량·이동 경로·기능 사용 빈도 | 에러 스택트레이스 |
| **size-limit / Lighthouse CI** | 머지 전 번들 예산·성능 점수 회귀 차단 | 실사용자 데이터 |
| **ESLint** | 복잡도·레이어 경계 | 런타임 문제 |

- Sentry는 **이미 배포된 뒤에** 알려주므로 번들이 PR마다 수 kB씩 조용히 커지는 것은 쌓여서 눈에 띌 때까지 못 막는다 → 빌드 게이트가 별도로 필요([[번들-회귀-방지-CI와-ESLint-복잡도-도입]]).
- **ErrorBoundary**는 정보가 아니라 Sentry의 포착 범위를 넓히는 장치. 렌더 에러는 없으면 포착도 안 되고 화면만 하얘진다. 대시보드는 카드 단위로 감싸 하나가 터져도 나머지는 살게.
- 에러 모니터링으로 잡히는 대표 사례: 응답 형식이 명세와 달라(`assignees` 배열 등) 타입 가드가 실패해도 Network 탭은 200이라 정상처럼 보이는데, 화면에는 "불러오지 못했습니다"만 뜨는 버그 — Sentry가 있으면 가드 실패 지점이 잡힌다.

## 결정: GA4는 지금 도입하지 않음
- GA4가 유일하게 답하는 "43개 화면 중 뭘 많이 쓰나"는 지금 당장 필요한 정보가 아니고 Sentry 라우트별 요청 수로 대략 대체 가능.
- 붙이면 따라오는 비용: 경로 정규화(`/species/1842/observations/77` → `/species/:speciesId/observations/:observationId`로 개체 ID가 구글로 나가는 것 차단 — GA 약관상 PII 전송 금지, 리포트가 URL마다 쪼개지는 것도 동시에 해결), Google 신호 끄기, 개인정보처리방침 고지, 쿼리스트링 제외. 3시간 작업에 개인정보 책임이 붙는데 얻는 건 화면별 조회수 하나.
- 광고 차단기에 막히면 그 직원 데이터가 통째로 빠지므로 GA 숫자는 절대값이 아닌 화면 간 상대 비교용. 에러 모니터링 용도로는 부적합(스택트레이스 없음).
- 나중에 사용 행태가 궁금해지면 GA보다 **PostHog 셀프호스팅**(데이터가 밖으로 안 나가고 세션 리플레이 포함)을 먼저 본다. 실제로 GA4를 붙일 때의 체크리스트는 [[GA4-내부-어드민-SPA-도입-체크리스트]].
- 최종 최소 구성: GitHub Actions → Sentry(에러+Web Vitals+API 계측+ErrorBoundary, 약 4h) → size-limit(30m), Lighthouse CI는 코드 스플리팅 이후. 처음부터 다 깔면 설정만 하고 안 보는 대시보드가 생긴다.

## Sentry/로그 도입 시 같이 설정할 것
- `beforeSend`에서 Authorization 헤더 스크럽, 세션 리플레이 입력 마스킹 기본값(직원·회원 데이터), `environment: import.meta.env.MODE`로 로컬 전송 차단, 401은 정상 로그아웃 흐름이라 에러에서 제외.
- 빈 axios 인터셉터에 주석(`// 공통 에러 처리 자리`)만 있던 것이 도입 전 상태였다.
