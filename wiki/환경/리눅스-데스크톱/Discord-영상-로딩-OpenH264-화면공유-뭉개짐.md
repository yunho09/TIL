# Discord 영상 로딩 무한 대기(OpenH264 꺼짐)와 화면공유 뭉개짐

리눅스 Discord에서 상대 영상 타일이 계속 로딩만 돌던 원인은 GPU가 아니라 **OpenH264 코덱 설정이 꺼져 있던 것**이었다. 켠 뒤 영상은 나왔고, 이후의 화면공유 뭉개짐은 받는 쪽이 아니라 **보내는 쪽 비트레이트** 문제로 판단됐다.

## 증상과 원인
- 증상: 통화방에서 친구들 영상(캠·화면공유) 타일 3개가 계속 로딩 표시만 나옴.
- 원인: Discord 설정 `settings.json`에 `"openH264Enabled": false`. 상대 영상이 **H.264**로 오는데 이 Discord는 H.264 디코딩에 Cisco가 제공하는 OpenH264 라이브러리를 쓰므로, 꺼져 있으면 디코더가 안 열린다(로그 `avcodec_open2 error`).
- 오진: 10-17에 런처에 다시 넣은 `--disable-gpu`가 범인으로 의심됐지만 이 문제와 무관했다 ([[GPU-유휴클럭-램프업-지연-프레임드랍]]에서도 같은 플래그가 오진으로 반증됨).

## 해결
- Discord 사용자 설정 → **음성 및 비디오 → 고급** → **"OpenH264 비디오 코덱 (Cisco Systems, Inc. 제공)"** 스위치 켜기.
- 확인: 로그에 `Using libopenh264 decoder`가 찍히고 디코더 오류가 사라짐.
- 다음에 영상이 안 보이면 이 스위치부터 확인한다.

## 화면공유가 블록처럼 무너질 때 (진단)
- `--disable-gpu`를 뺀 런처로 재실행(옛 런처는 `.bak-20261020-gpu`로 백업)해도 여전히 뭉개짐 → 받는 쪽 GPU 렌더링 문제가 아니었다.
- 로그 근거(보내는 사람 쪽 문제):
  - 화면공유: 2216x1440을 60fps로 보내는데 실제 전송량이 약 **90kbps**뿐. 이 해상도엔 보통 수 Mbps가 필요해서 움직임이 있으면 블록처럼 깨진다. 전송 손실은 거의 0 — 받은 그대로 보여 주는 것이고 원본이 이미 뭉개진 상태.
  - 캠: 대부분 정상(약 1.2~2Mbps). 한 명만 패킷 손실 340·프레임 드롭 188, 해상도 전환 순간에 깨짐 → 그 사람 업로드 쪽 문제로 추정.
- 내 쪽 정상 근거: 와이파이 -42dBm·손실 0%, CPU 여유, 디코더(OpenH264) 정상.
- 확인법: 다른 참가자에게 "너도 깨져 보여?"를 묻는다. 다 깨져 보이면 공유하는 사람이 **720p 30fps**로 낮추면 개선될 것(Claude 제안, 적용 결과는 미확인). 나만 깨져 보이면 브라우저 Discord와 비교해 본다.

## 미확정
- `--disable-gpu`는 아직 제거된 상태로 둔 채 결과를 보던 중이며, 최종적으로 어느 쪽이 나은지는 확정되지 않음.

## 2026-10-24 재진단: 친구 화공 일그러짐 (나만 깨짐 → 내 앱 쪽 유력)
- 상황: 친구의 1440p 60fps 화면공유가 스크롤·페이지 전환 때 깨짐. 로그상 수신은 1440p 60fps를 **0.1~0.4Mbps**(프레임당 ~700바이트)로 받고 패킷 손실은 13분에 5개, 디코딩 CPU 스레드 23%.
- 첫 결론("보내는 쪽 비트레이트 문제")은 **"다른 사람들은 잘 보인다"는 사용자 확인으로 뒤집힘** → 이 PC의 Discord 앱 쪽 문제로 판단. 로그의 저비트레이트 수치만으로 송신자 탓을 확정하면 안 된다.
- 깨짐 모양으로 원인 가르기: 네모 블록·뭉개짐·이전 페이지 잔상 = 송신 압축 부족, 화면 찢김·늘어남·엉뚱한 색 = 수신 쪽 그리기 문제. 스크롤 중 글자 줄이 2~3겹으로 겹치고 가로로 찢기는 모양은 둘 다 가능해 **디코더가 앞 프레임을 잘못 참조**하는 경우도 의심.
- 시청자는 화질을 못 고른다: Discord에 보는 쪽 화질 메뉴가 없고, 송신자가 1080p30으로 낮추는 것(왼쪽 아래 통화 패널의 "해상도 FPS" 글자 → 스트림 화질)이 유일한 정공법. 시청 창 크기는 송신 상한에 영향(로그: 작은 타일 1.1Mbps / 중간 2.1 / 크게 3.5Mbps)을 주므로 "작은 창으로 보라"는 조언은 오히려 반대 — 전체화면 시도는 로그상 크기가 안 바뀌어 효과 미확인.
- 유력 원인(미확정): 10-08 업데이트 이후 이 PC는 H.264를 OpenH264로만 디코딩하고, 화공 뭉개짐 첫 불만이 10-10. 비슷한 보고: 리눅스에서 "앱은 깨지고 웹 브라우저는 멀쩡"(Vesktop issue #997).
- 배제/보류한 것:
  - **OpenH264 끄기**: 10-20에 꺼 봤더니 남의 캠·화공이 무한 로딩 → 앱은 H.264를 이것으로만 풀 수 있어 시험용으로만 가능(끄고 10초 보고 로딩이면 즉시 복구).
  - **하드웨어 가속**: 설정이 켜져 있어도 효과 없음. 친구 영상 수신마다 HW 디코더 초기화에 실패하고 OpenH264로 폴백 — snap Discord 안의 그래픽 드라이버가 오래돼 Lunar Lake를 모르고, 우분투 본체에도 `intel-media-va-driver` 미설치. 제대로 쓰려면 드라이버 설치+snap 대신 공식 .deb 재설치가 필요하고 Linux Discord에서 실제로 붙을지는 해 봐야 안다.
  - **X11 vs Wayland**: 이 PC Discord는 Wayland로 뜸(업데이트가 붙인 X11 옵션을 런처의 Wayland 옵션이 이김). 영상 디코딩은 음성 모듈의 CPU 작업이라 화면 방식과 무관할 가능성이 커서 후순위.
- 결정적 시험: **크롬 웹(`discord.com/app`)으로 같은 화공 보기** — 크롬은 자체 FFmpeg 디코더를 써서 앱과 디코더만 달라진다. 웹에서 멀쩡하면 앱 디코딩 문제 확정, 똑같이 깨지면 송신 쪽. 주의: 같은 계정이라 웹이 음성에 들어가면 앱 음성 연결이 끊겨 내 화공도 꺼진다.
- 앱을 고치는 길(결과 미확인, 통화 후 진행): ① snap 대신 공식 .deb + 인텔 영상 드라이버 설치 ② Vesktop 사용(크롬과 같은 디코더, 다만 비공식 클라이언트라 약관상 회색지대).
