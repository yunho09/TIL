# GPU 유휴 클럭 램프업 지연으로 인한 프레임 드랍

120Hz 패널인데 **창을 드래그하거나 오버뷰를 열 때만** 뚝뚝 끊기고, 계속 움직이면 저절로 부드러워지는 증상. 원인은 GPU가 유휴 시 최저 클럭(400MHz)에 붙박여 있고 최대 클럭까지 올라오는 데 **약 1.5초**가 걸리는데, GNOME Shell 애니메이션은 **0.2~0.4초**라 클럭이 올라오기 전에 끝나버리는 것이었다. 컴포지터·패널·앱 GPU 렌더링은 전부 무죄였다.

## 증상

- 정적인 화면(스크롤, 동영상 등)은 120Hz로 완전히 매끄럽다.
- 창을 드래그하거나 `Super`로 오버뷰를 열고 닫을 때만 순간적으로 버벅인다.
- **계속 휘저으면(드래그를 멈추지 않으면) 몇 초 안에 저절로 부드러워진다.** 손을 떼고 다시 하면 처음 몇 번은 또 버벅인다.

## 오진단 2건 (측정으로 반증됨)

같은 문제를 조사할 때 먼저 의심하기 쉽지만 이 케이스에서는 아니었던 경로:

1. **컴포지터/패널이 60Hz로 떨어진다** — wayland `presentation-time` 프로토콜로 직접 측정한 결과 반증. frame callback 118~119fps, presentation 간격 p50 8.33ms(=120.001Hz), 60초 측정에서도 놓친 프레임 0.45%. 패널도 XWayland `xrandr` 보고 기준 119.98Hz로 정상.
2. **특정 앱의 `--disable-gpu` 플래그(소프트웨어 렌더링)가 범인** — Discord `.desktop` 오버라이드에 `--disable-gpu`가 박혀 있어 의심했지만, rAF/Chrome FPS 카운터로 A/B 측정한 결과 그 플래그를 단 채로도 120fps였다. 채팅 UI 정도는 소프트웨어 렌더링으로도 120Hz를 따라간다.

두 가설 모두 **정적 화면 측정**이었기 때문에 못 잡았다. 결정적 전환점은 사용자가 "데스크톱 **이동할 때**"라고 특정한 것 — 그 순간부터 범인이 개별 앱에서 GNOME Shell 자체 애니메이션(창 드래그, 오버뷰, 워크스페이스 전환)으로 좁혀졌다.

## 원인 확정

GPU(이 기기는 Intel Arc 140V, Xe 드라이버) 주파수를 초당 샘플링해 애니메이션 구간과 겹쳐본 결과:

```
유휴 (t=0~5s)     cur_freq 400MHz 고정   ← min_freq = rpe_freq = 400
부하 시작(t=5.0)  400 → 1950 튀기 시작
    (t=5.5)       avg 1020MHz            ← 아직 절반
    (t=6.0)       avg 1191MHz
    (t=6.5)       1950MHz 안착           ← 완전히 올라오는 데 ~1.5초
```

GNOME 창 드래그·오버뷰 애니메이션은 0.2~0.4초로 끝나기 때문에, **클럭이 올라오기 전에 애니메이션이 이미 종료**된다. 그래서 모든 짧은 동작이 GPU 성능의 1/4 이하(400~700MHz)로 그려진다. 계속 휘저으면 부하가 끊기지 않아 클럭이 유지되고, 그래서 "계속하면 부드러워진다"는 체감과 정확히 일치한다.

이 사이 gnome-shell CPU 사용률은 시종일관 0~2%였다 — **CPU 병목이 전혀 아니다.**

## 진단에 쓴 측정 기법 (재사용 가능)

- **wayland `presentation-time` 프로토콜**: 최소 클라이언트를 직접 만들어 frame callback과 실제 vblank 기준 presentation 타임스탬프를 읽으면, 컴포지터가 "정직하게" 몇 Hz로 프레임을 내보내는지 패널 리프레시(`refresh` 필드, ns 단위)까지 확인 가능. 앱 쪽 rAF 측정과 분리해서 컴포지터/패널 결백을 증명하는 데 유용.
- **120Hz vs 60Hz 시각 비교자("ruler")**: 평균 이동 속도는 같고 갱신 주기만 다른 두 막대(매 프레임 갱신=120Hz 모션 / 2프레임마다 갱신=60Hz 모션)를 나란히 띄워, 사용자의 "느려 보인다"는 체감이 실제 측정치와 일치하는지 눈으로 교차검증. 측정이 깨끗한데 체감이 다르면 이 비교자로 모순 여부를 먼저 가른다.
- **sysfs `act_freq`/`cur_freq` 초당 샘플링**: GPU 주파수를 프레임 측정과 같은 시간축에 찍으면 "몇 초 뒤 저절로 좋아짐" 같은 정성적 체감을 클럭 램프업 곡선과 직접 대응시킬 수 있다.
- **같은 바이너리, 플래그만 바꾼 대조 실험**: XWayland(`--ozone-platform=x11`) vs 네이티브 Wayland처럼, 변수 하나만 바꿔 라운드별로 재측정하면 우연/노이즈와 진짜 원인을 구분하기 쉽다.

## 해결

GPU 최저 클럭 바닥을 올려 램프업 거리를 줄인다(1550MHz→950MHz 폭 단축):

```
pkexec /bin/sh -c 'echo 1000 > /sys/devices/pci0000:00/0000:00:02.0/tile0/gt0/freq0/min_freq'
```

경로의 `tile0/gt0`는 Xe 커널 드라이버(i915 후속) 구조다. 적용 후 유휴 상태에서도 `cur_freq`가 1000MHz 아래로 내려가지 않는 것을 확인했다.

**원복(되돌리기)**:
```
pkexec /bin/sh -c 'echo 400 > /sys/devices/pci0000:00/0000:00:02.0/tile0/gt0/freq0/min_freq'
```
sysfs 값이라 **재부팅하면 자동으로 400(기본값)으로 돌아간다** — 지금 적용한 상태 자체는 위험 없는 임시 조치.

## 트레이드오프

유휴 클럭을 올리면 **배터리 사용 시간이 줄어든다.** AC 연결 상태에서는 손해가 없지만, 영구 적용(systemd/udev로 부팅 시 자동 설정)한다면 "AC일 때만 1000, 배터리일 때는 400"처럼 전원 상태에 따라 분기하는 편이 낫다.

## 미해결로 남은 것

- **"오늘 갑자기 시작됐다"는 원인은 못 찾음.** 조사 당일 패키지 변경 0건, 디스플레이 설정(`monitors.xml`)은 수개월간 변경 없음. GPU 전력 관리 동작 자체가 그날 바뀔 계기가 안 보여, 원래 있던 증상을 그날 처음 인지했을 가능성이 있다.
- **XWayland 프레임 페이싱**: 소수 배율(1.5) 환경에서 X11 앱(VS Code, Claude Desktop, Notion, Discord 등 다수)은 mutter가 정수 배율 2배 버퍼(3840×2400, 패널 2880×1800 대비 78% 더 많은 픽셀)를 그리게 하고, 프레임 간격도 vsync에 안 물려 있다(min 4.6ms < 8.33ms 프레임 예산). 이번 프레임 드랍의 주범은 아니었지만 별개 비효율로 남아 있다.
