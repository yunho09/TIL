# 리눅스에서 앱별 메모리 점유를 정확히 재는 법 (PSS, zram/shmem/slab)

여러 앱이 메모리를 나눠 먹고 있을 때 "뭐가 이렇게 많이 먹지"를 진단하려면, 프로세스별 RSS를 단순히 더하면 안 된다. 공유 라이브러리·공유 메모리가 여러 프로세스에 중복으로 잡혀 실제보다 부풀려지기 때문이다.

## RSS 대신 PSS로 합산

- **RSS**(Resident Set Size)는 각 프로세스가 매핑한 실제 메모리 크기지만, 여러 프로세스가 같은 공유 라이브러리·공유 메모리를 매핑하면 그 부분이 프로세스마다 전체 크기로 중복 계산된다. Chrome/Electron처럼 프로세스 수가 많은 앱일수록 왜곡이 커진다.
- **PSS**(Proportional Set Size)는 공유된 페이지를 매핑한 프로세스 수로 나눠 배분하므로, 앱별로 합산해도 실제 물리 메모리 사용량과 맞아떨어진다. 앱 하나가 프로세스를 몇 개로 쪼개 떠 있든(Chrome 43개, Figma 15개처럼) PSS로 그룹 합산해야 앱 간 비교가 의미 있다.

## 앱 목록만으론 총량이 안 맞는다 — zram/shmem/slab도 더해야 한다

앱별 PSS를 다 더해도 `free`가 보여주는 총 사용량에는 못 미친다. 앱이 아닌 다음 요소들이 별도로 실제 RAM을 차지하기 때문에, 이것들을 더해야 총량이 설명된다:

- **zram** — 압축 스왑이 RAM 안에 상주한다. 예: 4.9GB 분량 데이터를 2.4배로 압축해 2.07GB로 보관. zram이 꽉 차가는 중이면 [[절전-복귀-지연-원인과-zram-도입]]에서 겪은 절전 복귀 지연과 같은 증상이 재발할 수 있는 전조 신호다.
- **Shmem/tmpfs** — `/dev/shm` 등 GPU·Electron이 프로세스 간 공유 버퍼로 쓰는 영역. `ps`/`smem` 프로세스 목록에는 온전히 안 잡힌다.
- **커널 slab** — 커널 내부 캐시. 상당 부분(관찰 사례에서 약 70%)은 메모리 압박 시 회수 가능한 캐시라 당장 위협은 아니다.
- 페이지테이블 등 소소한 커널 오버헤드.

## 정리 우선순위 판단법

Electron 기반 앱(Figma, Discord, VS Code, Claude Desktop 등)은 각자 자기 몫의 Chromium 런타임을 통째로 들고 있어서, **하나를 끄면 그 앱의 점유가 통째로 돌아온다** — 브라우저 탭을 하나 닫는 것과는 회수되는 단위가 다르다. 그래서 "언제 안 쓰는지 아는 앱 중 가장 큰 것"부터 끄는 게 여러 앱을 조금씩 정리하는 것보다 체감 효과가 크다. Figma 데스크톱 앱의 구체적인 원인은 [[Figma-데스크톱-앱-메모리-중복]] 참고.
