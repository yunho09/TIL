# 낙관적 락(`@Version`)만으로는 스테일 폼 덮어쓰기를 못 막는다 — version을 클라이언트가 왕복시켜야 한다

공유 냉장고의 재료 수정 API에서 `@Version`을 걸고 409 처리까지 했지만, 코드 리뷰가 "요청·응답에 `version`이 없어서 오래된 화면의 저장이 다른 멤버의 수정을 조용히 덮어쓴다"고 지적했다. 해결은 응답에 `version`을 싣고 수정·삭제 요청에 되돌려 받아 서비스에서 비교하는 것이다. 같이 PATCH→PUT 전환, 변경 없는 저장의 버전 재확인 문제도 나왔다.

## 왜 `@Version`만으론 부족한가
- 서비스가 한 요청 안에서 엔티티를 다시 로드해 고치면, `@Version`은 **밀리초 단위로 겹치는 두 트랜잭션**만 잡는다.
- 시나리오: A가 수정 모달을 열어 둔 사이 B가 저장 → 30초 뒤 A가 저장하면 A의 요청은 최신 version을 읽어 그대로 성공(200)하고 B의 변경이 사라진다. 409 메시지가 약속한 상황을 못 잡는 것.
- **해결**: `FridgeItemResponse`에 `version` 포함 → `FridgeItemUpdateRequest`에 `version` 필수 → 서비스에서 `!item.getVersion().equals(request.version())`이면 충돌 예외(409 `CONCURRENT_MODIFICATION`). 삭제도 `DELETE ...?version=`로 동일 적용. 목록 조회 응답에도 `version`이 있어야 모달이 값을 받는다.
- `ObjectOptimisticLockingFailureException`은 커밋 시점에 터지므로 전역 예외 핸들러에서 409로 매핑.

## 변경 없는 저장의 허점 (CodeRabbit 지적)
- 값을 하나도 안 바꾸고 저장하면 Hibernate가 UPDATE를 건너뛰어 **저장 시점에 version을 다시 검증하지 않는다**. 그 사이 다른 멤버가 고쳤어도 200과 옛 `version`이 반환돼 화면이 "최신으로 저장됨"으로 오해한다(데이터 손실은 아님).
- 고침: 비교 후 저장 직전에 **버전을 한 번 더 확인**하는 한 줄 추가 → 바뀐 값이 없어도 그 사이 수정됐으면 409. 재현 테스트(같은 값 저장 중 다른 멤버가 수정)는 수정 전 실패·후 통과 확인.
- 제안됐던 "저장마다 버전 강제 증가"는 값이 바뀐 요청에서 버전이 한 번에 2씩 오를 수 있어 채택하지 않음.

## PATCH → PUT
- 모달의 세 칸(이름·이모지·유통기한)을 통째로 바꾸는 동작인데 보내지 않은 칸이 null로 지워졌다(`{"name":"두부"}`만 보내면 emoji·expiresAt이 사라지고, 유통기한이 없어진 재료는 추천에서 "유통기한 없음"인 채 계속 사용 가능으로 취급됨). "일부만 수정"을 뜻하는 PATCH와 동작이 어긋나므로 **실제 의미에 맞게 PUT**으로 바꾸고 FE가 항상 세 칸을 보내게 했다.
- 이름 길이 제한은 요청 DTO 30자 vs 컬럼 50자로 달랐다 → 등록 API가 아직 없어 DB 기준 **50자**로 통일(전체 교체라 31~50자 이름의 재료는 이모지만 바꾸려 해도 400이 되는 문제 방지).
