# MySQL 잠금 읽기와 H2 테스트 사각지대 (bium-be)

운영 DB는 MySQL(InnoDB), 테스트 DB는 H2인 Spring 프로젝트에서 동시성 코드를 리뷰하다 나온 두 가지: **트랜잭션 스냅샷 때문에 잠금을 기다려도 옛 데이터를 읽는 문제**와 **로그 INSERT가 FK 공유 락을 잡아 생기는 데드락**. 둘 다 H2 테스트로는 재현되지 않는다.

## 1. 락을 기다렸다가도 옛 데이터를 읽는다 (REPEATABLE READ 스냅샷)
- 상황: 초대 코드 "새로 만들기"를 동시에 두 번 누르면 쓸 수 있는 코드가 둘 남는 문제. `fridges` 행을 `PESSIMISTIC_WRITE`로 잠가 직렬화하려 했다.
- 함정: MySQL 기본 격리 수준(REPEATABLE READ)은 트랜잭션에서 **처음 일반 SELECT를 한 시점의 스냅샷**으로 계속 읽는다. 뒤 요청이 냉장고 락을 기다렸다가 풀려도, 그 뒤 일반 조회는 앞 요청이 커밋한 새 코드를 못 본다 → 기존 코드를 못 막아 활성 코드가 둘 남음. (CodeRabbit이 지적, 처음 리뷰에서는 못 잡음)
- 해결: 기존 코드를 막을 때 쓰는 조회를 **잠금 읽기(`SELECT ... FOR UPDATE`)**로 추가(`@Lock(PESSIMISTIC_WRITE)` 쿼리). 잠금 읽기는 스냅샷이 아니라 **현재 커밋된 최신 행**을 읽는다. SQL 로그로 `for update`가 실제로 붙는지 확인했다.
- "지금 쓸 수 있는 코드 보기" 같은 순수 조회는 막을 일이 없어 일반 조회 유지.
- 냉장고 행 락은 남겨 둔다: 활성 코드가 하나도 없을 때는 잠글 행이 없어서, 두 요청이 동시에 INSERT하는 것을 막으려면 부모 행 락이 필요.
- H2는 읽기 방식이 달라 재현 불가 → 이 문제만 잡는 자동 테스트는 못 넣었다(PR에 한계로 명시).

## 2. 로그 INSERT가 FK 공유 락을 잡아 생기는 데드락
- 상황: 재료 삭제(소프트 삭제 `UPDATE`)와 활동 기록 `INSERT`를 한 트랜잭션에서 한다.
- 원인 체인(MySQL/InnoDB 문서화된 동작, 리뷰어가 코드로 추론·재현은 안 함):
  1. 로그 ID가 DB 생성(IDENTITY)이라 `save` 즉시 INSERT가 나감.
  2. 재료의 `UPDATE ... where version=?`은 커밋 시점(flush)에야 나감.
  3. 로그의 FK 검사가 `fridge_items` 행에 **공유 락**을 잡음.
  4. 같은 재료를 두 요청이 동시에 지우면 둘 다 공유 락을 쥔 채 커밋 때 배타 락을 요구 → 데드락, 하나가 죽음(error 1213) → `CannotAcquireLockException`. `@Version` 충돌(`OptimisticLockingFailureException`→409)만 매핑해 둔 핸들러에서는 일반 500으로 떨어짐.
- 해결: **본 변경을 먼저 `flush()`해 배타 락을 잡은 뒤** 로그를 넣는다(`update()`는 원래 이 순서였음). 늦게 온 요청은 다시 깔끔한 409.
- 같은 부류: 두 경로가 `fridges` 행과 초대 행을 **서로 반대 순서로 잠그면** 데드락 → 락 순서를 통일(내보내기에서 로그 기록을 먼저 해 `fridges` 행부터 만지게 함).

## 3. 같이 나온 작은 교훈
- 컨트롤러 테스트가 `@Transactional`이면 모든 MockMvc 호출이 한 트랜잭션·한 영속성 컨텍스트를 공유해 flush/롤백 버그를 가린다 → "실패하면 기록도 롤백"은 **트랜잭션을 나눈 실제 커밋 테스트**로 확인([[낙관적-락-version-스테일-수정-방지와-PUT-전환]]의 동시 수정 테스트 패턴). 테스트 이름은 실제로 검증하는 것에 맞출 것(순서만 검증하면서 "롤백"이라 부르지 않기).
- 고친 부분을 **일부러 되돌려 새 테스트가 실패하는지** 확인하면 버그를 잡는 테스트인지 알 수 있다.
- 바뀐 값이 없는 저장에 "수정" 기록이 쌓이지 않게: flush 후 version이 안 바뀌었으면 로그 생략.
- 기록 메서드는 `@Transactional(propagation = MANDATORY)`로 "같은 트랜잭션 안에서만" 계약을 강제. 같은 타입(`Long`) 인자 순서는 프로젝트 관례(userId 먼저)에 맞춰야 바뀌어도 컴파일이 통과하는 사고를 막는다.
- 정렬 기준은 인덱스와 맞추기: 인덱스가 `(fridge_id, created_at)`이면 `order by id`는 매번 filesort → `order by createdAt desc, id desc`.
- 공개 참여 API(코드 입력)에는 호출 제한이 필요: 8자(32종) 코드는 약 1.1×10¹² 가지라 활성 코드가 1,000개·초당 1,000회 시도면 약 13일. 기존 `RecommendationRateLimiter` 패턴 재사용 권장 → [[LLM-프롬프트-입력-검증과-공개-API-호출-제한]].
