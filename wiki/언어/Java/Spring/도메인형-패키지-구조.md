# 도메인형 패키지 구조

Spring 프로젝트를 계층(controller/service/…)이 아니라 **도메인 먼저 쪼개고 각 도메인 안에서 계층을 나누는** 구조. 도메인을 나누는 기준(ERD 테이블 ≠ 도메인), 도메인 간 참조 규칙, 만드는 순서를 정리한다. 컴포넌트 스캔 기준점은 [[스프링-컨테이너]], 계층별 역할은 [[스프링-CRUD-계층구조]], 엔티티 작성은 [[ERD-to-JPA-엔티티-변환-팁]] 참고.

## 기본 뼈대
```
src/main/java/com/example/project/
├── domain/
│   ├── user/
│   │   ├── entity/      User.java
│   │   ├── repository/  UserRepository.java
│   │   ├── service/     UserService.java
│   │   ├── controller/  UserController.java
│   │   └── dto/{request,response}/
│   ├── post/            (동일 구조)
│   └── comment/         (동일 구조)
└── global/
    ├── common/          BaseTimeEntity
    ├── config/          JpaConfig, SecurityConfig, SwaggerConfig
    ├── error/           ErrorCode, GlobalExceptionHandler, CustomException
    └── security/        JWT 등
```
- `global` 대신 `common`/`core`도 같은 역할. **하나 골라 끝까지 일관되게.**
- `global`은 **기술적 공통 코드** 자리 — 엔티티를 넣지 않는다. 어느 도메인에도 안 붙는 엔티티는 `domain/` 밑에 그 이름으로 새 폴더.

## 도메인 나누는 기준
- **ERD 테이블 = 도메인이 아니다.** 가장 흔한 실수.
  - `users`·`user_profiles`·`user_roles` → `user` 도메인 하나
  - `orders`·`order_items` → `order` 도메인 하나
- 기준: **"이 테이블이 혼자 살 수 있나?"** `order_items`는 `orders` 없이 의미가 없으니 같은 도메인. `posts`와 `comments`는 FK로 이어져도 각각 독립 개념이면 분리 가능.
- 애매하면 **일단 합치고 나중에 쪼갠다.** 처음부터 잘게 나누면 도메인 간 참조가 지저분해진다.
- N:M 중간 테이블은 주된 쪽 도메인에 (`OrderItem` → `domain/order/entity/`).

## 도메인 간 참조
- 엔티티 참조는 정상 (`Post`가 `User`를 `@ManyToOne`).
- 단 **Service 레벨 참조는 한 방향만.** `PostService`↔`UserService`가 서로 부르면 **순환 참조로 앱이 안 뜬다** ([[빈과-DI]]의 생성자 주입 시 순환 의존 오류).

## 작은 프로젝트는 평평하게
- 도메인이 5개 이하면 `entity/` 등 하위 폴더 없이 `domain/user/` 바로 밑에 클래스를 두어도 된다. 파일이 늘면 그때 나눠도 늦지 않다.

## 만드는 순서
- 폴더를 미리 다 파지 않는다. **ERD에서 가장 독립적인 테이블 하나**(보통 `user`)를 골라 그 도메인 한 벌(엔티티→리포지토리→서비스→컨트롤러→DTO)을 끝까지 완성 → 그게 템플릿이 되고 나머지는 복사해 채운다. 빈 폴더부터 만들면 절반은 채워지지 않은 채 남는다.
