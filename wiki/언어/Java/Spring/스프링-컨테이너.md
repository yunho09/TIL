# 스프링 컨테이너

> 컨테이너(ApplicationContext) = **`Map<이름, 객체>`** 로 이해하면 된다.
> `SpringApplication.run()` 한 줄 안에서 스캔 → 설계도 등록 → 생성·주입이 전부 끝난다.

## 빈은 메모리에만 존재한다

디스크에 있는 `.java`/`.class`는 **설계도**일 뿐, 객체가 아니다. 서버가 뜨면서 스프링이 그 설계도를 읽어 `new`를 대신 실행하고, 결과 객체를 힙 메모리 위 컨테이너의 Map에 보관한다.

```java
// 컨테이너 내부 (개념적으로)
Map<String, Object> 창고 = {
    "postService"    : (힙 메모리의 PostService 객체),
    "postRepository" : (힙 메모리의 PostRepository 구현체),
    ...
}
```

- **앱을 끄면 사라진다.** 창고도 그 안의 객체도 프로세스가 죽으면 증발 — 데이터를 남기려면 DB([[MySQL-연동]])가 필요한 이유.
- 확인하는 유일한 방법은 실행 중 창고에 물어보는 것뿐. 폴더를 뒤져도 "만들어진 객체"는 안 보인다.
- 필드에 다른 빈을 주입받으면 **같은 객체의 참조**를 공유한다(복사 아님) — 자바스크립트 객체 참조 대입과 동일한 감각.

## 조립 순서 (서버 시작 시, 딱 한 번)

```
run() 실행
→ 메인 클래스 패키지 하위 스캔
→ @Component 계열 어노테이션 발견 (@Service, @Repository, @RestController 포함)
→ 의존 관계 계산해서 생성:
   ① 아무것도 필요 없는 것부터 (예: Repository)
   ② 그걸 필요로 하는 것 (예: Service)
   ③ 그걸 필요로 하는 것 (예: Controller)
→ 전부 창고에 보관 (싱글톤). 톰캣이 포트에서 대기 시작
```

설정이 틀리면(예: 같은 타입 빈이 둘이라 못 고름) 요청 한 번 오기 전에 **시작하자마자 죽는다** — 실패는 빠를수록 좋다는 설계.

## @SpringBootApplication의 정체

3개가 합쳐진 어노테이션이다:
- `@ComponentScan` — 이 패키지 아래를 뒤져 빈 후보를 찾음
- `@EnableAutoConfiguration` — 의존성(build.gradle)을 보고 톰캣, ObjectMapper, DataSource 등을 자동 등록
- `@Configuration`

## 컴포넌트 스캔 기준점 = 메인 클래스 패키지

`@SpringBootApplication`이 붙은 클래스의 패키지 **하위만** 스캔 대상이다. 그 밖에 두면 `@Component`를 붙여도 못 찾는다.

```
com/example/springpractice/     ← 메인 클래스 위치 = 기준점
├── controller/  ✅ 스캔됨
└── service/     ✅ 스캔됨

com/other/       ❌ 스캔 안 됨
```

패키지 이름은 **폴더 경로와 반드시 일치**해야 한다(`package com.example.springpractice;` ↔ `com/example/springpractice/`). 앞부분(`com.example.springpractice`)은 프로젝트 생성 시 `group`(제작자/조직, 역도메인) + `artifact`(프로젝트명) 조합으로 정해지고, 전 세계 이름 충돌을 피하려고 도메인을 뒤집어 쓰는 관례다. 뒷부분(controller, service...)은 자유롭게 정한다.

### src 폴더 구조

```
src/
├── main/                              ← 실제 앱 코드 (배포에 포함)
│   ├── java/                         ← .java만, 컴파일되어 .class
│   │   └── com/example/springpractice/   ← group+artifact, 스캔 기준점
│   └── resources/                    ← 자바 아닌 것 (yaml, 설정 등), 그대로 복사
└── test/                              ← main과 대칭 구조, 배포에 안 들어감
```

계층 폴더(controller/service/domain/repository)는 **역할별** 분리(현재 방식)이고, 도메인이 여럿으로 늘면 **기능별**(post/, user/ 폴더 안에 각각 4계층) 분리도 쓴다.

## getBean은 학습용, 실무는 생성자 주입

```java
ApplicationContext context = SpringApplication.run(...);
UserService userService = context.getBean(UserService.class);   // 학습/실험용
```

`getBean`으로 직접 꺼내는 건 IoC의 반대 방향(내가 창고에 손을 넣음)이라 실무에서는 거의 안 쓴다. 실제 흐름은 요청이 오면 스프링이 알아서 담당 빈을 찾아 실행하고, 필요한 다른 빈은 생성자로 주입받는 것. main은 보통 원래 한 줄:

```java
public static void main(String[] args) {
    SpringApplication.run(SpringPracticeApplication.class, args);
}
```

"서버 시작 시 뭔가 실행하고 싶다"는 요구에는 `getBean` 대신 `CommandLineRunner`를 쓴다(이름만 알아두면 됨).
